# Vibecoding 传统 vs Vibe 做法对比分析（要点版）

> 本文件是《Vibecoding 传统与 Vibe 做法对比分析报告》的要点版，仅保留结论与关键证据，供快速查阅与汇报使用。完整论证见 [[Vibecoding传统与Vibe做法对比分析报告]]。
> 项目：天平校验视频分析系统（第 1 组）｜ 团队 2 人双 PM ｜ 需求 22 FR / 6 NFR / 7 AC

---

## 一、一句话结论

- **Vibe 没有取消九大知识领域里的任何一个，只是把「昂贵、易偷懒、可自动化的环节」交给 AI/工具，人只留两件事：定边界与验收标准、盯真实验证。**
- 本项目成效：成本 53 人时 vs 计划 282 人时；质量 78 Java + 5 OCR 全绿；过程 5 基线 + 6 变更单 + Git 双留痕。

## 二、九大领域速览

| 领域 | 传统核心 | Vibe 做法 | 结果 |
|---|---|---|---|
| 范围 | 需求+WBS+变更控制 | AI 起草、人审定、CR-001 留痕 | ✅ |
| 进度 | 甘特图+关键路径 | 脚本化甘特图、用测试数当进度 | ✅ |
| 成本 | 估算+EVM | 人时大幅压缩（53 vs 282） | ✅（归集滞后） |
| 质量 | QA/QC+缺陷 | TDD+code-review 前移关卡、78+5 全绿 | ✅ |
| 配置 | 基线+变更+SCCB | Git 分支+5 基线+6 变更单 | ✅ |
| 团队 | 组织+RAM | 2 人双 PM、AI 放大产能、接口先行 | ✅ |
| 风险 | 识别+Top5+跟踪 | 技术尖峰提前验证、R1~R15 清单（跟踪 12 项） | ⚠️ 部分 |
| 沟通 | 会议+纪要 | Git/互审/交接文档替代会议 | ✅ |
| 合同 | 招投标+合同 | 自制/外购分析→无外包 | ✅ |

## 三、逐领域要点

### 3.1 范围管理
- **传统**：需求收集 → SRS → WBS → 范围说明书 → 变更控制（教材第 4、5 章）。
- **为什么**：防「范围蔓延」——需求膨胀、边界漂移会拖垮进度成本。
- **Vibe**：AI 起草 SRS/WBS，人逐条审定业务规则（±0.05%、身份卡阻断等）；变更走 CR-001；文档与代码同库版本化。
- **是否解决**：✅ 解决，可追溯性更强；⚠️ 风险=人若把「审定」也交给 AI，边界失守。
- **适合**：边界清晰、可规则化的小系统；**不适合**：需求模糊需大量澄清的探索型项目。

### 3.2 进度管理
- **传统**：活动排序 → 排程 → 甘特图/网络图/关键路径 → 里程碑 → 挣值跟踪。
- **为什么**：不排程就不知何时交付、哪里是瓶颈；痛点=重排甘特图成本高。
- **Vibe**：`render_gantt.py` 脚本化甘特图，改数据即重绘；用「78+5 测试通过」代替主观百分比；关键路径随迭代滚动重估。
- **是否解决**：✅ 解决；⚠️ 仍需人及时回填实际数据。
- **适合**：迭代式、有可运行产物/测试的项目；**不适合**：纯瀑布、按合同节点对外报量。

### 3.3 成本管理
- **传统**：估算 → 预算 → 实际归集 → CV/CPI 挣值分析。
- **为什么**：人时资金有限，防「超支后知后觉」。
- **Vibe**：乙编码 62 人时计划 → 实际 3 人时；全项目 53 人时（管理文档占 28）。
- **是否解决**：⚠️ 部分——成本本身大降，但**工时归集一度滞后到收尾才补**。
- **结论**：Vibe 压缩执行成本，未必压缩管理成本；**适合**重复编码多、人力单价高的项目，**不适合**按工时计价、需精确归集的项目。

### 3.4 质量管理
- **传统**：质量计划 → QA（过程）/QC（测试评审）→ 缺陷跟踪。
- **为什么**：缺陷发现越晚修复越贵；痛点=测试常被压缩到末期后补。
- **Vibe**：`tdd` 技能固化红绿循环；`code-review` 切片即审（CR-YI-01/02/03）；78+5 全绿；DEF-001/002 闭环。
- **是否解决**：✅ 解决，Vibe 最亮眼处；⚠️ AI 测试可能「只测实现不测意图」，断言需人确认。
- **适合**：可自动化验证的系统（尤其纯函数）；**不适合**：UI 审美、硬件、安全关键。

### 3.5 配置管理（专题详见详细报告第 4 章）
- **传统**：配置项标识 + 基线 + 变更控制（SCCB）+ 状态报告/审计。
- **为什么**：回答「谁改了、改了什么、为什么改、能否回退」；痛点=小项目流于形式。
- **Vibe**：Git 分支承载版本；5 基线（B_RM/DES/CODE/TEST/REL）；6 变更单 CM-001~006；环境基线 + 自检脚本。
- **是否解决**：✅ 解决，文档与代码同源、账实相符；⚠️ SCCB 决策留痕仍需人自觉。
- **关键区别**：版本控制从「人肉登记/签入签出」变成「Git 内建」，人只补决策层。

### 3.6 团队（资源）管理
- **传统**：组织结构 → 角色职责 → RAM/OBS → 团队建设。
- **为什么**：防「职责不清推诿、人手不足延误」。
- **Vibe**：2 人双 PM、各兼多职；AI 放大个人产能；接口先行 + feature 分支避免冲突；交接文档固化边界。
- **是否解决**：✅ 解决；⚠️ 多人多 AI 并发时接口漂移会指数级放大，需契约测试/CI 门禁。
- **适合**：小团队（1~3 人）、边界清晰；**不适合**：大型团队多 AI 并发。

### 3.7 风险管理
- **传统**：识别 → 定性/定量 → Top5 → 应对 → 持续跟踪。
- **为什么**：项目充满不确定性，防「事发才处理」。
- **Vibe**：风险计划 + 执行期 Top5 + R1~R15 清单（跟踪 12 项）；技术风险靠「技术尖峰」提前验证。
- **是否解决**：⚠️ 部分——风险最终都闭环，但**发现时机偏晚**（DEF-001 示值 OCR 拖到 11-02）。
- **核心教训**：Vibe 让常规开发变快，反而容易低估「需真实验证的未知点」——「看起来做完了」≠「验证通过了」。
- **适合**：不确定性集中在「代码可实现性」；**不适合**：物理世界/合规/外部依赖。

### 3.8 沟通管理
- **传统**：沟通计划 → 干系人分析 → 会议机制 → 纪要。
- **为什么**：防「信息不对称、决策无留痕」。
- **Vibe**：以 Git 提交/结对互审/交接文档替代正式会议；提交即留痕、可异步回溯。
- **是否解决**：✅ 解决；代价=缺实时同步，2 人团队由互审补足。
- **适合**：小团队、异步协作、文字化习惯好；**不适合**：多干系人高频同步、强情感协调。

### 3.9 合同（采购）管理
- **传统**：自制/外购分析 → 招投标 → 合同签订管理 → 履约验收。
- **为什么**：决定哪些自己做/外包，管控供应商履约。
- **Vibe**：自制/外购分析 → 结论「无外包」，一份《合同管理说明》闭环。
- **是否解决**：✅ 解决（且被 Vibe 从根本上消解）——AI 压低自制成本，可外包边界收缩。
- **适合**：自制成本可被显著压低、无合规外购要求；**不适合**：依法规/资质必须外包。

---

## 四、总结要点

**适合 Vibe**：
1. 小团队、边界清晰、以代码为主要交付物；
2. 可自动化测试/验证、有明确验收标准；
3. 重复性编码占比高、人力单价高。

**不适合 Vibe**：
1. 大团队多人多 AI 并发（接口漂移失控）；
2. 强监管/纸质签批/实物交付（电子留痕法律效力不足）；
3. 物理世界不确定性为主、或需求高度模糊需大量面对面澄清。

**两条铁律（不可外包给 AI）**：
- 边界与验收标准由人定；
- 真实验证由人盯。
