## 1. 引言

### 1.1 目的
规定本项目的配置标识、基线与配置库、变更控制、配置审计与状态统计，**管理开发过程中的变化，维护产品的完整性与可追溯性**（教材 §9.1.1）。

### 3.2 配置库与工作空间

- **配置库（受控库）**：集中存储所有基线配置项及版本、修改请求、变化记录；库中文件不可直接改，更改即产生新版本（教材 §9.2.2）。
- **三类工作空间**（分支）：

| 空间 | 分支 | 权限 |
|---|---|---|
| 个人空间 | feature/* | 仅本人可读写 |
| 团队空间 | develop（dev） | 组内读写、外部只读 |
| 公共空间 | main（master） | 统一存放阶段性成果，只读发布 |

### 3.3 基线

| 基线 | 内容 | 对应里程碑 |
|---|---|---|
| B_RM 需求基线 | SRS、WBS | M1 需求评审（已建立） |
| B_DES 设计基线 | 数据库/架构/原型 | M2 设计评审 |
| B_CODE 代码基线 | 源代码、脚本 | M3 编码完成 |
| B_TEST 测试基线 | 测试计划/用例/报告 | M4 测试完成 |
| B_REL 发布基线 | 部署包、说明、视频 | M6 交付 |

> 基线代表开发过程的里程碑，标志一个阶段结束（教材 §9.1.3）。

### 3.4 变更控制程序

**流程**（教材 §9.2.3）：变更请求 → 变更评估 → 批准/拒绝 → 变更实现。

1. **变更请求**：填写《项目变更申请》，含变更内容、紧急程度、影响分析。
2. **变更评估**：CMO 做**波及分析**，填《项目变更评估表》（技术/进度/预算/接口影响）。
3. **批准/拒绝**：SCCB 决策「直接实现 / 挂起延迟 / 拒绝」；拒绝须通知并留档。
4. **变更实现**：CMO 出库修改 → 验证 → 入库并更新版本标识 → 生成基线变更记录表。

> 变更单模板见 [[附录A 常用的项目管理模板]]。本项目需求已定稿（B_RM），后续变更须走此流程。

### 3.5 配置审计

- **配置管理活动审计**：成员是否符合导入/导出频度、版本升级规则。
- **基线审计**：基线完整性（配置项齐全、编译可产生最终产品）与一致性（需求↔设计↔代码一致、变更波及项均已改）。
- 记录不符合项并跟踪至解决（教材 §9.2.4）。

### 3.6 配置状态统计

定期出具**配置状态报告**：配置库结构、当前基线位置、各配置项版本演进、变更请求数量与历史。

## 4. 分支管理策略（Git）

采用**基于主干的开发**为主（教材 §9.3.2）：

| 分支 | 用途 | 说明 |
|---|---|---|
| `main` | 稳定/发布 | 通过测试、可交付；每里程碑打 Tag |
| `develop` | 集成/开发 | 活跃开发，频繁合入 |
| `feature/*` | 个人空间 | 单个功能开发，完成后合并回 develop |

**提交规范**：每人每天至少一次有规律提交；提交前本地自测，降低污染主干风险；关键节点（M1~M6）在 main 上打标签形成基线。
