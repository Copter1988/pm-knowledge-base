## 1 引言

规定本项目的**基线定义、版本控制、变更控制过程、变更委员会（SCCB）管理与变更控制记录**，以受控方式引入变更、监控执行、确认结果并可追溯，**维护产品的完整性与可追踪性**（教材 §9.1.1）。

## 3 基线定义

### 3.1 基线概念与作用
- **基线**：一个或多个配置项的集合，其内容和状态已通过技术复审并在生存期某一阶段被接受，**只能经正式变更控制过程改变**（教材 §9.1.3）。
- 基线代表开发过程的**里程碑**，是范围、进度、质量与变更的参照点，也是配置库的受控边界。

### 3.2 配置项标识规则
标识格式（教材 §9.2.1）：`项目名_阶段_产品名_V<主>.<次>.<内部>`。
- 项目名 `TPJY`；阶段 `RM`需求 / `DES`设计 / `IMP`编码 / `TEST`测试 / `REL`发布。
- 示例：`TPJY_RM_SRS_V1.2.0`（需求阶段·需求规格说明书·V1.2.0）。

### 3.5 基线的建立、变更与关闭规则
1. **建立**：阶段成果通过评审 → CMO 将配置项入库并打版本标签 → 宣布基线建立（记录于配置状态报告）。
2. **变更**：基线内配置项的任何修改，只能经 §5 变更控制过程与 §6 SCCB 决策；变更实现后重新发布基线版本。
3. **关闭**：下一基线建立后，上一基线转为「已关闭/只读」，仅保留追溯。

## 4 版本控制

### 4.1 配置库与三类工作空间
- **配置库（受控库）**：集中存储所有基线配置项及其版本、变更请求与变化记录；库中文件不可直接改，更改即产生新版本（教材 §9.2.2）。

| 工作空间 | Git 分支 | 权限 |
|---|---|---|
| 个人空间 | `feature/*` | 仅本人读写 |
| 团队空间 | `develop` | 组内读写、外部只读 |
| 公共空间 | `main` | 阶段性成果，只读发布 |

### 4.2 版本号规则
`V<主版本>.<次版本>.<内部版本>`：

| 位 | 触发条件 | 示例 |
|---|---|---|
| 主版本 | 基线级/重大范围或架构变更 | SRS V1.x → V2.0 |
| 次版本 | 新增功能、需求变更（如 CR-002/003） | SRS V1.0→V1.1→V1.2 |
| 内部版本 | 缺陷修复、内部迭代 | 代码 V1.2.0→V1.2.3 |

### 4.3 Git 分支策略与提交规范
采用**基于主干的开发（TBD）** 为主（教材 §9.3.2）：

| 分支 | 用途 | 说明 |
|---|---|---|
| `main` | 稳定/发布 | 通过测试、可交付；每基线打 Tag |
| `develop` | 集成/开发 | 活跃开发，频繁合入 |
| `feature/*` | 个人空间 | 单个功能开发，完成后合并回 develop |

- **提交规范**：每人每天至少一次有规律提交；提交前本地自测，降低污染主干风险。
- **合并评审**：feature → develop 前经另一成员互审（结对，见团队计划 §4.2）。

### 4.4 入库 / 出库（check-in / check-out）规则
1. **入库（check-in）**：配置项完成后提交并**自动锁定**，填写版本标识、描述、关联项。
2. **出库（check-out）**：修改需导出并锁定，期间他人只读；修改后入库生成新版本。
3. **并发修改**：对同一配置项并行修改时走 `feature/*` 分支，合并时解决冲突，避免互相覆盖。

### 4.5 标签（Tag）与基线对应
每次基线建立时在 `main` 上打标签，命名 `v<版本>-<阶段>`：

| 基线 | 建议 Tag |
|---|---|
| B_RM | `v1.2.0-rm` |
| B_DES | `v1.0.0-des` |
| B_CODE | `v1.0.0-code` |
| B_TEST | `v1.0.0-test` |
| B_REL | `v1.0.0-rel` |

## 5 定义变更控制过程

### 5.1 变更来源与类型

| 类型 | 示例 | 主要来源 |
|---|---|---|
| 需求变更 | 单位保留、PDF 测量时间、身份卡 OCR（CR-002/003） | 甲方、需求评审 |
| 文档变更 | 文档结构重排、章节号修订（CR-001） | 评审、编制规范 |
| 设计变更 | 数据库字段、接口契约调整 | 设计评审、编码反馈 |
| 代码变更 | 缺陷修复、功能补齐 | 测试、代码评审 |
| 配置/环境变更 | 依赖升级、部署脚本调整 | 运维、部署 |

### 5.2 变更控制流程（教材 §9.2.3）

```
① 变更请求 → ② 登记受理 → ③ 评估（波及分析） → ④ SCCB 决策 → ⑤ 实施（版本控制） → ⑥ 验证与关闭 → 更新基线
```

| 步骤 | 活动 | 责任人 | 产出 |
|---|---|---|---|
| ① 请求 | 填写《项目变更申请》（内容、紧急程度、初步影响） | 提出人 | 变更申请单 |
| ② 登记 | 分配变更号（CR/CM-xxx）、纳入变更日志 | CMO | 变更日志一行 |
| ③ 评估 | 验证完整性；做**波及分析**（功能/进度/成本/接口/测试） | CMO | 变更评估表 |
| ④ 决策 | 按 §6 规则批准 / 挂起 / 拒绝 | SCCB | 决策记录 |
| ⑤ 实施 | 出库修改、验证，提交并更新版本标识 | 开发人员 | 新版本 |
| ⑥ 关闭 | 复核变更已实现、关联项已同步；更新基线 | CMO + SCCB | 关闭记录 |

### 5.3 变更影响分析（评估要点）
逐项评估：**功能范围、进度关键路径、成本、质量、接口、测试用例**，并明确需同步修改的工作产品（WBS、进度、成本、测试、文档），确保一致性。

### 5.4 变更的实现方式（三选一）
- **尽可能快地实现**：紧急/阻塞交付的变更；
- **按特定日期实现**：需协调里程碑的变更；
- **在下一版本中实现**：非紧急的累积变更。

### 5.5 变更相关表单
《项目变更申请》《项目变更评估表》模板见 [[附录A 常用的项目管理模板]]；本项目实际记录见 [[变更单与状态报告]]。

## 6 变更委员会（SCCB）的管理

### 6.1 组成
| 角色 | 人员 | 说明 |
|---|---|---|
| 主席 | 成员甲（PM） | 召集、主持决策，对重大变更有一票否决 |
| 委员 | 成员乙（CMO） | 提供波及分析、执行与记录 |
| 顾问 | 甲方（检验科室） | **需求类变更**须其确认（业务源头） |

### 6.2 职责与权限
- 从技术、进度、成本、组织角度**评估基线变更影响**，决定是否变更（教材 §9.1.4）。
- 批准变更申请、规范变更流程、反馈结果并与管理层沟通。
- 权限：普通变更→SCCB 内部决策；需求类变更→须甲方确认；重大变更→全员评审。

### 6.3 决策规则与会议机制
| 情形 | 决策规则 |
|---|---|
| 普通变更（文档/局部代码） | 甲乙**两人一致**即可 |
| 需求类变更 | 须**甲方确认**（书面/会议纪要） |
| 紧急变更（阻塞交付） | PM 可先行批准实施，**24 小时内追认** |
| 重大变更（影响关键路径 ≥2 天或工作量 ≥10%） | **召开评审会**，三人（含甲方）评审，形成纪要 |

- **会议**：事件驱动（有变更即评审）；重大变更单独召开评审会并记录（模板见 [[../沟通管理/沟通计划（含会议记录）]]）。

### 6.4 与其他角色的关系
- 与 **PM**：SCCB 主席即 PM，决策纳入项目计划。
- 与 **CMO**：CMO 提供波及分析与执行，SCCB 决策。
- 与 **甲方**：需求类变更以甲方为业务源头与最终确认方。
