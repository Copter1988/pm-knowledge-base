# 软件项目质量计划（质量保证与质量控制）

> 项目名称：天平校验视频分析系统　|　组别：第 1 组　|　编制日期：2026-10-01　|　更新日期：2026-11-04

> 依据：[[../../需求规格说明书-SRS]]（§3.2 性能、§附 验收标准）、[[../进度管理/进度计划（甘特图与网络图）]]
> 对应教材：[[第8章 软件项目质量计划]]

## 0. 编制说明

- **方针**：**质量是计划出来的，不是检查出来的**；质量形成于开发过程，**预防重于检查**（教材 §8.1.3、§8.3）。
- **对象**：既管理**产品质量**，也管理**过程质量**（教材 §8.1.4）。
- **三大过程**：**质量计划**（定标准）→ **质量保证 QA**（"完成得是否正确？"，管理职能、审计）→ **质量控制 QC**（"是否正确完成？"，检查职能、发现消除缺陷）。
- **责任人**：**项目经理是质量的最终责任承担者**（教材 §8.5.3）。
- **范围**：覆盖需求、设计、编码、测试、交付全过程的软件过程质量与产品质量（SRS、设计说明书、代码、测试报告、交付物）。
- **引用标准**：教材《软件项目管理案例教程（第5版）》第 8 章；SRS 验收标准 AC-01~07；非功能需求 NFR-001~006。
- **术语与缩写**：QA 质量保证、QC 质量控制、COQ 质量成本、DEF 缺陷编号、AC 验收标准、NFR 非功能需求、PDCA 戴明环。
- **参考资料**：[[../../需求规格说明书-SRS]]、[[附录A 常用的项目管理模板]]、教材第 8 章。
- **版本更新条件**：质量目标、审计/测试安排或质量职责发生变化时更新；每次里程碑评审后按需修订。

**质量规划过程**（教材 §8.5.1、§8.5.2）

- **规划输入**：质量方针（预防重于检查）、SRS（AC-01~07、NFR-001~006）、WBS 工作分解、团队与进度约束。
- **规划方法**：**基准对照**（对齐 2023 中国软件行业缺陷率基准）+ **质量成本分析**（COQ，§5）+ **测试与检查规划**（D1~D4 四层测试，§3）；对判定引擎、视觉识别等高风险点辅以**因果分析图**定位缺陷原因。
- **规划产出**：§1 质量目标与质量模型、§2 QA 审计安排、§3 QC 测试安排、§6 质量职责。

## 1. 质量目标（质量模型）

采用**加权质量模型**（教材 §8.5.1 项目质量模型案例），总分 100 分，**质量目标 ≥ 85 分**，执行中跟踪分数走势。

| 质量特征 | 权重 | 质量子特征 | 权重 | 本项目落地指标 |
|---|---|---|---|---|
| **功能性** | 44.44% | 完整性 / 准确性 / 安全性 | 29.7% / 53.9% / 16.4% | 判定规则 100% 与 §3.1.5 一致；权限隔离、复核后锁定 |
| **可靠性** | 22.22% | 健壮性 / 容错性 / 易恢复性 | 66.6% / 16.7% / 16.7% | 数据每日备份；**最终记录人工核对后 100% 正确（OCR 预填 ≥95%、不足人工兜底）** |
| **效率** | 11.11% | 时间特性 / 资源特性 | 50% / 50% | 单视频识别 ≤ 2 分钟；并发 ≤ 5 人 |
| **易使用性** | 11.11% | 易理解性 / 用户文档 / 易操作性 | 53.9% / 16.4% / 19.7% | "导入→核对→提交" ≤ 3 步；配置/使用说明完备 |
| **标准** | 11.11% | 行业标准 / 企业标准 | 50% / 50% | 符合 SRS、课程交付规范 |

**关键质量目标（可验收）**：

| 目标 | 指标 | 对应需求 |
|---|---|---|
| 判定准确 | ±0.05% 逐示值判定、一票否决、较大误差标记与规则完全一致 | FR-010/011/012 |
| 数据准确 | 最终校验记录经人工核对后 100% 正确；OCR 预填准确率 ≥95%、不足部分人工补录兜底 | FR-004/006 |
| 性能达标 | 单视频识别 ≤ 2 分钟 | NFR-001 |
| 易用达标 | 核心流程 ≤ 3 步 | NFR-004 |
| 缺陷控制 | 交付阶段缺陷率 ≤ P50（13.16 缺陷/千功能点） |

> 加权质量模型与关键质量目标的关系：模型 5 大特征按子特征逐项打分后加权求和得总分（目标 ≥85 分）；关键质量目标 5 项是模型的验收锚点——判定准确/数据准确对应「功能性 + 可靠性」，性能达标对应「效率」，易用达标对应「易使用性」，缺陷控制对应过程质量。执行中每周评审跟踪总分走势。

> 数据准确性口径：教材 §8.7 MSHD 案例以「数据准确性高于 95%」为整体目标；本计划结合「OCR 辅助录入、人工核对兜底」（SRS §2.1.2）拆分为两个口径——最终记录人工核对后 100% 正确、OCR 预填 ≥95% 不足部分人工兜底。

**质量目标分解到工作包**（教材 §8.5.1：目标按 WBS 分解、落实到人）

## 2. 质量保证（QA，过程与产品审计）

QA 是对过程或产品的**结构化独立评估**（质量审计），贯穿整个生命周期，表达为 **"Is it done right?"**（教材 §8.3.1）。

### 2.1 软件过程审计

| 审计对象 | 审计内容 | 时机 | 责任人 |
|---|---|---|---|
| 需求过程 | SRS 完整性、一致性、可检验性 | M1 需求评审（已完成） | 项目经理 |
| 设计过程 | 数据库/架构/原型是否覆盖 SRS | M2 设计评审 | 组员 |
| 编码过程 | 编码规范、评审记录、Git 提交规范 | 编码阶段每周 | 组员 |
| 测试过程 | 测试用例覆盖、缺陷记录闭环 | M4 测试评审 | 项目经理 |

### 2.2 软件产品审计

| 审计对象 | 审计内容 |
|---|---|
| 需求规格说明书 SRS | 章节完整、FR/NFR/AC 齐全（已定稿） |
| 设计说明书 | 数据库设计覆盖 SRS §3.4 数据需求 |
| 代码 | 判定引擎等关键模块符合规范 |
| 测试报告 | 用例覆盖、结论明确 |

### 2.3 审计输出

- 不符合问题记入**质量保证报告表 / 不符合问题表**（模板见 [[附录A 常用的项目管理模板]] 附表 2~4）。
- 重大问题上报项目经理，跟踪至关闭。

### 2.4 实施计划（评审与审计安排）

| 评审/审计 | 频度 | 主持/执行 | 参与人 | 对应里程碑 |
|---|---|---|---|---|
| 高层管理定期评审 | 每里程碑 | 指导教师 | 甲方 + 全组 | M1~M6 |
| 项目经理定期评审 | 每周周例会 | 成员甲（PM） | 全组 | — |
| 项目经理基于事件评审 | 变更/缺陷发生时 | 成员甲（PM） | 相关人 | — |
| 过程审计 | 需求/设计/编码/测试阶段 | 成员乙（QA） | 全组 | M1/M2/编码每周/M4 |
| 产品审计 | 每阶段成果产出后 | 成员乙（QA） | 全组 | SRS/设计/代码/测试报告 |

## 3. 质量控制（QC，发现与消除缺陷）

QC 确定结果与标准是否相符、消除缺陷，表达为 **"Is it right done?"**（教材 §8.3.2）。缺陷越晚消除费用越高，故**每个阶段完成后即开展 QC**。

### 3.1 QC 活动与测试安排（对应进度 D1~D4）

| QC 活动 | 内容 | 对应进度 | 重点 |
|---|---|---|---|
| 代码走查 | 结对编程互审、关键逻辑走查 | 编码阶段 | 判定引擎、留痕逻辑 |
| 单元测试 | 对 ±0.05%、一票否决、较大误差写用例 | D1 | **判定规则正确性** |
| 集成测试 | 模块联调：识别→核对→判定→提交 | D2 | 模块接口 |
| 系统测试 | **3 个视频（2 正确 1 错误）**端到端 | D3 | 识别与提示 |
| 验收测试 | 逐条核对 AC-01~AC-07 | D4 | 需求可检验性 |

### 3.2 测试重点（针对本项目高风险点）

- **判定引擎**：限额实时计算不得引用写死值；9 次示值逐次判定；清洁/水平/内部校正一票否决。
- **视觉识别兜底**：OCR 仅预填，验证"识别不到可人工补录、识别错可改值留痕"。
- **状态机**：待复核/已复核/已作废流转与"提交后示值不可改"。
- **权限**：三类角色隔离、复核后锁定。

## 4. 敏捷质量实践（质量内建 + 质量外延）

本项目为 2 人组、增量开发，采用教材 §8.4 敏捷质量实践：

| 实践 | 在本项目的落地 | 预期效果 |
|---|---|---|
| **结对编程** | 2 人组天然结对，互审关键模块 | 提高质量、促进知识传递（降低人员风险 R3） |
| **TDD** | 判定引擎先写测试用例再实现 | 缺陷前置消除 |
| **版本控制/分支策略** | Git + 分支策略（同时应对风险 R5） | 提高代码稳定性与可追溯性 |
| **持续集成** | 每次合并触发构建与测试 | 减少集成问题 |
| **迭代评审/回顾** | 每里程碑评审、复盘改进 | 尽早发现问题、持续改进 |

> **质量内建**：需求阶段发现问题的修复成本仅为生产阶段的 1/100（教材 §8.4.1），故评审前置。

## 5. 质量成本与指标

### 5.1 质量成本（COQ）

| 类别 | 本项目构成 | 实际投入 |
|---|---|---|
| 预防成本（一致性） | 评审、结对编程、编码规范、测试用例设计 | 约 10 人时（需求评审 4 + 质量管理 6） |
| 评估成本（一致性） | 单元/集成/系统/验收测试、审计 | 36 人时（测试 1.4.1~1.4.4） |
| 缺陷成本（非一致性） | 返工、重新测试（内部）；部署后修正（外部） | 约 4 人时（DEF-001 人工兜底返工，估算） |

> **质检过失比 =（预防 + 评估）÷ 缺陷 =（10 + 36）÷ 4 ≈ 11.5 > 2**，达标（教材 §8.1.3）。即宁可前期多投入预防与评估，减少后期缺陷。
> 本项目质量管理预算 6 人时（成本计划 1.6.5），质检过失比按实际预防投入与缺陷返工成本核算。

### 5.2 质量指标与基准对照

| 指标 | 本项目目标 | 本项目实际 | 行业基准（2023 中国软件行业） |
|---|---|---|---|
| 测试阶段缺陷率 | ≤ P50 | 0.045 缺陷/功能点（1 个 DEF-001 ÷ 22 FP）✅ | 0.16 缺陷/功能点 |
| 交付阶段缺陷率 | ≤ P50 | 不适用（项目未交付） | 13.16 缺陷/千功能点 |
| 测试覆盖率 | ≥ 80% | 行 66.8% / 方法 79.0% / 分支 43.7%（排除 cli 行 75.6%）——**未达标** | 敏捷内建目标 |
| 预防/缺陷成本比 | > 2 | 11.5 ✅ | 努力目标 |

> 行业基准为教学示例值（2023 中国软件行业），实际按项目统计替换。
> **代码覆盖率实测**（jacoco，76 用例 / 0 失败 / 0 跳过）：行 66.8%、方法 79.0%、分支 43.7%，**排除 cli 后行 75.6%**，未达 ≥80% 目标。冒烟测试跑通后 service.frame（22%→67.1%）、controller（32.9%→44.8%）显著提升；`cli` 包（命令行入口 438 行 0% 覆盖，依赖 ffmpeg）已从统计中排除。需求覆盖率（FR 有测试覆盖）21/22 ≈95%，是与代码覆盖率不同的口径。

## 6. 质量组织与职责

| 角色 | 职责 |
|---|---|
| 项目经理 | 质量最终责任人；审批质量计划；主持评审；上报重大问题 |
| QA（成员乙兼） | 规划与维护质量过程；执行过程/产品审计；出具质量报告 |
| QC（开发人员甲/乙） | 代码走查、单元/集成/系统测试；发现并消除缺陷 |
| 全组 | 敏捷质量实践（结对、TDD、CI） |

> 原则：**开发高质量产品是开发组的责任，QA 的职责是规划和维护质量过程**（教材 §8.3.1）。
> **SQA 权利与上报渠道**（教材 §8.5.3、附录 A #6 第二节）：QA（成员乙）对发现的质量不符合项有权记录、要求整改并跟踪至关闭；重大问题除报项目经理外，可直接**上报指导教师（特殊上报渠道，慎用）**。

## 7. 质量记录与跟踪

- **跟踪机制**：结合进度计划的**每周评审**，跟踪质量模型得分走势（目标 ≥ 85 分）。

- **戴明环 PDCA**：计划–执行–检查–措施，落实到责任单位。
