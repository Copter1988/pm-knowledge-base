# 软件项目风险计划（风险清单与 Top5 跟踪）

> 项目名称：天平校验视频分析系统　|　组别：第 1 组　|　编制日期：2026-10-01
> 依据：[[../../需求规格说明书-SRS]]、[[../进度管理/进度计划（甘特图与网络图）]]
> 对应教材：[[第11章 软件项目风险计划]]

## 0. 编制说明

- **过程**（教材 §11.1.3，循环进行）：**风险识别 → 风险评估 → 风险规划 → 风险控制**。
- **方法**：以**风险条目检查表 + 头脑风暴**识别；用**风险分析矩阵**定性评估；**风险值 R = 概率 P × 影响 I** 排序，取 **Top5** 持续跟踪。
- **原则**：采取**主动风险管理**（预防、消灭风险根源），而非被动「救火」（教材 §11.1.3）。
- **风险管理者**：项目经理（负责本计划的维护与跟踪）。

---

## 1. 风险识别

依据 WBS、SRS、项目计划假设与历史经验，按**风险类型**（商业/管理/人员/技术/开发环境/客户/产品/过程）识别，形成风险清单。

| 编号 | 风险事件 | 类别 | 预测角度 |
|---|---|---|---|
| R1 | 视觉识别（OCR/二维码）准确率达不到预期，影响核心功能 | 技术风险 | 已知 |
| R2 | 工期紧（约 11 周、2 人课余投入），关键路径延误 | 管理风险 | 已知 |
| R3 | 人员投入不足 / 流动（学业冲突、兼职时间不够） | 人员风险 | 可预测 |
| R4 | 需求变更（业务规则或判定阈值被甲方调整） | 管理/需求风险 | 已知 |
| R5 | 多人协作导致代码冲突、版本混乱 | 过程风险 | 可预测 |
| R6 | 客户（检验科室）沟通不畅、需求理解偏差 | 客户风险 | 可预测 |
| R7 | 视频质量差（清晰度不足、天平整电变暗）致识别失败 | 开发环境风险 | 已知 |
| R8 | 判定引擎规则实现错误（±0.05% / 一票否决） | 技术/产品风险 | 已知 |
| R9 | 甲方对系统不认可、评分偏低 | 商业/客户风险 | 可预测 |
| R10 | 部署环境差异（内网环境）导致无法运行 | 开发环境风险 | 可预测 |

> 识别方法：风险条目检查表（教材表 11-1，覆盖商业/管理/技术三大类）+ 团队头脑风暴。

## 2. 风险评估

**评估尺度**（教材 §11.3.1，概率、影响各分 5 级），风险值 **R = P × I**：

| 概率级别 | 区间 | 影响级别 | 含义 |
|---|---|---|---|
| 1 极低 | 1%~20% | 1 极微 | 可忽略 |
| 2 低 | 21%~40% | 2 微量 | 轻微 |
| 3 中 | 41%~60% | 3 中等 | 中等 |
| 4 高 | 61%~80% | 4 重大 | 严重 |
| 5 极高 | 81%~100% | 5 致命 | 灾难 |

### 2.1 风险评估结果（按风险值排序）

| 排序 | 编号 | 风险 | 概率 P | 影响 I | 风险值 R | 等级 |
|---|---|---|---|---|---|---|
| 1 | R1 | 视觉识别准确率不达标 | 60% | 60% | **36%** | 高 |
| 2 | R2 | 工期紧、关键路径延误 | 50% | 60% | **30%** | 高 |
| 3 | R3 | 人员投入不足/流动 | 50% | 50% | **25%** | 中高 |
| 4 | R4 | 需求变更 | 40% | 50% | **20%** | 中高 |
| 4 | R5 | 版本/协作混乱 | 50% | 40% | **20%** | 中高 |
| 6 | R6 | 客户沟通不畅 | 40% | 40% | **16%** | 中 |
| 7 | R7 | 视频质量差 | 50% | 30% | **15%** | 中 |
| 7 | R8 | 判定规则实现错误 | 30% | 50% | **15%** | 中 |
| 7 | R9 | 甲方不认可 | 30% | 50% | **15%** | 中 |
| 10 | R10 | 部署环境差异 | 30% | 40% | **12%** | 中低 |

行=概率级（5 高→1 低），列=影响级（1→5）：

| 概率＼影响 | 1 极微 | 2 微量 | 3 中等 | 4 重大 | 5 致命 |
|---|---|---|---|---|---|
| **5 极高** | | | | | |
| **4 高** | | | | | |
| **3 中** | | R5,R7 | R1,R2,R3 | | |
| **2 低** | | R6,R10 | R4,R8,R9 | | |
| **1 极低** | | | | | |

- **区域 A（高风险，须建应对计划）**：R1、R2、R3（概率中 × 影响中等及以上）。
- **区域 B（中高风险，尽量制订应对）**：R4、R5、R6、R8、R9。
- 全部风险均落在 A/B 区，无 D 区（低风险）；**R1（视觉识别）**为最高优先级。

## 3. 风险规划（应对策略）

按教材 §11.4 四大策略（回避/转移/损失控制/自留）与控制手段（损失预防/损失抑制）制定应对。

| 编号 | 风险 | 应对策略 | 具体措施 | 责任人 | 状态 |
|---|---|---|---|---|---|
| R1 | 视觉识别不达标 | **损失控制**（预防+抑制） | 采用成熟开源库 ZXing 做二维码；OCR 预留接口 + **人工录入兜底**；编码前做技术验证（先跑通样例视频） | 组员·开发 | OPEN |
| R2 | 工期紧 | **损失控制**（预防） | 关键路径（C2/C3）重点监控；快速跟进+必要时赶工；末端留 3 天项目缓冲；每周进度评审 | 项目经理 | OPEN |
| R3 | 人员投入不足 | **损失控制**（预防+抑制） | 文档标准化、任务交叉备份、关键模块双人熟悉；预留后备人员 | 项目经理 | OPEN |
| R4 | 需求变更 | **损失控制 + 自留** | SRS 基线 + 变更控制流程；增量式开发响应变更；阈值（0.05%/1%）写死为可配置项 | 项目经理 | OPEN |
| R5 | 版本/协作混乱 | **损失控制**（预防） | Git 版本控制 + 分支策略；配置管理计划；明确责任分工 | 组员 | OPEN |
| R6 | 客户沟通不畅 | **损失控制**（预防） | 业务建模让检验科室参与；原型演示 + 需求确认签字；建立直接沟通渠道 | 项目经理 | OPEN |
| R7 | 视频质量差 | **自留 + 抑制** | 以人工核对为准（OCR 仅预填）；拍摄规范写入使用说明；环境假设已纳入 SRS §2.3 | 组员 | OPEN |
| R8 | 判定规则实现错误 | **损失控制**（预防） | 对 ±0.05%、一票否决写单元测试；代码评审；用 3 个视频（2 正确 1 错误）验证 | 组员·开发 | OPEN |
| R9 | 甲方不认可 | **损失控制**（预防） | 聚焦甲方核心痛点（留痕/自动判定/可回溯）；制作汇报视频；验收标准对齐 | 项目经理 | OPEN |
| R10 | 部署环境差异 | **转移 + 预防** | 利用 12/15–24 协助部署窗口；提前对接内网环境；编写一键配置说明 | 组员 | OPEN |

**风险缓解率**（教材 §11.5）：

```
风险缓解率 =（应对前风险值 − 应对后风险值）÷ 风险缓解成本
```

> 例：R1 应对前 R=36%，经「成熟库 + 人工兜底」应对后降至约 R=15%，若投入约 4 人时的技术验证成本，则缓解率 > 1，**值得投入**。

## 4. 风险控制与 Top5 跟踪

- **Top5 清单**（按风险值，每次跟踪更新）：**R1 视觉识别 → R2 工期 → R3 人员 → R4 需求变更 / R5 版本协作**。
- **跟踪机制**：结合 [[../进度管理/进度计划（甘特图与网络图）]] 的**每周进度评审**同步评审 Top5 风险，记录状态（OPEN / 缓解中 / 已关闭 / 已发生）。
- **触发升级**：当风险状态变为「已发生」时，转为**问题**处理，并启动应对措施（教材：风险未及时处理即转为问题）。
- **跟踪记录**：各次风险跟踪 Top5 见「风险管理 / 风险跟踪记录」（待补）。
