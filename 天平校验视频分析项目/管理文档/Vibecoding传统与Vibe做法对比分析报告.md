# 1. 项目与 Vibecoding 概述

## 1.1 项目背景

天平校验视频分析系统（第 1 组）是「软件项目管理」课程的实训项目，目标是把电子天平的日常校验从「纸质手写」升级为「电子化记录」：**手机录像 + 视觉识别（辅助录入）+ 人工核对**，自动完成校验的记录、判定与归档，实现留痕可回溯、自动判定、可查询导出。

| 维度 | 内容 |
|---|---|
| 核心业务规则 | 3 个砝码各称 3 次（共 9 次示值），示值须在标称值 ±0.05% 内 |
| 角色 | 管理员 1、检验人员 2（李一/李二）、复核确认人员 1（齐一） |
| 技术栈 | Spring Boot 2.7 + Thymeleaf + MyBatis-Plus + MySQL 8 + ZXing（二维码）+ ffmpeg（抽帧）+ RapidOCR（本地文字卡识别）+ Flying Saucer（PDF） |
| 需求规模 | 22 条功能需求（FR）/ 6 条非功能需求（NFR）/ 7 条验收标准（AC） |
| 团队规模 | 2 人（成员甲 `ddddachui`、成员乙 `Copter1988`，双项目经理制） |
| 部署形态 | 内网单机，并发 ≤ 5 人 |
| 交付周期 | 2026-09-26 启动，提交截止 2026-11-25 |

## 1.2 本项目的 Vibecoding 是什么

本报告必须先界定「Vibe」在本项目中的具体含义，否则后续所有比较都会落空。本组的 Vibecoding **不是「把需求扔给 AI 一键生成」**，而是一套**「人定约束、AI 执行、测试与审查兜底」**的工作方式：

| 维度 | 本项目的落地形式 |
|---|---|
| 编码执行者 | Claude Code 作为代码编写与调试的执行者，人负责目标、边界与验收标准 |
| 节奏约束 | 通过 mattpocock-skills 的 `tdd`（红绿循环）、`code-review`（写后即审）、`diagnosing-bugs`（排查沉淀）技能，把方法固化为固定动作 |
| 推进方式 | 垂直切片（tracer bullet）：先跑通一条探路子弹，再并行铺开，禁止一次写完多个切片再测 |
| 质量兜底 | 全项目 78 项 Java 测试 + 5 项 OCR 测试全绿；代码审查产出 CR-YI-01/02/03 三个高严重度修复 |
| 过程证据 | 配置库 5 基线、变更单 CM-001~006、缺陷 DEF-001/002、甲乙交接文档 |

一句话概括：**「人把怎么干活显式写成流程和文档，AI 在护栏内高速执行，测试与审查代替人工盯错。」**

## 1.3 对比方法与五要素说明

本报告严格按《项目管理要求 2026》的五要素展开，每个知识领域统一结构：

1. **① 传统怎么做** —— 传统 PMBOK 方法的完整步骤，并标注教材章节依据；
2. **② 为什么要这么做、解决什么问题** —— 该方法背后的动机与它要消除的管理痛点；
3. **③ 本项目 Vibe 中的做法** —— 本组实际怎么做的，附具体文档、数据、变更单号等实证；
4. **④ 传统 vs Vibe 对比表** —— 从过程、工具、人力、文档、风险等维度逐点对照；
5. **⑤ 原问题是否解决/规避** —— 分「已解决 / 部分解决 / 新产生的问题」三档作诚实判断；
6. **⑥ Vibe 适合哪些情况** —— 结合本项目实际，给出适用与不适用的边界。

> 说明：PMBOK 第六版的知识领域为「整合、范围、进度、成本、质量、资源、沟通、风险、采购、干系人」十大领域；本课程依据教材（第 4~12 章）采用九大领域口径，即「范围、进度、成本、质量、配置、团队（对应资源）、风险、沟通、合同（对应采购）」，其中**配置管理**按课程要求另行单列专题（第 4 章）。

# 2. 全貌总览：Vibecoding 项目管理全貌

## 2.1 九大知识领域对比速览表

| 知识领域 | 传统做法核心 | 本项目 Vibe 中的做法 | 原问题是否解决/规避 |
|---|---|---|---|
| 范围管理 | 需求管理 + WBS + 范围说明书 + 变更控制 | AI 辅助起草 SRS/WBS，人逐条审定业务规则；变更走 CR-001 留痕 | ✅ 解决（范围可控、变更留痕） |
| 进度管理 | 甘特图/网络图/关键路径/挣值跟踪 | 脚本化甘特图（render_gantt.py），随 Git 提交自动重绘与回填 | ✅ 解决（滞后可见、计划随实际迭代） |
| 成本管理 | 估算 → 预算 → 实际成本 → CV/CPI | 人时大幅压缩：全项目实际 53 人时 vs 计划 282 人时 | ✅ 成本下降（但归集口径回填滞后） |
| 质量管理 | 质量计划 + QA/QC + 评审 + 缺陷跟踪 | TDD + code-review 技能前移质量关卡；78+5 测试、DEF 闭环 | ✅ 解决（缺陷早发现、可回归） |
| 配置管理 | 配置项标识 + 基线 + 变更控制 + SCCB + 审计 | Git feature 分支 + 5 基线 + 6 变更单 + 配置库索引 | ✅ 解决（版本/变更/环境可控） |
| 团队管理 | 组织结构 + RAM/OBS + 职责分工 + 团队建设 | 2 人双 PM + AI 放大个人产能 + 接口先行避免冲突 | ✅ 解决（人力不足被产能补足） |
| 风险管理 | 风险识别 + Top5 + 应对计划 + 跟踪 | 技术风险靠「技术尖峰」提前闭环；R1~R15 清单（跟踪 12 项） | ⚠️ 部分（技术风险可控，但尖峰时机略晚） |
| 沟通管理 | 沟通计划 + 会议 + 干系人管理 | 以 Git 提交/结对互审/交接文档替代正式会议 | ✅ 解决（信息以文档与提交留痕） |
| 合同管理 | 采购管理 + 招投标 + 合同 | 自制/采购分析 → 无外包说明 | ✅ 解决（自制决策，无采购风险） |

## 2.2 Vibe 如何重塑项目管理生命周期

传统项目管理按「启动 → 计划 → 执行 → 监控 → 收尾」五大过程组推进；Vibecoding 没有取消任何一个过程组，而是**改变了每个过程组里「哪些工作由人做、哪些由工具/AI 做」的分工**：

| 过程组 | 传统主要工作 | Vibe 下的变化 |
|---|---|---|
| 启动 | 立项、可行性、章程 | 基本不变；AI 辅助起草立项背景与 PPT 摘要 |
| 计划 | 需求、WBS、进度、成本、质量、配置、团队、风险、沟通、合同等十类计划 | 计划文档由 AI 起草、人审定；甘特图脚本化；计划与代码同库版本化 |
| 执行 | 编码、测试、协作 | **变化最大**：AI 承担编码与测试的机械部分，人负责边界/验收/审查 |
| 监控 | 跟踪、度量、变更控制、审计 | 用「可运行的测试数量」代替主观百分比；变更与审计以 Git + 变更单双留痕 |
| 收尾 | 验收、交付、归档、总结 | 交接文档可续接；配置库/基线/环境基线使交付包可复现 |

## 2.3 总体结论（三句话）

1. **Vibe 没有取消传统项目管理的任何一个知识领域**，而是把每个领域里「昂贵、易偷懒、可自动化的环节」转交给 AI 与工具。
2. **Vibe 在本项目上同时实现了成本下降（53 人时 vs 计划 282 人时）、质量提升（78+5 测试全绿）、可追溯性增强（Git + 变更单双留痕）**。
3. **Vibe 不可外包给人的有且仅有两件事：边界与验收标准由人定、真实验证由人盯**——这是本项目的两条核心教训。

# 3. 逐领域详细对比（九大知识领域）

## 3.1 范围管理

### ① 传统怎么做

范围管理是项目管理的起点，传统上依次经历（教材第 4、5 章）：

1. **需求收集与定义**：通过访谈、问卷、现场观察等方式，把干系人的期望转化为可验证的需求；
2. **需求规格说明书（SRS）**：把需求写成一份干系人可签字确认的正式文档，明确「做什么、不做什么」；
3. **WBS 工作分解**：把范围自顶向下分解为可估算、可分配、可跟踪的工作包，直到可管理的最小单元；
4. **范围说明书与范围基准**：锁定范围边界，作为后续进度、成本、质量计划的共同输入；
5. **需求/范围变更控制**：任何边界变化都要走正式的变更流程（提交 → 评审 → 批准/拒绝 → 记录）。

### ② 为什么要这么做、解决什么问题

范围管理要解决的头号问题是**「范围蔓延」（scope creep）**——需求天然会膨胀、边界会漂移，若没有一份书面共识和变更闸门，进度与成本必然失控。它解决的是：**让所有干系人对「做什么、不做什么」有同一份可签字的共识，并把任何边界变化纳入正式流程，可追溯、可追责。**

### ③ 本项目 Vibe 中的做法

- **AI 辅助起草、人逐条审定**：SRS（22 条 FR / 6 条 NFR / 7 条 AC）由 AI 辅助起草，但**核心业务规则由人逐条确认**——「3 砝码各称 3 次、示值须在 ±0.05% 内」「身份卡不匹配即阻断」这类规则绝不让 AI 凭空定，而是由人对照《电子天平日常校验记录表》敲定。
- **WBS 与范围文档同库版本化**：`WBS工作分解结构.md`、`WBS字典.md`、`项目范围说明书.md` 与代码同在一个 Git 仓库，需求—WBS—代码可回溯。
- **变更留痕**：需求/范围变化走《需求变更记录》CR-001（如 PDF 增加「测量时间与 g/mg 原屏单位」），与代码提交互相印证。

### ④ 传统 vs Vibe 对比表

| 维度 | 传统做法 | 本项目 Vibe 做法 |
|---|---|---|
| 需求收集 | 访谈、问卷为主 | 依据甲方提供的记录表/PPT 摘要，AI 辅助结构化 |
| SRS 编写 | 人逐字撰写 | AI 起草，人逐条审定业务规则 |
| WBS 分解 | 人画树状图 | AI 生成 WBS + 字典，人核对边界 |
| 变更控制 | 纸质/电子变更单 | 变更记录 + Git 提交双留痕 |
| 范围核实 | 评审会议 | 以 7 条 AC 逐条对照测试验证 |

### ⑤ 原问题是否解决/规避

✅ **已解决。** 范围蔓延的根因是「共识没有书面固化」。Vibe 下 AI 起草 + 人审定没有跳过书面化，反而因为文档与代码同库版本化，使「需求—WBS—代码」的可追溯性比纯纸质文档更强。

⚠️ **新风险**：若人把「审定」也交给 AI，边界就会失守——AI 生成的 SRS 会「看起来对、实则空」。本组通过「业务规则人工确认」规避了这一点，但这是一条需要纪律守住的底线。

### ⑥ Vibe 适合哪些情况

- ✅ **适合**：需求边界清晰、可用规则显式表达的小型系统（本组 22 FR / 6 NFR / 7 AC 正好契合）；以可验证验收标准（AC）驱动范围的项目。
- ⚠️ **不适合**：需求高度模糊、需要大量面对面澄清的探索型项目——那类项目 AI 起草的 SRS 容易「空转」，反而不如先做原型。

## 3.2 进度管理

### ① 传统怎么做

进度管理传统上依次经历（教材第 7、13 章）：

1. **活动定义与排序**：把 WBS 工作包拆成活动，确定活动间的依赖关系（FS/SS/FF）；
2. **工期与资源估算**：估算每个活动的工期与所需资源；
3. **排程**：绘制甘特图 + 网络图（AON/AOA），计算关键路径（CPM）与浮动时间；
4. **里程碑设置**：在关键节点设置里程碑，作为高层控制点；
5. **进度跟踪与挣值**：定期采集实际进度，与基准比对，计算偏差（SV/SPI），必要时重排。

### ② 为什么要这么做、解决什么问题

因为活动之间有依赖与资源约束，不排程就无法知道「何时交付、哪里是瓶颈、能否赶上节点」。它解决「进度滞后了才发现、资源排不开」的问题。传统最大痛点在于**计划一旦滞后，重排甘特图、重算关键路径的人工成本很高，导致很多团队干脆放弃滚动更新，计划沦为一次性摆设。**

### ③ 本项目 Vibe 中的做法

- **脚本化甘特图**：`管理文档/进度管理/scripts/render_gantt.py` 把甘特图写成脚本，计划与实际两条曲线随数据更新自动重绘；成品见 `项目进度甘特图_计划与实际_2026-11-04.png`。
- **用可运行测试数量代替主观百分比**：进度跟踪记录里以「78 tests 通过 + 5 OCR」作为进度标尺，而非「感觉完成了 80%」——这是 Vibe 下最有效的进度度量方式。
- **随迭代滚动更新关键路径**：迭代 0 骨架 → 迭代 1 核心闭环 → 迭代 2 完整功能 → 迭代 3 打磨部署，剩余关键路径与工作随每次合并重估。

### ④ 传统 vs Vibe 对比表

| 维度 | 传统做法 | 本项目 Vibe 做法 |
|---|---|---|
| 排程工具 | 甘特图软件（Project/Excel） | Python 脚本生成 PNG，改数据即重绘 |
| 关键路径 | 人工计算/软件计算 | 随迭代滚动重估剩余关键路径 |
| 进度度量 | 「% 完成」主观估计 | 可运行的测试数量（78+5）作客观标尺 |
| 重排成本 | 高（人工重画） | 趋近于零（脚本重跑） |
| 跟踪频率 | 周报/里程碑 | 每次合并后自动更新 |

### ⑤ 原问题是否解决/规避

✅ **已解决。** 传统进度管理的最大成本是「图的重绘」，Vibe 把它脚本化后重绘成本趋近于零，使「计划—实际」始终新鲜；用可运行的测试数量代替主观百分比，也从根本上防住了「进度虚报」。

⚠️ **新风险**：脚本化甘特图仍需要人**及时回填实际数据**——本组成本/工时的回填曾滞后（见 3.3），若数据不新鲜，图再自动化也是「垃圾进垃圾出」。

### ⑥ Vibe 适合哪些情况

- ✅ **适合**：迭代式、有可运行产物或测试可自动验证进度的项目。
- ⚠️ **不适合**：纯瀑布、交付物不可自动验证、需要严格按合同节点对外报量的项目。

## 3.3 成本管理

### ① 传统怎么做

成本管理传统上依次经历（教材第 6 章）：

1. **成本估算**：用类比估算、参数估算、自下而上估算等方法，估算项目总成本（人时/资金）；
2. **预算与成本基准**：把估算分配为按时间分布的预算，形成成本基准（BAC）；
3. **实际成本归集**：持续记录实际发生的成本；
4. **挣值分析（EVM）**：计算 PV/EV/AC，得出 CV/CPI、SV/SPI，判断成本与进度偏差；
5. **成本控制**：对超支采取纠偏措施。

### ② 为什么要这么做、解决什么问题

因为人时与资金都是有限资源，需要提前算清「要花多少」、持续核对「实际花了多少」。它解决「钱/人时超支却后知后觉」的问题——没有成本基准，超支往往到项目末期才暴露，已无纠偏空间。

### ③ 本项目 Vibe 中的做法

- **人时被大幅压缩，这是 Vibecoding 最直观的价值**：成员乙模块计划编码 **62 人时，实际仅 3 人时**；全项目实际投入 **53 人时**（乙 21 = 编码 3 + 测试 2 + 管理 16，甲 18 = 编码 6 + 管理 12，需求分析 8、系统设计 6 甲乙共同）。
- **保留 EVM 骨架**：`成本估算与预算.md` 给出估算 + 预算 + 基线；`实际成本记录.md` 记录实际成本与 CV/CPI。
- **诚实记录一个缺陷**：成员乙在个人报告中明确写道「实际成本记录里除需求阶段外的工时一度长期空着，直到收尾才补」。

### ④ 传统 vs Vibe 对比表

| 维度 | 传统做法 | 本项目 Vibe 做法 |
|---|---|---|
| 估算对象 | 人月/人时为主 | 人时（AI 压缩编码人时后，管理文档人时反而占大头） |
| 主要成本 | 编码 + 测试 + 管理 | 管理文档（28/53 人时）远超编码（9） |
| 归集方式 | 考勤/工时表 | Git 提交 + 事后回填 |
| 控制手段 | EVM（CV/CPI） | EVM 骨架 + 人时对比 |
| 风险 | 超支后知后觉 | **归集滞后**（执行成本被压缩，管理成本未必） |

### ⑤ 原问题是否解决/规避

⚠️ **部分解决。** 「成本超支」本身被显著解决（人时大幅下降），但**「成本归集的及时性」反而退化**——因为人的精力被投向「用 AI 写代码」，人工管理动作（回填工时）被延后。这说明 **Vibe 压缩的是执行成本，未必压缩管理成本**，甚至可能因「写代码变快」而让管理动作更被轻视。

### ⑥ Vibe 适合哪些情况

- ✅ **适合**：人力单价高、重复性编码占比大的项目，Vibe 的性价比最高。
- ⚠️ **不适合**：把「工时」作为合同计价依据、需要精确到人/天的核算型项目——那类需要考勤式归集，Vibe 的松散记录会失真。

## 3.4 质量管理

### ① 传统怎么做

质量管理传统上分两层（教材第 8 章）：

1. **质量计划**：确定质量目标、质量标准与质量活动；
2. **质量保证（QA）**：对过程进行审计，保证「在做对的事」；
3. **质量控制（QC）**：通过评审、测试等手段验证产品，保证「事做对了」；
4. **缺陷跟踪**：对发现的缺陷登记、分级、修复、验证、关闭。

### ② 为什么要这么做、解决什么问题

因为软件缺陷发现越晚，修复成本越高（呈指数增长），必须把质量关卡前置。它解决「缺陷晚发现、返工成本高」的问题。传统最大痛点是**测试常被压缩到末期，沦为「事后补」**——因为手工写测试成本高，人天然倾向于先写实现。

### ③ 本项目 Vibe 中的做法

- **TDD 纪律由技能固化**：加载 `tdd` 技能，把「red（写失败测试）→ green（最小实现）」循环变成每次实现的固定动作，而非靠自觉；
- **代码审查由技能常态化**：切片完成后跑 `code-review`，产出 CR-YI-01（连续写多表无事务）、CR-YI-02（页面所选天平与视频识别天平不一致）、CR-YI-03（示值不足 9 次仍落库）三个高严重度发现并在交付前修复；
- **测试数量作为硬基线**：全项目 **78 Java + 5 OCR 全绿**，作为「不能破」的交付红线；
- **缺陷闭环**：DEF-001（示值 OCR）、DEF-002（覆盖率）走「登记 → 修复 → 验证 → 关闭」；《功能完善性检查流程》把验收前检查项做成 7 大类逐项可勾选清单。

### ④ 传统 vs Vibe 对比表

| 维度 | 传统做法 | 本项目 Vibe 做法 |
|---|---|---|
| 测试编写时机 | 常后补 | TDD 前置（技能固化红绿循环） |
| 测试编写成本 | 高（人手写） | 低（AI 承担机械部分） |
| 代码审查 | 阶段末评审 | 切片完成即审（code-review 技能） |
| 缺陷跟踪 | 缺陷单 | DEF-001/002 + CR-YI-01/02/03 双轨 |
| 质量度量 | 缺陷数 | 78+5 测试通过率 + 缺陷闭环 |

### ⑤ 原问题是否解决/规避

✅ **已解决，且是 Vibe 最亮眼的一处。** 传统「测试后补」的根因是测试编写成本高、人懒于先写；Vibe 下由 AI 承担红绿循环的机械部分，测试编写成本骤降，于是「测试先行」从口号变成常态。代码审查也因 AI 能快速跑出带严重度、带回归的发现清单而常态化。

⚠️ **新风险**：AI 生成的测试可能「只测实现、不测意图」，需要人确认测试断言真的对上了业务规则（本组由人确认「±0.05% 限度、逐示值判定、一票否决」等断言）。

### ⑥ Vibe 适合哪些情况

- ✅ **适合**：凡有自动化测试护栏、可回归验证的系统都适合（尤其纯函数逻辑，如本组判定引擎 JudgeService）。
- ⚠️ **不适合**：无法自动化验证的领域（UI 审美、硬件适配、安全关键系统的形式化验证）。

## 3.5 配置管理

> 本节为标准领域对比；配置管理被《项目管理要求》单独点名，完整专题见第 4 章。

### ① 传统怎么做

配置管理（CM）传统上有四大职能（教材第 9 章）：**配置项标识、基线管理、变更控制（SCCB 变更控制委员会）、配置状态报告与审计**。

### ② 为什么要这么做、解决什么问题

因为多人协作下变更会互相覆盖、版本会混乱，需要回答「谁改了、改了什么、为什么改、能不能回退」四大问题。它解决「改了什么不知道、回退不了、账实不符」的问题。传统痛点是**过程重、文档多，小项目往往流于形式、与真实开发脱节**。

### ③ 本项目 Vibe 中的做法

- **Git 分支模型承载版本控制**：`main` 主分支 + `feature/jia-modules`（甲）+ `feature/yi-modules`（乙），接口与表结构先行定稿；
- **5 个基线**：B_RM / B_DES / B_CODE / B_TEST / B_REL（`配置库/基线/`）；
- **6 份变更单 CM-001~006**，每份走「请求 → 登记 → 波及分析 → SCCB 决策 → 实施 → 验证关闭」闭环；
- **配置状态报告 + 审计记录**；**环境基线**固定 JDK/Maven/MySQL/ffmpeg/RapidOCR 版本与 DEV/TEST/UAT 三环境矩阵。

### ④ 传统 vs Vibe 对比表

| 维度 | 传统做法 | 本项目 Vibe 做法 |
|---|---|---|
| 版本控制 | 签入/签出、人工登记 | Git 分支 + 提交历史内建 |
| 基线 | 人工冻结版本 | 配置库 5 基线清单 + Git tag/提交 |
| 变更控制 | 纸质变更单 + SCCB 会议 | 变更单 CM-001~006 + Git 提交双留痕 |
| 状态/审计 | 定期审计 | 配置状态报告 + 审计记录 |
| 环境 | 人工记录 | 项目配置环境基线 + 自检脚本 |

### ⑤ 原问题是否解决/规避

✅ **已解决，且比传统更「账实相符」。** 传统 CM 最大的失败模式是「文档一套、代码一套」；Vibe 下文档与代码同源（同仓库、同提交），变更单可与 Git 提交互相印证。剩余不足是 **SCCB 决策留痕仍需人自觉补齐**——AI 不会自动提醒「该开变更单了」。

### ⑥ Vibe 适合哪些情况

- ✅ **适合**：交付物以代码/文档为主、可全部纳入 Git 的软件项目；小团队敏捷迭代。
- ⚠️ **不适合**：有实物/签字版交付物、法定签批链或监管要求纸质配置库审计的项目。

## 3.6 团队（资源）管理

### ① 传统怎么做

团队/资源管理传统上依次经历（教材第 10 章）：

1. **组织结构设计**：选择职能型/项目型/矩阵型等组织形态；
2. **角色与职责定义**：明确每个角色的职责边界；
3. **RAM/OBS 责任矩阵**：把工作包与责任人对应起来，消除职责空白与重叠；
4. **团队建设与激励**：组建团队、建立协作规范、处理冲突。

### ② 为什么要这么做、解决什么问题

因为项目成果靠人完成，职责不清会互相推诿、人手不足会延误交付。它解决「谁负责什么、职责交叉冲突、人力不够」的问题。

### ③ 本项目 Vibe 中的做法

- **2 人双项目经理制**：成员甲、乙共同担任 PM，各兼开发/测试/配置/质量多重角色；
- **AI 放大个人产能**：让 2 人承担传统上需要更多人的编码量（53 人时完成全部编码 + 测试 + 管理文档）；
- **接口先行避免冲突**：甲负责识别/判定/查询/审计，乙负责落库/复核/账号/主数据，路径与表结构在编码前定稿，乙「不碰甲已实现的代码」；
- **交接文档固化边界**：《甲模块交付说明》《乙实现进度与交接》《给乙的继续开发清单》把接口共识写成可续接的书面约定。

### ④ 传统 vs Vibe 对比表

| 维度 | 传统做法 | 本项目 Vibe 做法 |
|---|---|---|
| 组织结构 | 职能/项目/矩阵 | 项目型为主 + 轻量矩阵（2 人双 PM） |
| 职责分工 | RAM/OBS | RAM + 接口先行 + feature 分支 |
| 冲突预防 | 团队建设、会议协调 | 接口定稿 + 交接文档 + 不碰对方代码 |
| 人力 | 按 WBS 配人 | AI 放大个人产能，2 人即可 |
| 激励 | 物质/精神激励 | 课程项目，靠共同目标与双 PM 对等责任 |

### ⑤ 原问题是否解决/规避

✅ **已解决。** 「人手不够」被 AI 产能补足；「职责冲突」靠接口先行 + feature 分支 + 交接文档规避。交接文档本质是「把接口共识写成可续接的书面约定」，比口头约定可靠得多。

⚠️ **新风险**：**多人 + 多 AI 并发写码时，接口漂移与合并冲突会指数级放大**——本组的「接口先行」经验只在小团队下成立，规模扩大后需要更重的治理（契约测试、CI 门禁）。

### ⑥ Vibe 适合哪些情况

- ✅ **适合**：小团队（1~3 人）、成员可全栈或边界清晰的项目，Vibe 的杠杆最大。
- ⚠️ **不适合**：大型团队多 AI 并发开发（需要契约测试与 CI 门禁支撑）、需要强领导力协调的政治性项目。

## 3.7 风险管理

### ① 传统怎么做

风险管理传统上依次经历（教材第 11 章）：

1. **风险识别**：识别可能影响项目的风险事件；
2. **定性/定量分析**：评估风险的概率与影响，排序；
3. **Top5 重点管理**：聚焦最重要的少数风险；
4. **应对计划**：规避 / 转移 / 缓解 / 接受；
5. **持续跟踪**：定期重评风险，更新登记册。

### ② 为什么要这么做、解决什么问题

因为项目充满不确定性，被动应对会措手不及。它解决「风险失控、事发才处理」的问题。

### ③ 本项目 Vibe 中的做法

- **完整风险文档链**：`风险计划（风险清单与Top5跟踪）`（基础清单 + 矩阵）→ `执行期风险登记册与Top5应对计划（2026-11-02）`（执行期专项 Top5）→ `风险跟踪记录`（清单 15 项、跟踪 12 项）；
- **最有价值的一条教训**：示值数字 OCR（DEF-001）是本项目唯一一度未达成的需求，直到 11-02 才接入本地 RapidOCR 关闭。成员乙反思「不确定性高的技术点要尽早做技术尖峰，而不是放到验收前」。

### ④ 传统 vs Vibe 对比表

| 维度 | 传统做法 | 本项目 Vibe 做法 |
|---|---|---|
| 识别 | 头脑风暴/专家判断 | AI 辅助列风险清单，人补充业务风险 |
| 排序 | 概率×影响矩阵 | 基础矩阵 + 执行期 Top5 双轨 |
| 应对 | 规避/转移/缓解/接受 | 技术风险靠「技术尖峰」提前验证 |
| 跟踪 | 定期会议重评 | R1~R15 清单 + 12 项跟踪记录随合并更新 |
| 新风险形态 | 外部/进度/成本风险为主 | **「看起来做完了」≠「验证通过了」** |

### ⑤ 原问题是否解决/规避

⚠️ **部分解决。** 技术风险最终都被闭环（风险清单 R1~R15、跟踪 12 项、DEF-001 关闭），但**发现时机偏晚**。根因很微妙：Vibe 让「常规开发」变得极快，反而容易让人**低估「需要真实验证的未知点」**——AI 能飞快写出 OCR 调用代码，但「实拍视频到底识别准不准」这类不确定性，AI 替不了真实验证。这是 Vibe 下风险管理要格外警惕的新形态风险。

### ⑥ Vibe 适合哪些情况

- ✅ **适合**：不确定性主要集中在「代码可实现性」的项目，Vibe 能快速试错。
- ⚠️ **不适合**：不确定性在「物理世界/外部依赖/合规」的项目——那类风险 Vibe 无法加速验证，反而可能放大「假完成」的错觉。

## 3.8 沟通管理

### ① 传统怎么做

沟通管理传统上依次经历（教材第 14 章）：

1. **沟通计划**：确定谁需要什么信息、何时、以何种方式；
2. **干系人分析**：识别所有干系人及其信息需求；
3. **会议机制**：通过例会、评审会等同步信息；
4. **会议纪要**：把决策与结论书面留痕。

### ② 为什么要这么做、解决什么问题

因为信息不对称会导致决策错位、口径不一，需要同步与留痕。它解决「信息不对称、决策没留痕」的问题。

### ③ 本项目 Vibe 中的做法

- **以 Git 提交 / 结对互审 / 交接文档替代正式会议**：本组没有召开正式会议，`沟通计划（含会议记录）` 里明确写了这一机制；
- **交接文档承载关键沟通**：《甲模块交付说明》《乙实现进度与交接》《给乙的继续开发清单》把「谁做了什么、边界在哪、下一步是什么」写成可异步读取的文档；
- **Git 提交历史即沟通记录**：每次提交的「模块: 摘要」格式（如「修复：…」「文档：…」）本身就是一种规范化沟通。

### ④ 传统 vs Vibe 对比表

| 维度 | 传统做法 | 本项目 Vibe 做法 |
|---|---|---|
| 同步方式 | 例会/评审会 | Git 提交 + 结对互审 + 交接文档 |
| 留痕方式 | 会议纪要 | 提交历史 + 文档（天然可回溯） |
| 时效性 | 实时同步 | 异步为主（2 人团队补足） |
| 干系人 | 甲方 + 团队 | 甲方以评审/验收参与 |

### ⑤ 原问题是否解决/规避

✅ **已解决。** 传统沟通要解决的本质是「让信息可达、可查」。Git 提交 + 交接文档天然**留痕、可回溯、可异步**，比会议更防「口说无凭」。代价是缺少同步的及时反馈——但在 2 人团队里，结对互审补足了这一点。

### ⑥ Vibe 适合哪些情况

- ✅ **适合**：小团队、异步协作、成员自律且有文字化习惯的项目。
- ⚠️ **不适合**：需要高频同步、多干系人、强情感协调（如对外谈判）的项目——那类仍需要会议这类同步媒介。

## 3.9 合同（采购）管理

### ① 传统怎么做

合同/采购管理传统上依次经历（教材第 12 章）：

1. **自制/外购分析**：决定哪些自己做、哪些外包；
2. **招投标**：选择供应商；
3. **合同签订与管理**：明确范围、价格、验收与违约责任；
4. **履约验收**：监督供应商履约并验收。

### ② 为什么要这么做、解决什么问题

因为需要决定哪些自己做、哪些外包，并管控供应商履约。它解决「该不该外包、如何管控供应商」的问题。

### ③ 本项目 Vibe 中的做法

- **自制/采购分析后结论为「无外包」**：本组做了自制/外购分析，结论是全部自制，用《合同管理说明（无外包）》一份文档闭环；
- **这是一个被 Vibe 从根本上消解的管理决策**：AI 大幅降低了自制的边际成本后，「自制」在更多场景成为更优解，采购风险直接被规避。

### ④ 传统 vs Vibe 对比表

| 维度 | 传统做法 | 本项目 Vibe 做法 |
|---|---|---|
| 自制/外购 | 权衡成本/能力/时间 | AI 压低自制成本 → 倾向自制 |
| 招投标 | 需要时执行 | 无需（无外包） |
| 合同管理 | 签合同、管履约 | 一份无外包说明闭环 |
| 风险 | 供应商履约不确定性 | 被规避（无供应商） |

### ⑤ 原问题是否解决/规避

✅ **已解决（且是被 Vibe 从根本上消解的）。** 合同管理的核心风险是「供应商能力与履约不确定性」。Vibe 降低自制成本门槛后，「自制」在更多场景成为更优解，采购风险直接被规避——**这是 Vibe 对采购管理的一个结构性影响：当 AI 让自制的性价比普遍上升，可外包的边界会收缩。**

### ⑥ Vibe 适合哪些情况

- ✅ **适合**：自制成本可被 Vibe 显著压低、且无合规必须外购的项目。
- ⚠️ **不适合**：依法规/资质必须外包的场景（Vibe 再快也替代不了资质门槛）。

# 4. 配置管理专题：传统做法 vs Vibe 做法（完整版）

《项目管理要求》把配置管理从九大领域中单列出来，说明它是 Vibecoding 实验中**最需要讲清楚的一个领域**——因为传统配置管理与 Vibe 的代码工作方式重叠最多，也最容易混淆。

## 4.1 为什么配置管理被单独点名

配置管理（CM）是连接「开发活动」与「管理活动」的枢纽：它既要管代码（技术），又要管变更决策（管理）。在 Vibecoding 下，代码的版本控制被 Git 天然内建了，**传统 CM 里最重的「版本登记」工作量消失了**，但「决策留痕」仍要人做。这个「一半被工具替代、一半必须人做」的特殊性，正是它被单独拿出来比较的原因。

## 4.2 传统配置管理四大职能详解

| 职能 | 具体做法 | 解决什么问题 |
|---|---|---|
| 配置项标识 | 给每个受控对象（文档/代码/数据）编唯一的配置项号，建立配置项清单 | 「哪些东西要受控」——否则改了什么都不知道 |
| 基线管理 | 在关键节点冻结一组配置项，形成可回溯的确定状态 | 「某个时点系统的确定状态」——否则无法回退、无法对照「交付版」 |
| 变更控制 | 变更请求 → 评审（SCCB）→ 批准/拒绝 → 实施 → 验证，全程留痕 | 「改之前要审批、改之后要留痕」——否则变更失控、责任不清 |
| 状态报告与审计 | 定期报告配置项当前状态，审计是否与计划一致 | 「当前在哪个版本、是否账实相符」——否则账实不符 |

传统痛点是**过程重、人工多**，在小型/敏捷项目里常退化成「事后补文档」，与真实开发脱节。

## 4.3 本项目 Vibe 中的配置管理落地

| 传统职能 | 本项目 Vibe 落地 | 载体 |
|---|---|---|
| 配置项标识 | 配置管理计划（含配置项清单）+ 配置库索引 | `管理文档/配置管理/配置管理计划（含配置项清单）.md`、`配置库/配置库索引` |
| 基线管理 | 5 个基线 B_RM / B_DES / B_CODE / B_TEST / B_REL | `配置库/基线/`（如 `B_REL_发布基线.md`） |
| 变更控制 | 变更单 CM-001~006，每份走「请求→登记→波及分析→SCCB 决策→实施→验证关闭」 | `变更单与状态报告.md` |
| 状态/审计 | 配置状态报告 + 审计记录 | 同上 |
| 版本控制 | **Git 分支模型 + 提交历史**（main / feature-jia / feature-yi） | Git 仓库本身 |
| 环境基线 | JDK/Maven/MySQL/ffmpeg/RapidOCR 版本 + DEV/TEST/UAT 矩阵 | `项目配置环境基线.md` |

## 4.4 关键区别：版本控制从「人肉登记」变成「工具内建」

传统配置管理里，「版本控制」需要靠人把每个版本登记到配置库、靠签入签出（check-in/check-out）防覆盖；而在 Vibe 下，**代码的版本、变更、回退、作者、时间戳天然由 Git 承载，人肉登记这一步被工具替代了**。人工要补的只剩 Git 管不到的「决策层」：为什么批准这个变更（SCCB 决策）、波及了哪些（波及分析）、当前交付版是哪一版（基线）。

## 4.5 原来的问题是否解决/规避

✅ **核心问题解决，且比传统更「账实相符」。** 传统 CM 最大的失败模式是「文档一套、代码一套」；Vibe 下文档与代码同源（同仓库、同提交），变更单可与 Git 提交互相印证，可追溯性反而更强。

⚠️ **剩余不足**：**SCCB 决策留痕仍需人自觉补齐**——AI 不会自动提醒你「该开变更单了」。这条仍依赖流程纪律，是 Vibe 无法替代的「管理判断」。

## 4.6 Vibe 的配置管理适合哪些情况

- ✅ **适合**：交付物以代码/文档为主、可全部纳入 Git 的软件项目；小团队敏捷迭代；需要强可追溯但人手有限。
- ⚠️ **不适合**：有实物/签字版交付物、需要法定签批链、或监管要求纸质配置库审计的项目——Git 的电子留痕在这些场景下法律效力不足。

# 5. 总结论：Vibecoding 项目管理的全貌

## 5.1 一个统一判断

Vibe 没有「取消」传统项目管理的任何一个知识领域，而是**改变了每个领域里「哪些工作由人做、哪些由工具/AI 做」的分工**：

| 传统里昂贵/易偷懒的环节 | Vibe 下的替代 |
|---|---|
| 写测试（人嫌慢） | AI 承担红绿循环，测试先行常态化 |
| 画甘特图/重排计划 | 脚本化生成，重绘成本趋近零 |
| 代码审查 | `code-review` 技能快速产出带严重度的发现清单 |
| 版本登记/签入签出 | Git 内建，人只补决策留痕 |
| 大量重复编码 | AI 执行，人力转向边界与验收 |

## 5.2 两个不可外包给 AI 的「人」的职责

Vibe 下真正被**强化**而非弱化的人工作有两件，也是本项目最大的两条教训：

1. **边界与验收标准必须人来定**——需求业务规则（±0.05% 限度、归组规则、身份卡不匹配阻断）是人工逐条确认的，AI 只负责「照着写」。
2. **真实验证必须人来盯**——「AI 写完了」不等于「真跑通了」。示值 OCR（DEF-001）的教训说明，不确定性高的技术点要尽早做技术尖峰，不能因为 Vibe 让常规开发变快，就误以为所有风险都被加速消解了。

## 5.3 三类适合 / 三类不适合（总结）

**适合 Vibe 的情况**：

1. 小团队、边界清晰、以代码为主要交付物的项目——Vibe 在此类项目上同时压低成本、提升质量、强化可追溯性；
2. 可自动化测试/验证、有明确验收标准的项目——「可运行测试数」成为可靠的进度与质量标尺；
3. 重复性编码占比高、人力单价高的项目——AI 的杠杆最大。

**不适合 Vibe 的情况**：

1. 大团队多人多 AI 并发——接口漂移与合并冲突失控，需要契约测试与 CI 门禁兜底；
2. 强监管/纸质签批/实物交付——电子留痕法律效力不足；
3. 物理世界不确定性为主（硬件/合规/外部依赖）或需求高度模糊需大量面对面澄清——AI 无法加速「真实验证」。

## 5.4 与传统项目管理的完整流程对照表

| 知识领域 | 传统核心活动 | Vibe 下「人做」 | Vibe 下「AI/工具做」 |
|---|---|---|---|
| 范围 | 需求/WBS/变更控制 | 定业务规则、审定边界、批准变更 | 起草 SRS/WBS、整理变更 |
| 进度 | 排程/关键路径/跟踪 | 定里程碑、回填实际 | 生成甘特图、算关键路径 |
| 成本 | 估算/归集/EVM | 定口径、按时回填 | 估算辅助、人时对比 |
| 质量 | 计划/QA/QC/缺陷 | 定验收标准、审断言 | 写测试、跑审查、跑回归 |
| 配置 | 标识/基线/变更/审计 | SCCB 决策、补变更单 | Git 版本、基线清单、状态报告 |
| 团队 | 组织/RAM/建设 | 定接口、定边界 | 放大产能、生成交接文档 |
| 风险 | 识别/排序/应对/跟踪 | 判断真实验证点、做技术尖峰 | 列风险清单、跟踪记录 |
| 沟通 | 计划/会议/纪要 | 结对互审、决策留痕 | 交接文档、提交历史 |
| 合同 | 自制外购/招投标/合同 | 做自制/外购决策 | 辅助分析、文档生成 |
