# 软件项目团队计划（组织与职责分工）

> 项目名称：天平校验视频分析系统　|　组别：第 1 组　|　编制日期：2026-10-01
> 依据：[[../../需求规格说明书-SRS]]、[[../范围管理/WBS工作分解结构]]
> 对应教材：[[第10章 软件项目团队计划]]

## 0. 编制说明

- **核心理念**：影响进度、成本、质量的因素是「人、过程、技术」，其中**人是第一位**（教材 §10.1）。
- **团队规模**：本项目为 **2 人组**（第 1 组）。
- **关键约束**：**两名成员都参与代码开发**——1 人兼项目经理，1 人兼测试/配置管理，但**系统设计与编码由两人共同承担**，编码模块按工作量对半划分（见 §2.4）。
- **内容**：组织结构选型 → 人员职责（RAM/OBS/模块分工）→ 干系人计划 → 敏捷团队工作方式。

---

## 1. 团队组织结构

### 1.1 结构选型

本项目为**课程实训小项目**，团队仅 2 人、单目标、周期短，采用**项目型（单目标垂直组织）**为主、辅以**轻量矩阵**（甲方人员参与评审）的混合结构：

| 结构 | 适用性 |
|---|---|
| 项目型 | ✅ 主结构：2 人核心组，PM 直接负责、沟通简洁、决策快 |
| 轻量矩阵 | ✅ 辅：甲方（检验科室）以评审/业务专家身份参与需求与验收 |
| 职能型 | ❌ 不适用（无多个职能部门） |

### 1.2 组织结构图

```
              ┌──────────────────────────┐
              │    甲方（检验科室）        │  ← 业务专家 / 验收
              └────────────┬─────────────┘
                           │ 评审、需求确认
              ┌────────────┴─────────────┐
              │  成员甲：项目经理 兼 开发   │  ← 计划/沟通/风险 + 编码
              └────────────┬─────────────┘
                           │ 结对协作、并行开发
              ┌────────────┴─────────────┐
              │  成员乙：开发 兼 测试/配置  │  ← 编码 + 测试/配置管理
              └──────────────────────────┘
```

> **两名成员均为开发人员**：系统设计（1.2）与编码实现（1.3）由两人共同完成；管理职责由甲（PM）、测试/配置职责由乙分担。

## 2. 人员职责计划

### 2.1 角色与职责（文本描述）

| 角色 | 人员 | 主要职责 |
|---|---|---|
| **项目经理 兼 开发** | 成员甲 | 制定计划（范围/进度/成本/质量/风险/配置）、主持评审、对外沟通、风险管理、进度跟踪、SCCB 主席；**同时承担一半编码模块** |
| **开发 兼 测试/配置管理** | 成员乙 | **承担一半编码模块**、单元/集成测试、部署、文档编写；兼任配置管理员（CMO） |
| **甲方（业务专家）** | 检验科室 | 提供业务规则、现场配合、需求确认、验收评审 |

> 两人职责差异仅在**管理/测试的兼任部分**；**系统设计与编码开发两人对等参与**。

### 2.2 责任分配矩阵（RAM）

符号（教材表 10-1）：**A=批准（Approve）、R=评审（Reviews）、P=参加（Participant）、C=建立（Creator）**。确保**每项任务只有一个人负责（C）**。

| WBS 工作包 | 成员甲（PM 兼开发） | 成员乙（开发兼测试） | 甲方 |
|---|---|---|---|
| 1.1 需求分析 | C | P | P |
| 1.2 系统设计 | C | C | R |
| 1.3 编码实现 | C | C | — |
| 1.4 测试 | A | C | P |
| 1.5 部署与交付 | A, P | C | R |
| 1.6 项目管理 | C | P | — |
| 需求评审 | C | P | A |
| 验收测试 | P | C | A |

> 设计（1.2）与编码（1.3）两阶段**两人均为 C（共同负责）**，具体到模块时再按 §2.4 唯一归属，避免职权不清。

### 2.3 组织分解结构（OBS）

与 WBS 对应（教材 §10.2.2），显示「哪个角色负责哪项工作」：

| OBS 单元 | 负责的 WBS 阶段 |
|---|---|
| 项目管理组（成员甲） | 1.1 需求评审、1.6 项目管理 |
| **开发组（成员甲 + 成员乙）** | **1.2 设计、1.3 编码** |
| 测试组（成员乙） | 1.4 测试 |
| 交付组（甲 + 乙） | 1.5 部署与交付 |
| 甲方业务组 | 需求提供、验收 |

### 2.4 编码模块分工（两人对半）

8 个编码模块按工作量（合计 124 人时）**对半划分**，各约 **62 人时**：

| WBS   | 编码模块              | 负责（C） | 协作（P） | 工时     |
| ----- | ----------------- | ----- | ----- | ------ |
| 1.3.2 | 视频导入与视觉识别         | **甲** | 乙     | 24     |
| 1.3.5 | 校验判定引擎            | **甲** | 乙     | 12     |
| 1.3.6 | 查询 / 曲线图 / PDF 导出 | **甲** | 乙     | 16     |
| 1.3.8 | 留痕与审计日志           | **甲** | 乙     | 10     |
|       | **甲小计**           |       |       | **62** |
| 1.3.1 | 用户登录与权限管理         | **乙** | 甲     | 16     |
| 1.3.3 | 校验记录管理            | **乙** | 甲     | 20     |
| 1.3.4 | 复核确认              | **乙** | 甲     | 12     |
| 1.3.7 | 天平 / 砝码与模板维护      | **乙** | 甲     | 14     |
|       | **乙小计**           |       |       | **62** |

> 分工原则：**核心难点模块（1.3.2 视频识别）由兼 PM 的甲承担，与判定引擎（1.3.5）协同**；两人模块边界清晰、接口先定、**结对互审**（见 §4.2），保证「两个组员都参与代码开发」。

## 3. 项目干系人计划

### 3.1 干系人识别与登记

| 姓名/单位 | 部门 | 项目角色 | 主要需求 | 主要期望 | 目前状态 |
|---|---|---|---|---|---|
| 检验科室 | 甲方 | 客户/业务专家 | 校验记录电子化、可回溯 | 减轻工作、判定准确 | 支持 |
| 甲方决策者 | 甲方 | 出资/决策 | 项目按期交付、可评分 | 系统可用、满足需求 | 支持 |
| 成员甲 | 乙方 | 项目经理兼开发 | 计划可控、按期交付 | 高评分 | 首倡者 |
| 成员乙 | 乙方 | 开发兼测试 | 任务清晰、协作顺畅 | 完成交付 | 支持 |
| 指导教师 | 校方 | 评审/监理 | 文档规范、过程完整 | 交付物齐全 | 中立偏支持 |

### 3.2 干系人分析坐标格（重要性 × 支持度）

纵轴=重要性（高/中/低），横轴=支持度（支持/中立/不支持）：

| 重要性＼支持度 | 支持 | 中立 | 不支持 |
|---|---|---|---|
| **高** | A1：甲方业务/决策者、成员甲、成员乙 | A2：— | A3：— |
| **中** | B1：指导教师 | B2：— | B3：— |
| **低** | C1：— | C2：— | C3：— |

- **策略**（教材 §10.3.3）：借助首倡者与内部支持者，争取中坚力量，至少让不支持者不反对；对重要干系人（A1 区）的需求详析并动态调整。
- 本项目干系人整体支持度高，重点在**保持甲方持续参与**（降低需求变更风险 R4/R6）。

## 4. 敏捷团队工作方式

### 4.1 自组织与仆人式领导

- **自组织团队**：2 人组自决谁执行范围内工作，跨职能、集体负责、共同拥有完成工作所需技能（教材 §10.5.2）。
- **仆人式领导**：PM 通过对团队服务来领导、为团队赋权，关注成员需要与发展（教材 §10.5.3）。

### 4.2 团队协作实践

| 实践 | 落地 |
|---|---|
| **结对编程** | 两人互为对方模块的 P，关键模块（1.3.2、1.3.5）结对互审 |
| 接口先行 | 编码前先定两人模块间的接口，减少集成冲突 |
| 每日同步 | 每日站立会议（15 分钟），更新任务板与燃尽图 |
| 迭代评审 | 每里程碑向甲方展示增量、收集反馈 |
| 透明化 | Git 仓库 + 任务板公开进度 |

### 4.3 沟通渠道

- 沟通渠道数 N(N–1)/2：核心组 2 人 → **1 条**；纳入甲方（3 人）→ **3 条**；纳入指导教师（4 人）→ **6 条**。
- 保持渠道**畅通且单一**，客户接口唯一（由 PM 对接甲方）（教材 §10.4.2）。
