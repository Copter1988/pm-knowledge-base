# 第4章 软件项目范围计划——需求管理

> 本章讲「范围从需求开始」：项目范围管理的起点是需求，核心是**需求管理五过程**（获取→分析→规约编写→验证→变更），以及传统（数据流/UML）与敏捷（影响地图、需求池、用户故事等）两大类需求分析方法。

## 核心概念速览

| 概念 | 一句话 |
| --- | --- |
| 项目范围管理 | 对项目包括什么与不包括什么的定义与控制过程 |
| 软件需求 | 用户对软件功能和性能的要求（想做什么、做成什么样、达到什么性能） |
| 软件需求规约（SRS） | 充分描述软件系统外部行为的正式文档，是软件产品范围的书面界定 |
| 需求验证 | 验证需求的正确性、一致性、完整性、可行性、必要性、可检验性、可跟踪性 |
| 需求基线 | 需求变更的依据，每次变更评审后重新确定 |
| 数据流图（DFD） | 用过程、实体、数据流、数据存储四种基本元素描述系统逻辑模型 |
| 用例（use case） | 系统向用户提供一个有价值结果的某项功能，捕捉功能性需求 |
| 用户故事 | 从用户角度描述渴望功能的三要素（角色、活动、商业价值） |

---

## 4.1 软件项目范围的定义

- **项目范围管理**是对项目包括什么与不包括什么的定义与控制过程，是制订软件计划的依据，包括对功能、性能、接口和可靠性的确定。
- 定义项目范围是**项目实施的依据和变更的输入**；项目目标必须**可实现、可度量**，这一步管理不好会导致项目最终失败。
- **项目范围** = 开发项目产品所包括的工作 + 产生这些产品所用的过程。项目人员既要对「产生什么样的产品」达成共识，也要对「如何生产这些产品」达成共识。
- 项目的规模、复杂度、重要性决定范围计划的工作量；软件项目的范围**首先从需求开始**。

## 4.2 需求管理过程

需求是软件开发过程的基础、软件项目建设的基石。关键数据（说明需求阶段的重要性）：

- 软件项目中 **40%～60%** 的问题在需求分析阶段埋下隐患。
- 返工开销占开发总费用的 **40%**，其中 **70%～80%** 由需求错误导致。
- 失败的软件项目中 **80%** 是需求分析不明确造成的。

**软件需求的三个层次**：

| 层次 | 英文 | 说明 | 由谁确定 |
| --- | --- | --- | --- |
| 业务需求 | business requirement | 组织机构/客户对系统高层次目标要求 | 管理人员或市场分析人员 |
| 用户需求 | user requirement | 用户通过软件必须完成的任务 | 用户协助提供（用例/场景） |
| 功能需求 | functional requirement | 开发人员必须实现的软件功能 | 开发方（满足业务需求） |

三者关系：用户需求必须与业务需求一致 → 从中总结出功能需求 → 形成**软件需求规约（SRS）**。SRS 还包括系统需求、非功能性需求、质量属性、约束和假设。

### 4.2.1 需求获取

- 软件需求具有**模糊性、不确定性、变化性、主观性**四个特点，与传统行业相比更难以获取。
- **需求获取** = 通过与用户交流、对现有系统的观察及对任务的分析，开发、捕获和修订用户的需求。
- 主要任务是**访谈式沟通**（用户方领导层、业务层），宏观把握需求方向和趋势，了解组织架构、业务流程、软硬件环境、现有系统等，建立良好沟通渠道。

**需求获取的四项活动**：
1. 了解所有用户类型及潜在类型，确定系统整体目标和工作范围。
2. 需求调查（访谈、调研）——方式含面对面沟通（Q&A 列表）、电视电话会议访谈、需求专题讨论会（头脑风暴）、自行搜集需求；每次交流必须有记录。
3. 对收集到的需求做进一步分析和整理（追问「为什么」，把「如何实现」转为「实现什么」，挖掘隐含需求）。
4. 将调研结果呈交双方确认（标识未确定需求项、符合整体目标、保证一致性、解决冲突）。

**获取需求的注意问题**：识别真正的客户（客户并非平等，需排序）；正确理解客户需求（有选择地过滤、理解隐含「需要」）；具备忍耐力和清晰思维；说服和教育客户（正视变更负担）；建立需求分析小组、实地考察、用图形表格工具。

### 4.2.2 需求分析

- 需求分析又称**需求建模**，为最终用户看到的系统建立概念模型，任务是从当前系统的逻辑模型导出目标系统的逻辑模型，解决「做什么」。
- 关键观点：
  - 需求是**与技术无关（technology independent）**的，需求阶段讨论技术没有意义。
  - 应有经验的系统分析员负责（忌新手/程序员），并让**用户参与**（选精通业务或计算机技术的用户，跨行业产品选有代表性的用户）。
  - 需求分析通常与需求获取**并行**，区别在于用**模型**来描述需求，提供可视化沟通桥梁。

**需求分析的活动**：以图形描述系统整体结构（边界与接口）；通过原型/页面流提供可视化界面让用户评价；以模型描述功能项、数据实体、外部实体、实体间关系与状态转换。

**基本策略**：头脑风暴、专家评审、焦点会议组；必要时提供原型系统和业务流程报告、数据项表；用户审查后签字确认。

### 4.2.3 需求规约编写

- **需求规约（SRS）**的编制是为了使用户和开发者双方对软件初始规定有共同理解，是开发工作的基础；**需求分析完成的标志是提交一份完整的 SRS**。
- 需求规约是**软件产品范围正式且书面的界定**，是必需的**基础性文档**，相当于软件开发的「图纸」；格式无统一标准。
- **需求规约 + 工作陈述（SOW）** 是很关键的两个文档，SRS 编写可参照甲方 SOW 信息，为客户和开发者之间建立约定。
- 危险思想：开发方与客户只在大轮廓上达成一致、细节以后再补——许多项目失败正因需求阶段描述不够细致。正确做法是全面细致讨论应用背景、功能、性能、界面、接口、评价标准，并建立直接联系渠道以尽早沟通需求变动。

### 4.2.4 需求验证

以需求规约为输入，通过符号执行、模拟或快速原型等途径，分析需求规约的**正确性和可行性**。验证的方面如下：

| 方面 | 要点 |
| --- | --- |
| 正确性 | 开发方和用户都复查；以需求来源为参考，抵触系统需求即不正确；必须用户代表参与 |
| 一致性 | 与其他软件需求或高层（系统/业务）需求不矛盾、无冲突、无二义性 |
| 完整性 | 不遗漏任何必要信息；用 **TBD（待确定）** 标识缺漏，开发前解决所有 TBD |
| 可行性 | 在已知系统/环境限制内可实施；收集需求时始终有软件工程小组成员检查技术可行性 |
| 必要性 | 每项需求都是客户真正需要的，都能回溯至某客户输入（「根源」） |
| 可检验性 | 能写出测试用例验证；模糊需求（如「界面友好」）是「扯皮」根源 |
| 可跟踪性 | 每项需求与根源、设计元素、源码、测试用例建立链接（结构化、细粒度编写） |
| 最后的签字 | 评审通过的需求规约由用户方签字，作为项目合同附件，对双方有约束力 |

**前向追踪 vs 后向追踪**：前向追踪看需求是否在后续阶段（设计、编码）体现，保证软件满足需求；后向追踪看后期工作成果满足何种需求，在变更、回归测试时更有用。项目过程中可用**需求跟踪矩阵**管理需求。

### 4.2.5 需求变更

- 需求变更（像「无底洞」）是软件项目最普遍、突出的特点，是导致项目失败的主要原因之一。
- 必须接受「需求会变动」的事实，做好变更管理。**需求变更管理的主要工作**：
  1. **建立需求基线**——需求确定并评审后建立第一个基线，之后每次变更评审后重新确定新基线。
  2. **确定需求变更控制过程**——制定简单有效的变更控制流程并形成文档。
  3. **建立变更控制委员会（SCCB）**——由项目多方人员（含用户方和开发方决策人员）组成，裁定接受哪些变更。
  4. **进行需求变更影响分析**——先申请后评估，经过与变更大小相当级别的评审确认，明确对整体进度和相关任务的影响及工作量。
  5. **跟踪所有受需求变更影响的工作产品**——软件计划、产品、活动相应变更以保持一致。
  6. **建立需求基准版本和需求控制版本文档**，维护变更历史记录（版本号、日期、变更内容、原因、负责人）。
  7. **跟踪每项需求状态、衡量需求稳定性**——记录基准数量和一段时间内变更数量；某需求频繁变更说明认识不深入；总体变更数过高说明范围未确定或政策变化大。
- 太细的需求定义对需求渐变**没有效果**——需求变化是永恒的。变更管理流程含**需求提交、需求受理、需求规划分析、需求实施**四个阶段（图4-6）。

## 4.3 传统需求分析方法

### 4.3.1 基于数据流建模（结构化分析 SA）

- 结构化分析（Structured Analysis，SA）是 20 世纪 70 年代最早发展起来的开发方法，代表有 Coad/Yourdon 面向数据流方法、Jackson/Warnier-Orr 面向数据结构方法、日本 PAD 方法。面向对象方法中的操作仍以结构化方法为基础。
- 结构化分析将现实世界描绘为**数据在信息系统中的流动及向信息的转化**；通常配合**结构化设计（SD）**进行系统设计。
- **数据流图（DFD）、系统流程图**等都属于结构化分析技术。

**1. 数据流图（DFD）**

- 直观展示系统中数据如何被加工处理和流动，是广泛使用的**自上而下**方法。
- 四种基本元素：**过程、实体、数据流、数据存储**。缺点：无法判断活动的**时序关系**；尤其适用于管理信息系统（MIS）。
- 确定 DFD 后还需确定**数据字典**和**加工说明**。
- 分层：**顶层**（只含一个加工，表示整个系统及其输入输出）、**中间**（对父图某加工细化）、**底层**（加工不能再分解，即「原子加工」）。
- **父图与子图的平衡**：任一子图必须与父图某加工对应，输入输出数据流保持一致（数据流数目/名称可不同，子图是对父图加工和数据流同时分解）。
- 约束：每个加工必须有输入和输出数据流；数据流必须经过加工。
- **数据字典**描述数据流图中的数据项、数据流、数据文件（配合 DFD 使用）。

**2. 系统流程图**

- 表示操作顺序和信息流动的图表，是描述**物理系统**的工具；节点代表一个或一组操作，是有向图。
- 绘制法则：**优先关系法则**（先整体当「功能」画粗略图，再逐层向下加入细节）。
- 设计步骤：分析实现程序必需的设备 → 分析数据在各设备间的交换过程 → 用基本符号描述交换过程。

### 4.3.2 基于 UML 需求建模

- 先确定系统**角色（参与者）**，再确定相应的**用例**。用例从用户（而非程序员）角度看待系统，做到以用户为中心；沟通从「希望系统为他做什么」转为「要利用系统做什么」。
- 以某进出口贸易项目为例，UML 建模基本步骤：
  1. **分析目标**——确定项目目标、定义系统特征（贸易涉及配额许可、询价、报价、合同、备货、信用证、商检、报关、运输、投保、付汇/结汇、核销退税等环节）。
  2. **确定角色（参与者）**——系统之外与系统交互的任何事物；角色存在共性，按封装和抽象原则归并（如出口商派生出口公司/工厂，存储派生码头/集装箱场地/仓库，海关派生 4 个子类，贸易管理部门派生 15 个子类，运输派生 5 个子类）。
  3. **确定需求用例**——用例捕捉功能性需求，所有用例构成**用例模型**（取代传统功能规范说明）；进出口贸易分「合同签订」「合同执行」两个阶段。
  4. **分解细化用例**——大的用例（业务用例）像黑盒，必要时打开黑盒审视内部（如「出口配额申请」细化为「计划分配配额」和「招标配额」）。
  5. **用例描述**——用顺序图、活动图、协作图或文字详细描述角色、目标、场景。

## 4.4 敏捷需求分析方法

> 教材称共 **7 个方法工具**：影响地图、需求池（backlog）、用户故事地图、用户故事编写、INVEST 原则、行为驱动开发（BDD）。其中正文分节详解 6 个，本章小结将 **MoSCoW 优先级原则**也列为方法工具之一。

### 4.4.1 影响地图（impact mapping）

- 可视化「业务目标 → 产品功能」的映射，用于需求讨论阶段。四层级别：

| 层级 | 名称 | 含义 |
| --- | --- | --- |
| 第一层 | 目标（why） | 要实现的业务目标/要解决的核心问题，应具体、清晰、可衡量；表述问题而非方案 |
| 第二层 | 角色（who） | 可通过影响谁的行为实现目标（主要用户、次要用户、产品关系人） |
| 第三层 | 影响（how） | 怎样影响角色行为达成目标（促进正面行为/消除负面行为，可能是冲突或互补的） |
| 第四层 | 功能（what） | 要交付什么功能或服务以产生希望的影响，决定产品范围，由此产生用户故事 |

### 4.4.2 需求池（product backlog）

- 需求梳理后放入需求池，即 product backlog——敏捷团队管理开发过程的**核心**，所有活动和交付物都围绕它进行。
- 迭代开发基于用户故事优先级：**Product Owner** 负责制定按重要性排序的用户故事列表，在迭代规划会议上与开发团队确认；小故事直接加入，大故事先拆分再加入。

### 4.4.3 用户故事地图（user story map）

- 把 backlog 变成**二维地图**，创建对产品的共同理解、可视化用户需求、激发故事创意。
- **第一维（横向）**：按时间顺序水平展开的用户任务，卡片间插入「然后」阅读（如「登录→创建空白费用报告→输入费用→提交费用报告」）。
- **第二维（纵向）**：某模块（任务）下的不同功能/备选方案，向下阅读时插入「或者」；按**优先级从高到低**排列。
- 可添加**标题卡**（格式化/打印/保存）实现史诗级抽象或模块分类；标题卡本身不是团队直接实施的故事，而是史诗（Epic）/主题/功能模块。
- 用途：从用户体验角度浏览发现遗漏活动（提问「用户接下来想做什么/会犯什么错/困惑什么/还需什么信息」）；加横线绘制**发布计划**，横线上方形成 **MVP（最小可行产品）**，下方为后续版本。

### 4.4.4 用户故事编写

- **用户故事三要素**：角色（谁使用）、活动（完成什么功能）、商业价值（为什么、带来什么价值）。用户故事是**范围的单位、交付的单位**。
- **编写模板**：

```
As a <type of user>,
I want <some goal>
so that <some reason>.
```

即「作为……我可以……以便于……」，通常写在卡片/即时贴上。
- **验收标准 AC（Acceptance Criteria）**：写在故事卡最后的轻量级验收测试，一般由 **PO** 编写并按 AC 验证实现。AC 作用：以用户视角表达业务交互、场景化沟通、识别体验友好性、需求共识记录、可视化故事粗细粒度、开发测试共识、限定完成边界、直观估算标准、活文档（FAQ 素材）、公平透明的定价标准。

### 4.4.5 用户故事 INVEST 原则

| 字母 | 含义 | 要点 |
| --- | --- | --- |
| I | Independent 独立 | 各故事无依赖性；「独立性」含两层——功能实现间无依赖、不要出现共同依赖的底层逻辑（如信用卡支付拆分为 Visa/MasterCard/银联时共同依赖支付底层逻辑） |
| N | Negotiable 可协商 | 需求实现程度可协商（如登录是密码/验证码/扫码，由 PO 与团队协商确定） |
| V | Valuable 有价值 | 严格按模板编写的故事必然有价值 |
| E | Estimable 可估算 | 编写者应具备该故事行业背景 |
| S | Small 小的/大小适当 | 小故事可放入短迭代、更易理解、更易估算 |
| T | Testable 可测试 | 至少含**客观性**（测试结果唯一）与**可重复性**（可重复验证） |

### 4.4.6 行为驱动开发（BDD）

- BDD 由 **Dan North 在 2003 年**命名，作为对 TDD 的回应，介于**业务领域与开发领域之间**（TDD/ATDD/BDD 的关系见原文图）。
- 核心在于「行为」：业务需求划分为业务场景，以 **Given…When…Then…** 范式描述，形成领域建模规约：

```
Given   场景的前提条件、初始状态（现在完成时态）
When    采取某动作或发生某事件（一定是动词，一般现在时）
Then    用「应该…(should be…)」描述期望结果（不用 assert）
```

- 强调 **What（什么）而非 How（怎么）**；使用自然语言编写团队可读的实例，最小化技术语言与领域语言来回翻译的代价。
- BDD 是 PO、开发、测试共创的行为，作为「代码到需求」的桥梁，其用户故事近自然语言、可直接作为需求文档。

## 4.5 AI 驱动项目的需求分析方法

- **需求的智能化抽取**：借助 AI 实现业务人员与 AIGC 直接对话生成软件（不需程序员「翻译」）；ChatGPT 可充当业务人员、产品经理、敏捷教练、测试人员，帮助梳理思路；通过需求讨论会议纪要等文件实现需求智能抽取。
- **用户故事需求的自动化生成**：利用 AI 生成需求具体描述，助力项目编写用户故事、梳理 MVP。

## 4.6 MED 项目的需求案例分析

> 项目：「医疗信息商务平台」（医疗信息管理平台，文档编号 BUPTMED-20120801055）。采用敏捷生存期模型，需求变更大的仍需变更控制。

### 4.6.1 需求规约

需求规约文档结构（共 12 章 + 附录）：导言、概述、UML 建模语言、执行者定义、主用例、医疗贸易社区服务、产品目录、后端事务管理、交易事务服务、内容管理、性能需求、产品提交需求，附录 A 关键特性列表。

**执行者（角色）定义**（actor 指与系统产生交互的外部用户或外部系统）：

| 用户类型 | 角色 | 子角色 |
| --- | --- | --- |
| medeal.com | webmaster / 内容管理经理 / 市场部经理 | — |
| 组织 · 交易组织 | 厂商 | 管理者、内容管理经理、内容管理者、销售经理、销售人员、决策人、市场分析员、合同履行人员、售后服务经理、售后服务人员、一般人员 |
| 组织 · 交易组织 | 经销商 | 上述子角色 + 采购经理、采购员 |
| 组织 · 交易组织 | 医院 | 管理者、决策人、采购经理、采购员、护士长、护士、一般人员 |
| 组织 · 非交易组织 | 协会/学会 | 管理者、编辑者、会员 |
| 个人 | 成员 / 非成员 | — |

- 厂商=卖方（医疗器材设备生产者，提供维修保养）；医院=买方（使用者）；经销商=买卖双方的中间服务（多厂商指定，既可为买方也可为卖方）。

**性能需求**：
- 响应时间：任何操作反应时间在 **5s 以内**，能监测通信中断、无法连接数据库等非正常情况。
- 可靠性：保证 **7×24h 不停机**，支持 **20 人同时在线**客户端登录。
- 开放性：灵活性以适应将来功能扩展。
- 安全性：安全政策含**访问控制、数据保护、通信安全、交易完整性**（保证交易公正性、身份真实性、信息完整性、不可抵赖性）。

**产品提交需求**：提交物含网站应用系统软件包、发布内容数据库（含建库脚本）、产品录入维护工具包、内容管理过程文档、使用维护说明文档；提交方式为 **CD 介质**。
**优先级划分**（Phase1 按优先级从高到低）：1) 用户信息管理（含注册登录）2) 产品浏览和查询 3) 产品维护 4) 交易 5) 其他。

### 4.6.2 需求变更控制系统

- 所有用户需求变更**直接由项目经理签收**并纳入变更管理；未纳入变更管理的需求**不进行开发**。
- 变更流程涉及业主方、项目需求管理方、项目开发方、项目测试方四方（提出需求变更要求 → 需求决策 → 整理需求调研表 → 业主确认 → 明确需求 → 编制进度计划/修改开发计划 → 配置资源、制订方案与测试计划 → 实施开发/测试 → 上线发布 → 业主确认）。

## 4.7 MSHD 项目的需求规约

> 需求分析采用**传统 UML 用例图 + 敏捷用户故事**结合的方法，形成软件需求规约（含功能需求和非功能需求），按迭代过程渐进式完善。

### 4.7.1 需求池与用户故事地图

- 第一步产生**产品需求池**（如手机号/邮箱登录、用户注册/主页/评论/上传、数据版本管理/恢复/校验、援灾渠道、灾情通知/预测/统计、权限/角色管理、数据备份等）和**用户故事地图**。
- 按优先级分**三次迭代**完成全部功能：
  - **第一次迭代**：用户登录、基于 XML 和 JSON 格式的数据获取、灾情数据编码和基本震情编码、基本数据管理。

## 本章小结

- 范围计划从需求开始：项目范围 = 所包括的工作 + 产生产品所用的过程，项目目标必须可实现、可度量。
- **需求管理五过程**：需求获取 → 需求分析 → 需求规约编写 → 需求验证 → 需求变更。需求分业务需求、用户需求、功能需求三个层次，最终形成 SRS。
- 需求阶段埋下 40%～60% 的问题、80% 的失败源于需求不明确，凸显需求管理的重要性。
- **需求验证**八个方面：正确性、一致性、完整性、可行性、必要性、可检验性、可跟踪性、最后签字。
- **需求变更管理**核心：建立需求基线、SCCB、变更控制流程、影响分析，用需求跟踪矩阵管理需求。
- **传统方法**：结构化分析（数据流图 DFD、系统流程图）与 UML 用例建模；**敏捷方法**（7 个工具）：影响地图、需求池、用户故事地图、用户故事编写、INVEST 原则、MoSCoW 优先级原则、行为驱动开发（BDD）。
- AI 驱动需求管理：需求智能化抽取、用户故事自动化生成。
- 案例：MED 项目（医疗信息商务平台）给出完整 SRS 与变更控制流程；MSHD 项目用「UML 用例图 + 用户故事」结合的方式形成需求规约，分三次迭代渐进式完善。
