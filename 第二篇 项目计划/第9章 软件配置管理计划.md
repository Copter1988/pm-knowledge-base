# 第9章 软件配置管理计划

> 本章讲「如何管理变化」：软件项目的变化是持续、永恒的，配置管理通过标识配置项、建立基线与配置库、控制变更、审计与状态报告，有效管理产品的完整性和可追溯性，是范围、成本、进度、质量之外的重要辅助计划。

## 核心概念速览

| 概念 | 一句话 |
| --- | --- |
| 软件配置管理（SCM） | 一套管理软件开发/维护及中间软件产品的方法规则，系统控制对配置的修改并维护其完整性与可追踪性 |
| 软件配置项（SCI） | 项目定义受控于配置管理的项，即生存期中产生或使用的特定、可文档化的工作产品集 |
| 基线（baseline） | 一个或多个配置项的集合，内容状态已通过技术复审、在某一阶段被接受，只能经正式变更控制过程改变 |
| SCCB | 软件配置控制委员会，评估基线变更对项目的影响并决定是否变更的机构（可一人或小组） |
| 配置库 | 受控库，集中存储所有基线配置项及其版本、修改请求、变化记录的存储系统 |
| 变更控制系统 | 变更请求 → 变更评估 → 变更批准/拒绝 → 变更实现 的文档化流程 |
| 全面配置管理 | 对项目所有产物（代码、构建产物、应用、环境）及其关系进行有效管理，支撑持续交付 |

---

## 9.1 配置管理概述

- 软件项目开发与实施始终在「变化」中进行：需求、技术、架构、代码乃至环境都会变。
- 有效配置管理可在受控方式下引入变更、监控执行、检验结果、确认变更并使其可追溯。
- **历史**：配置管理概念源于美国，美国空军 1962 年制定第一个配置管理标准；软件配置管理概念于 20 世纪 60 年代末 70 年代初提出，加利福尼亚大学圣巴巴拉分校 Leon Presser 教授在海军的航空发动机研制中发表论文《Change and Configuration Control》，提出控制变更和配置的概念。
- **发展**：从最初的版本控制，发展到提供工作空间管理、并行开发支持、过程管理、权限控制、变更管理等完整理论体系；工具方面出现 ClearCase、CVS、Microsoft VSS、Hansky Firefly、GIT 等。
- 配置管理贯穿软件生存期全过程，目的是建立和维护软件产品的**完整性**和**可追溯性**。

### 9.1.1 软件配置管理的定义

- SCM 是一套管理软件开发和维护及其各种中间软件产品的方法和规则，也是提高软件质量的重要手段，帮助团队对开发过程进行有效的变更控制。
- 通过特定时刻选择软件配置、系统控制对配置的修改、并在整个生命周期中维护配置的完整性和可追踪性来实现。
- 典型的中间产品：代码、技术文档、产品文档、管理文档、数据、脚本、执行文件、安装文件、配置文件甚至参数等。
- 软件配置管理相当于软件开发的**位置管理**，回答以下问题：
  - 我（他）是谁？
  - 为什么我（他）在这里？
  - 为什么我（他）是某某？
  - 我（他）属于哪里？
- 纳入配置管理的工作产品包括交付给顾客的软件产品（需求文档、代码）及生成这些产品所需的产品项（如编译程序）。
- **防止狭义理解**：配置管理≠版本控制。代码内容分两个层次——项目应用代码与环境相关代码；环境相关代码再细分为环境配置（基本固定的配置）与环境数据（部署时随情况调整的数据，如配置文件、开发/测试/生产环境地址）。

### 9.1.2 软件配置项

- **定义**：SCI 是项目定义其受控于软件配置管理的项，是在生存期中产生或使用的特定、可文档化的工作产品集。
- **Pressman 定义**：软件过程的输出信息分 3 类——计算机程序（源代码和可执行程序）、描述计算机程序的文档（针对技术开发者和用户）、数据（程序内部或外部），总称为软件配置项。
- **常见 SCI 示例**：软件项目计划、需求分析结果、软件需求规约说明书、设计规格说明书、源代码清单、测试规格说明书、测试计划、测试用例与实验结果、可执行程序、用户手册、维护文档；有时也把编辑器、编译器和其他 CASE 工具固定地作为配置的一部分。
- **类与实例类比**：配置项相当于类，版本相当于实例（如需求规约 V1.1、V1.2、V1.3 都是需求规约配置项的实例）。
- 配置项的识别是配置管理活动的基础；配置项划分可实现项目开发的数字化跟踪和管理。

### 9.1.3 软件项目基线

- **定义**：基线是一个或多个配置项的集合，其内容和状态已通过技术复审，并在生存期某一阶段被接受。
- **IEEE 定义**：已经正式通过复审和批准的某规约或产品，可作为进一步开发的基础，且只能通过正式的变化控制过程改变。
- 配置项分**基线配置项**（如设计文档、源程序）与**非基线配置项**（如项目各类报告）两类。
- 基线代表开发过程的**里程碑**，标志一个阶段的结束；已成基线的配置项可修改但须经特殊正式过程评估，未成基线的可非正式修改。
- 常用软件基线（阶段 → 基线成果）：

| 开发阶段 | 基线成果 |
| --- | --- |
| 系统工程 | 系统规格说明 |
| 需求分析 | 软件需求规约说明 |
| 软件设计 | 软件设计说明 |
| 程序编写 | 源代码 |
| 测试 | 测试计划、过程、数据 |
| 系统提交 | 可运行系统 |

### 9.1.4 SCCB

- 软件配置控制委员会（Software Configuration Control Board，SCCB）是处理配置项变更的基本机制，可一人或一个小组，通常由项目经理及相关人员组成。
- 从技术、逻辑、策略、经济和组织的角度及基线层次评估变更影响，比较变更期望与对进度、预算的影响。
- **目标**：保持全局观点，评估基线变更对项目的影响并决定是否变更。
- **责任**：评估变更、批准变更申请、在生存期内规范变更申请流程、对变更进行反馈、与项目管理层沟通。

### 9.1.5 软件配置管理在软件开发中的作用

- 主要思想和具体内容在于**版本控制**：追踪文件的变更（谁、何时、改了什么），版本号递增（如 V1.0、V1.1、V2.1），可随时恢复任一版本；记录配置项发展历史保证可追踪性。
- 版本控制的另一重要功能是**并行开发**，解决版本同步和开发通信问题。
- **版本控制 ≠ 配置管理**：版本控制重要但不是全部，工作空间管理等同样不可分割。
- 配置管理相当于软件开发生产线中的**仓库和调度**；无变更管理则项目被无限放大；有效配置管理可不断「命中移动的目标」，是对工作成果的有效保护。

## 9.2 软件配置管理过程

配置管理主要包括**配置项标识、变更控制、配置项状态统计、配置项审计**等活动。基本过程：

1. 配置项标识、跟踪
2. 配置管理环境建立
3. 基线变更管理
4. 配置审计
5. 配置状态统计
6. 配置管理计划

### 9.2.1 配置项标识、跟踪

- 将需控制的产品拆分成配置项，建立对应关系，进行系统跟踪和版本控制，最终组合生成适用于不同应用环境的正确软件版本。
- 配置项应唯一标识；一个项目可有文档类、代码类、工具类等一种或多种标识定义。
- **标识实例**：`项目名称_所属阶段_产品名称_版本标识`；版本号以「V」开头，分 3 节（主版本号、次版本号、内部版本号），以小数点间隔。
- 例：`School_Design_HLD_V2.1.1` = School 项目在设计（Design）阶段的总体设计（HLD）V2.1.1 版本。
- 需跟踪配置项之间的关系（如需求规约 V2.0 与系统测试用例 V1.0 的对应跟踪）。

### 9.2.2 配置管理环境建立

- 最重要的是建立**配置库**（即受控库）：存储所有基线配置项及相关文件，是建立和维护软件产品完整性的主要手段。
- 配置库存储配置项相应版本、修改请求、变化记录；版本控制是其核心功能，所有元素自动标识版本并保证命名唯一。
- 配置库中的文件不可更改，任何更改视为创建新版本。check out（导出）的文件自动锁定直到 check in（导入）；对最新版本修改产生新的顺序递增版本，对更老版本修改产生**分支版本**。
- 只存储版本间差异的方法称为**增量**，节省空间和访问时间；可按状态标签、修订版本号、日期、作者导出。
- **工作空间划分**（3 类分支）：个人（私有）、团队（集成）、全组（公共）。私有空间仅开发人员本人可操作；集成空间团队可读写、其他成员只读；公共空间统一存放各团队阶段性成果、提供全组统一标准版本。

### 9.2.3 基线变更管理

- 变更原因：程序员犯错误、客户需求变更、产品环境变更、新技术等；变更应经 SCCB 授权、按程序控制并记录修改过程。
- **变更控制系统流程**：变更请求 → 变更评估 → 变更批准/拒绝 → 变更实现。

1. **变更请求**：变更控制的起始点，通常来自系统外事件触发（需求变化、不符合项、软件测试报告）。需填写《项目变更申请》表单（项目名称、变更申请人、提交时间、变更题目、紧急程度、变更具体内容、变更影响分析、变更确认、处理结果、签字）。
2. **变更评估**：验证请求的完整性、正确性、清晰性；不完整/无效/已评估的请求拒绝并保留记录。填写《项目变更评估表》（技术因素、运行、质量可靠性、规模、选择余地、资源、测试、利益、紧急性、依赖性、接口影响、进度影响、预算影响）。
3. **变更批准/拒绝**：SCCB 做出「直接实现、挂起或延迟、拒绝」三种决策；拒绝时通知请求人并保存记录。变更被接受后按 3 种进度形式之一实现：尽可能快地实现、按特定日期实现、在另外的版本中实现。
4. **变更实现**：项目人员用 SCCB 给予的权限从受控库取出基线副本，实现并验证变更；SCCB 确认后将更新的基线放回配置库并更新版本标识。

### 9.2.4 配置审计

- 一种质量审计活动，是变更控制的补充手段，确保某变更需求已被实现。
- **两方面的内容**：
  - **配置管理活动审计**：确保成员所有配置管理活动遵循已批准的方针和规程（如导入/导出频度、版本升级原则）。
  - **基线审计**：保证基线化工作产品的完整性和一致性。
- **完整性**考查：基线库是否含所有计划配置项、配置项内容是否完整、代码源文件是否齐全、编译能否产生最终产品。
- **一致性**考查：需求与设计、设计与代码的一致；有变更时检查所有受影响部分是否都做了相应变更。
- 记录不符合项并跟踪直到解决。

### 9.2.5 配置状态统计

- 定期检测配置管理系统运行情况及配置项变更历史，结果以**配置状态报告**形式给出，尽量通过工具自动生成。
- 配置状态报告着重反映当前基线配置项状态，主要内容：配置库结构和说明、开发起始基线构成、当前基线位置及状态、各基线配置项集成分支情况、私有开发分支分布、关键元素版本演进记录等。
- 评估系统状态常需信息：变更请求数量（按需求/文档/设计/源码等类别分类）、变更请求历史报告（各活动所花时间）、配置管理系统及 SCCB 运作异常次数。

### 9.2.6 配置管理计划

- 配置管理计划确定配置管理解决方案，影响开发环境、过程模型、使用者、产品质量与组织机构，是项目计划的一部分，由**配置管理者**制订。

**主要角色与分工**：

| 角色 | 职责 |
| --- | --- |
| 项目经理（PM） | 制定修改组织结构和配置管理策略；批准发布配置管理计划；决定项目起始基线和开发里程碑；接受审阅 CCB 报告 |
| 配置控制委员会（CCB） | 定制变更控制流程；建立、更改基线设置并审核变更申请；根据配置管理员报告决定对策 |
| 配置管理员（CMO） | 工具日常管理与维护；提交配置管理计划；各配置项管理与维护；执行版本控制和变更控制方案；完成配置审计并提交报告；培训开发人员；识别问题并拟解决方案 |
| 开发人员 | 按确定的配置管理计划和工具使用模型完成开发任务 |

**配置管理计划模板**：1 引言；2 软件配置管理（SCM 组织、责任、与其他机构关系）；3 软件配置管理活动（配置标识、配置控制程序、配置状态报告、配置审核）。

**实施建议**：
- 小企业/小项目：制定过程规则（可不使用工具）实现版本管理，条件允许用工具更好。
- 中小企业/中小项目：过程规则 + 简单版本管理工具，实现部分配置管理功能。
- 大企业/大项目/异地开发：配备专门配置管理人员 + 严密过程规则 + 配置管理工具，尽量多实现配置管理功能。

## 9.3 敏捷项目的配置管理

敏捷项目的主要特征是实现**持续交付**，配置管理（版本管理）是持续交付的重要基础。

### 9.3.1 全面配置管理

- 对项目所有相关产物及其关系进行有效管理，任何时刻能用标准化方法完整可靠地构建可正常运行的系统（不只是可工作的软件），且信息可关联、可审计、可追踪。
- 至少做好三方面：**代码和构建产物的配置管理**（分支策略、版本控制系统、构建产物及依赖）、**应用的配置管理**（配置存取与灵活性）、**环境的配置管理**（硬件、软件、基础设施、外部系统）。

### 9.3.2 开发过程的分支管理策略

- 纳入版本控制的不仅是源代码，还包括测试代码、数据库脚本、构建/部署脚本、依赖库文件等。
- 两种策略：**基于分支的开发**与**基于主干的开发**；敏捷持续交付建议采用**基于主干的开发（TBD）**。

**基于分支的开发**：接需求后拉出分支，分支生命周期长、可多分支并行，上线前后才合并到主干。优点：功能可完全并行、互不干扰、分支记录清晰。缺点：不同分支交互多时合并冲突量大、易出错耗时；时间越长分支与主干差别越大、风险越高，故持续交付不推荐。

**基于主干的开发**：所有成员提交到主干，提交后自动触发持续集成验证与快速反馈，冲突早期发现解决，主干一直保持健康，每次合入验证后可安全发布。主干开发不排斥分支（可创建发布分支并行做发布测试与缺陷修复），但强调**频繁有规律的提交**（如每人每天一次），提交前充分本地验证与预测试以降低污染主干的风险。

### 9.3.3 构建产物、应用、环境的配置管理

- **构建产物**：编译或打包阶段生成的可部署二进制包；一般不推荐存放于版本控制库（效率低且不必要），可通过版本标识等信息管理。
- 交付可运行系统需把应用配置与程序文件、数据、各类部署/控制脚本一起标准化注入**部署包**（全量包）；Docker 即封装应用与依赖生成镜像的典型方式。
- 部署包还需提供稳定的**控制接口**，描述程序如何启动、停止、重启、监控健康状况及如何部署运维。

## 9.4 配置管理工具及其应用实例

配置管理包含 **3 个要素：人、规范、工具**。配置管理工作尤其强调工具支持；选型需考虑经费（经费充裕采购商业工具、有限则用自由软件）。

### 9.4.1 常见的配置管理工具

- **历史**：1975 年 Leon Presser 成立 SoftTool 公司开发 CCC 工具；继 CCC 之后最具里程碑式的两个自由软件是 Marc Rochkind 的 **SCCS** 与 Walter Tichy 的 **RCS**，绝大多数现代工具都源于它们的设计思想与体系架构。
- 常见工具一览：

| 工具 | 说明 |
| --- | --- |
| Rational ClearCase | IBM 旗下企业级跨平台高档配置管理工具，功能最强大；支持版本控制、工作空间管理、Build 管理；价格不菲、需专门管理员与较多培训 |
| Git | 分布式版本控制系统，分支/合并/提交/标签等功能，广泛用于源代码管理 |
| GitHub / GitLab | 依托 Git 的代码托管平台，提供 Web 界面、wiki、问题跟踪器及协作工作流 |
| Gitee | 开源中国社区 2013 年推出的基于 Git 的代码托管服务 |
| Bitbucket | 基于 Git 的托管平台，与 Jira 等 Atlassian 产品集成性强 |
| CVS | 开源并发版本系统，简单易用跨平台免费，中小软件企业广泛使用；缺技术支持 |
| SVN（Subversion） | 集中式版本控制系统，2000 年 CollabNet 为替代 CVS 开发，核心是版本库，记录每次修改、可回溯 |
| Mercurial | 分布式版本控制系统，注重易用性和性能 |
| Jenkins | 开源自动化服务器，用于自动构建、测试和部署 |
| Ansible / Puppet | 自动化配置管理、应用部署与基础设施状态维护工具 |
| Microsoft VSS | 为 Visual Studio 配套的小型版本控制工具，与 VS 无缝集成、使用简单 |

### 9.4.2 配置管理工具应用实例（Git）

- Git 分支：**master**（记录官方发布轨迹）、**develop**（集成分支，记录新功能轨迹）；临时分支有 **feature**（新功能）、**release**（新版本发布）、**hotfix**（发布版 bug 修复）。
- **新功能分支**：每个新功能从 develop 派生独立分支，完成后合并回 develop，生命周期结束，不与 master 直接交汇。
- **发布分支**：功能满足发布条件后合并到 develop，再开 release 分支（只做 bug 修复和版本导向任务），到发布日期合并回 master 发布、打标签，同时合并回 develop。
- **维护分支（hotfix）**：快速修复生产环境紧急问题。
- **管理策略**：develop 主程序从 master 稳定版合并而来，按需求单位拉 feature 分支开发调试，通过代码审查后合并入 develop；特性集成完毕开 release 分支测试，通过后修复 bug 提交 master，master 最终合并回 develop；上线中发现紧急升级进入 hotfix 分支。

## 9.5 MED 项目配置管理计划案例分析

「医疗信息商务平台」配置管理计划文档结构：1 导言（目的、范围、缩写说明、术语定义、引用标准、版本更新记录）、2 配置管理流程、3 配置项标识、4 配置库建立、5 入库程序、6 出库程序、7 基线变更程序。

- **缩写**：SCM（软件配置管理）、VM（版本管理）、VMG（版本管理组）。
- **版本更新记录**：0.1 初始版（2018-7-3）、0.2 修改第 5 章（2018-7-8）、1.0 修改第 4 章（2018-7-12）。
- **配置项标识**：文件名规则含 5 部分，如 `BUPT-Med-RM-SRS-V1.0`（BUPT=企业名、Med=项目名、RM=项目阶段、SRS=文档类型、V1.0=版本号）。
- **配置库建立**：采用 VVS 工具；基线产品包括 B_RM（需求基线）、B_DESIGN（设计基线）、B_CODE（代码基线）、B_TEST（测试案例基线）等，非基线产品包括 TCM、RM、SPP、SPTO、SPE、SQA、SCM、TP 等；对项目人员按只读/读写授权。
- **入库程序**：分基线产品与非基线产品入库（导入、版本标识、描述、关联项与覆盖关系、生成基线状态记录表）。
- **出库程序**：有权限者按需以可读方式导出；变更时配置管理者以可写方式导出，期间该产品只能以可读方式出库。
- **基线变更程序**：新需求变更经审核通过后在下一个 Sprint 中实现，否则拒绝；配置管理者做波及分析 → 提交 SCCB 确定修改文件 → 出库修改 → 提交 → 入库 → 生成基线变更记录表。

## 9.6 MSHD 项目配置管理计划案例分析

- 项目配置管理体现为**版本管理与多人协同**：使用 Git + GitHub 实现多人协同、多端同步，选定**基于分支的开发**策略；通过同步配置文件与 pnpm 环境管理器，同时完成代码/构建产物、应用配置与环境配置管理，实现敏捷开发的全面配置管理。
- **三级分支**（稳定性/功能不同，nightly 基于 dev，dev 基于 main）：

| 分支 | 定义 |
| --- | --- |
| main（稳定） | 通过严格测试、相对稳定、适合生产环境；每轮迭代完成标志是产出稳定版本并部署 |
| dev（开发） | 活跃开发（新功能、bug 修复），含最新更改、未经全面测试，但保证基本功能运行 |
| nightly（夜间） | 高实验性与即时性，持续提交新代码，极少测试、可能存在问题，最新功能最多也最不稳定 |

- **升级流程**：新功能先推 nightly（经单元测试）→ 进入 dev（与其他组件联动验证）→ 合并入 main 成为下一稳定版本。
- **三级分支优势**：版本控制和管理、稳定性与实验性平衡、灵活性和迭代、早期反馈和测试、并行开发。
- **CI/CD**：项目采用 Spring Cloud，每个服务为可独立运行的 jar 包，选用 IDEA 插件 Alibaba Cloud Toolkit 进行 CI/CD，开发人员可随时在 IDEA 中部署服务而不受限于 GitHub。

## 本章小结

- 配置管理可有效管理产品完整性和可追溯性，控制软件变更，是范围/成本/进度/质量之外的重要辅助计划。
- 核心概念：SCM、SCI、基线、SCCB、配置库；版本控制是基本要求但不是配置管理的全部。
- 配置管理基本过程：配置项标识跟踪 → 配置管理环境建立 → 基线变更管理 → 配置审计 → 配置状态统计 → 配置管理计划。
- 变更控制经 SCCB 授权，走「变更请求→评估→批准/拒绝→实现」流程；配置审计与状态报告是变更控制的补充与监督。
- 敏捷/持续交付强调全面配置管理，推荐基于主干的开发（TBD）模式；MED 用 VVS 工具建立基线库，MSHD 用 Git+GitHub 三级分支（main/dev/nightly）实现多人协同。
