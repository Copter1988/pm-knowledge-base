# 第5章 软件项目范围计划——工作分解

> 本章讲「如何分解项目范围」：通过工作分解（WBS）把项目拆成更小、更易管理、更易操作的可交付成果，使责任分工更明确；传统分解方法（模板参照/类比/自顶向下/自底向上）与敏捷的用户故事分解（epic → story）殊途同归，最终界定项目范围基线。

## 核心概念速览

| 概念 | 一句话 |
| --- | --- |
| 工作分解结构（WBS） | 面向可交付成果、对项目元素分组的分级树形结构，组织并定义整个项目范围 |
| 工作包（work package） | WBS 最低层次的可交付成果，由唯一主体负责，可进一步分解为活动 |
| 工作分解 | 对需求的进一步细化、确定项目所有任务范围的过程，结果是 WBS |
| WBS 字典 | 汇集 WBS 具体工作要素阐述的文件，含进度日期、成本预算、人员分配等信息 |
| 史诗（epic） | 较大的高层用户故事，无法在一个迭代内完成，可分解为更小的用户故事 |
| 用户故事（user story） | 从用户角度描述、用户能看懂的需求，是敏捷分解的基本单元 |
| 范围基线 | WBS 提供的项目范围基准，是范围变更的重要输入 |

---

## 5.1 工作分解

**为什么必须做工作分解**：
- 项目管理第一法则是「做正确的事」，其次才是「正确地做事」；正确定义项目开发范围是成功的第一步，没有范围定义项目可能成为「无底洞」。
- 项目交付成果是项目的最终输出，是投入各种资源的依据；范围管理保证项目计划**包括且仅包括**为成功完成项目所需的所有工作。
- 范围计划编制是将产生项目产品所需进行的项目工作（项目范围）**渐进明细和归档**的过程；主要依据是**需求规约**，范围计划在此基础上进一步深入细化。
- 把大项目拆成小项目可降低对管理人员的要求、减少管理风险、下放权力、调动积极性，目标具体、易取得阶段性成果（「小就是美」）。
- 项目范围、项目工期、项目规模（成本）是支持项目成功的**三大支柱**；不可能只做小项目，但可把项目划分成生命周期的不同阶段以简化复杂度、提高成功率。

### 5.1.1 WBS

- 当问题过于复杂时先分解为易解决的子问题再分别解决（「化繁为简，分而治之」）。
- **WBS（Work Breakdown Structure，工作分解结构）**是工作分解的结果，是面向可交付成果的、对项目元素的分组，组织并定义了整个项目的范围。
- **不包括在 WBS 中的工作不是该项目的工作**；只有在 WBS 中的工作才是项目范围。它是一个**分级的树形结构**，是对项目由粗到细的分解过程。
- 每细分一个层次表示对项目元素更细致的描述；WBS 是项目评估的前提和**自下而上估算法**的基础。
- **WBS 编码**：每个具体细目通常指定唯一编码（code of accounts），编码设计与结构设计应一一对应——结构的每一层代表编码的某一位数，各组成元素编码唯一。例如「系统：1」，其下子系统为 1.1、1.2、1.3，再往下为 1.1.1、1.1.2、1.1.3 等。
- 没有完善的 WBS 或范围定义不明确，就不可避免地出现变更，导致返工、延长工期、降低士气。
- 制定 WBS 的指导思想是**逐层深入**：先确定项目成果框架，再每层分解，优点是结合进度、更直观、时间感强、评审中易发现遗漏或多出的部分。

### 5.1.2 工作包

- **工作包（work package）是 WBS 最低层次的可交付成果、WBS 的最小元素**（如图中 1.1.1、1.1.2、1.1.3 等）。
- 工作包应当由**唯一主体负责**，可分配给另外一位项目经理通过子项目的方式完成；作为外包工作时需制订相应的**合同 WBS**。
- 可对工作包进行成本估算、进度安排、风险分析以及跟踪控制；工作包还会被进一步分解为**项目进度中的活动**。
- 每个被分配的活动都应与一个工作包相关；当工作包被项目的活动创建后，**所有工作包的总和等于项目范围**，项目范围完成即满足产品要求，构成一个完整项目。

### 5.1.3 工作分解的形式

WBS 可采用提纲式（清单式）、组织结构图式（图表式），或能说明层级结构的其他形式表达。

**1. 提纲式（清单式）WBS**：以清单形式层层分解，如「程序变化计数器」项目：

```
1 程序变化计数器
  1.1 比较两个版本的程序
    1.1.1 预处理
    1.1.2 文件比较
    1.1.3 结果处理
  1.2 找出修改后的程序中增加和删除的代码行
    1.2.1 找出增加的代码行
    1.2.2 找出删除的代码行
  1.3 统计修改后的程序中增加和删除的代码行数
    1.3.1 统计增加代码行数
    1.3.2 统计删除代码行数
  1.4 统计总的代码行数
  1.5 设定标记以指示修改的次数
  1.6 在程序的头部增加修改记录
```

**2. 组织结构图式（图表式）WBS**：类似组织结构图，用图表形式层层分解，如「程序变化计数器」项目图表分解（版本比较 → 文件比较 → 预处理/结果处理，找出增删行、统计增删行数、统计总行、标记修改、修改记录等）。

### 5.1.4 WBS 字典

- **WBS 字典（WBS dictionary）**收集对 WBS 具体工作要素的阐述，包括对工作包的阐述以及其他信息（进度日期、成本预算、员工分配等），用于明确 WBS 的组件是什么。
- 典型 WBS 字典实例（BSN 事件日志管理系统）字段：WBS 表示号、名称、主题目标、描述、完成的任务、责任者、完成的标识（如通过质量保证部的验收报告）、备注。

## 5.2 传统工作分解方法

工作分解应根据需求分析结果和项目相关要求，参照以往项目分解结果进行，最终结果是 WBS。基本过程：输入 → 分解 → WBS。

**基本步骤**：
1. 确认并分解项目的主要组成要素（以项目目标为基础，作为第一级整体要素；用有形、可证实的结果描述，便于绩效检测）。
2. 确定分解标准并统一（如以生存期阶段、功能组成为标准；分解中统一使用一种标准，避免双重标准）。
3. 确认分解是否详细、能否作为费用和时间估计的标准、明确责任。
4. 确定项目交付成果（有衡量标准，以此检查交付结果）。
5. 验证分解的正确性，验证后建立一套编号系统。

### 5.2.1 模板参照方法

许多应用领域都有标准或半标准 WBS，可作为模板参考（如某软件企业的 WBS 模板：软件系统发布版本 → 项目规划、合同签订、需求开发、接口设计、编码、集成测试、验收测试等）。企业提供 WBS 分解指导说明和模板，项目人员评估相应信息来开发 WBS。

### 5.2.2 类比方法

虽然每个项目唯一，但 WBS 常被「重复使用」——许多项目在阶段周期上有相同或相似的分解要求。可采用类似项目的 WBS 作参考；企业保存 WBS 库和项目文档供参照，很多项目管理工具也提供 WBS 实例。

### 5.2.3 自顶向下方法

- 采用演绎推理，从一般到特殊、从项目大局入手逐步分解子细目（软件项目 A → 功能 1/2/3 → 子功能 1/2/3）。
- 需要更多逻辑和结构，是创建 WBS 的**最好方法**；先确定每个解决方案，再划分成可实际执行的步骤。
- 适用：开发人员对项目比较熟悉、对项目大局有把握。
- 操作：把主要交付成果/阶段写在便条上贴白板 → 逐个分解为更小交付成果 → 直到分解为易管理的工作包。可先把握大方向、给成员分配工作，不必一开始分得太细。

### 5.2.4 自底向上方法

- 与自顶向下相反，从特殊到一般：先定义项目的特定任务，再组织成更高级别的 WBS 层（软件项目 A ← 功能 1/2/3 ← 子功能）。
- 操作：把可能的任务写在便条上贴白板，观察任务关系，按逻辑层层组合成 WBS。
- 是一种发挥创造力的解决方法，适用：对项目人员来说是崭新的项目。

## 5.3 工作分解结果验证

### 5.3.1 分解结果检查原则

通过确认 WBS 较低层组件是完成上层可交付成果的**必要且充分**的工作来核实分解正确性。不同的可交付成果可分解到不同层次；分解越细，规划/管理/控制越有力，但过细会造成管理努力无效耗费、资源使用效率低下、实施效率降低、数据汇总困难。

**基本检验原则**：
- 明确并识别项目的主要组成部分（可交付成果 + 项目管理本身）；低层细目是否必要且充分，否则修正。
- 确定每个可交付成果的详细程度是否足以编制恰当的成本和历时估算；最底层要素存在重复就应重新分解。
- 确定可交付成果的组成元素，用切实、可验证的结果描述（既含产品也含服务），便于绩效测量。
- 核实分解正确性：最底层项是否必要且充分、定义是否清晰完整、能否恰当编制进度和预算。
- 与相关人员对 WBS 结果进行评审。

**实际操作的注意事项**：
- 分解结构是把**产品/服务结构、组织、过程**三种结构综合的过程；应善于将按产品/服务划分、按阶段划分、按组织责任划分有机结合。
- 最底层工作要具体，有利于责任分配、完整无缺地分配给个人/组织，明确工作块界面。
- 逐层分解也就是给组织人员分派角色和任务的过程；先分大块再细分，最底层可控可管理，避免分解过细，**最好不要超过 7 层**；注意参考类似项目、与相关人员讨论。
- 最底层工作块要有全面、详细、明确的文字说明并定义任务完成标准，汇集起来编成 WBS 字典。
- **并非所有分支都必须分解到同一水平**；任何分支最底层的细目叫工作包。按软件项目平均规模，推荐**至少拆分到一周的工作量（40 小时）**。工作包是完成一项具体工作所要求的特定、可确定、可交付、独立的工作单元。**任何项目并非只有唯一正确的 WBS**。

### 5.3.2 WBS 确定项目范围

WBS 提供项目**范围基线**，是范围变更的重要输入，使项目经理集中注意力于目标、不必考虑细节，为开发提供实施框架、明确责任、提供具体工作包，是估算和编制进度计划的基础：

- **明确完成项目所需的工作**——充分必要条件（必须完成且只需完成）。
- **建立时间观念**——项目经理与团队共同为可交付成果努力。
- **提供控制手段**——可视化地提供每个任务的状态和进展。
- **是范围基线的重要组成部分**——批准的需求规约及 WBS 字典也是基线组成部分。
- **及时提示是否变更**——可监督范围变化。

## 5.4 基于用户故事的敏捷工作分解

- 敏捷开发通过用户故事把需求具体化为可迭代开发的单元。较大的高层用户故事定义为**史诗（epic）**，一般无法在一个迭代内完成，可分解为更小的用户故事；史诗常包含很多**特性（feature）**（一类需求），特性再分解出**用户故事（user story）**，用户故事下再开发必要的**任务（task）**：

```
epic（史诗） → feature（特性） → user story（用户故事） → task（任务）
```

- 分解故事最典型的原因：把故事拆成足够小，以便在一次冲刺中交付其中几个；借此将**高价值**与**低价值（高付出）**的部分分开，低价值故事在重新确定优先级时会自然沉到待办列表底部。
- **两个目标**：缩小故事、剥离低价值部分。分解建议：最大的故事也要能在一次迭代（Sprint）内完成，最好在 **1/4 迭代时间**内完成；故事足够小以在一次冲刺中交付其中几个，不能要求十全十美。
- 分解标准：按业务工作流程的不同步骤、按不同业务规则、按不同操作、按功能性/非功能性需求等。
- 用户故事是站在用户角度描述、用户能看懂的故事；开发人员最容易犯的错误是站在自己角度思考和划分故事，背离用户故事初衷。
- **Epic 特点**：由许多较大的不确定需求组成，优先级较低，不能直接完成迭代开发，需先划分成较小的真正用户故事；因包含太多模糊需求常混杂多个特性（特性是对某特定用户有交互价值的一组同类需求）。
- 敏捷分解过程：定义项目所有史诗 → 针对每个史诗确定包含的特性及分解出的故事 → 针对每个故事开发必要的任务。

## 5.5 MED 项目的工作分解案例分析

- 「医疗信息商务平台」项目：根据需求规约分析，采用**图表（组织结构图）形式**进行工作分解，WBS 可随系统完善不断完善。
- 主要分解模块（F 编号为功能）：
  - **F1 用户**：F1.1 注册（个人注册、组织注册、协会/学会注册）、F1.2 管理（用户信息、用户权限、统计分析）
  - **F2 产品信息**：F2.1 编辑、F2.2 浏览、F2.3 查找
  - **F3 网上交易**：F3.1 售前、F3.2 售中、F3.3 售后（询价、接收订单、查看采购记录）
  - **F4 分类广告**：F4.1 与产品有关、F4.2 与产品无关、F4.3 匹配、F4.4 招标
  - **F5 协会/学会**：F5.1 编辑、F5.2 浏览、F5.3 管理
  - **F6 医院管理**：F6.1 编辑、F6.2 浏览、F6.3 检索、F6.4 管理
  - **F7 E-mail 管理**、**F8 Chat 管理**、**F9 护士排班表**、**F10 联机帮助**

## 5.6 MSHD 项目的工作分解案例分析

针对 MSHD 项目需求，将项目划分为 **5 个大用户故事（epics）**，每个 epics 再分解为不同的用户故事：

| Epic（大用户故事） | 分解出的用户故事 |
| --- | --- |
| 用户管理 | 用户登录、用户注册、账户管理（3 个） |
| 数据输入 | 参数配置、基于 JSON 格式的数据获取、基于 XML 格式的数据获取、人工数据获取（4 个） |
| 数据编码 | 数据来源编码、灾情数据编码、基本震情编码（3 个） |
| 数据管理 | 数据基本管理、灾情动态管理（备份）、基于地图的展示、统计分析（4 个） |
| 数据输出 | 数据请求管理、数据发送管理（2 个） |

- 图中编号（① ② ③）反映用户故事的**优先级**，这些优先级可对应到相应的迭代开发中。

## 传统 vs 敏捷工作分解对比

| 维度 | 传统工作分解 | 敏捷工作分解 |
| --- | --- | --- |
| 对象 | 全部需求的任务 | 基于需求的故事（story） |
| 过程 | 一次性分解全部工作 | 渐进式分解过程 |
| 结果 | WBS（可交付成果树形结构） | epic → feature → user story → task |
| 典型方法 | 模板参照、类比、自顶向下、自底向上 | 按工作流/业务规则/操作/功能非功能需求拆分故事 |

## 本章小结

- 工作分解是对需求的进一步细化、确定项目所有任务范围的过程，结果是 WBS；WBS 是面向可交付成果的分级树形结构，界定「包括且仅包括」的项目范围。
- **工作包**是 WBS 最低层次可交付成果，由唯一主体负责；可进一步分解为活动，所有工作包之和等于项目范围。
- WBS 三种表达形式：提纲式（清单式）、组织结构图式（图表式）、其他层级结构形式；WBS 字典汇集各工作要素的阐述。
- 传统分解方法：**模板参照、类比、自顶向下、自底向上**；自顶向下是最好方法，自底向上适合崭新项目。
- 分解结果验证：低层组件须是上层可交付成果的**必要且充分**工作；推荐至少拆分到一周工作量（40 小时）、不宜超过 7 层。
- 敏捷分解：以用户故事为单位，**epic → feature → user story → task** 渐进式分解；目标是缩小故事并剥离低价值部分。
- 案例：MED（图表式 WBS）、MSHD（5 个 epic 的优先级用户故事分解）。
