# 第8章 软件项目质量计划

> 本章讲「如何保证质量」：软件质量 = 满足明确与隐含需求的程度。质量管理的三大过程是**质量计划、质量保证、质量控制**，核心心法是「质量是开发出来的，不是检查出来的」，预防重于检验。

## 核心概念速览

| 概念 | 一句话 |
| --- | --- |
| 软件质量 | 与软件产品满足规定的和隐含的需求能力有关的特征或特性的全体 |
| 质量与等级 | 等级是技术分级，低等级≠低质量、高等级≠高质量 |
| 质量成本（COQ） | 产品第一次工作不正常而衍生的附加花费，含预防成本 + 缺陷成本 |
| 质量保证（QA） | 证明项目达到质量标准的有计划、有组织的活动，验证「是否做得正确」 |
| 质量控制（QC） | 检验产品与质量标准是否相符并纠正缺陷，检查「是否正确地做」 |
| 质量模型 | 用层次化特征描述软件质量的模型（Boehm、McCall、ISO/IEC 9126/25010） |
| 质量内建 | 在开发早期阶段就开始关注质量，与 DevOps 相辅相成 |
| 质量外延 | 测试左移 + 右移，体现为结对编程、TDD、ATDD 等敏捷实践 |
| 质量计划 | 确定项目质量标准及满足标准的方法与安排，质量是计划出来的 |

## 8.1 软件质量概述

开篇用两个事故说明质量的重要性：1981 年因程序改变导致 1/67s 时间偏差使航天飞机 5 台计算机不同步、发射失败；1986 年 Therac 25 机器因软件问题忽略数据校验、泄漏致命辐射致 2 名病人死亡。

### 8.1.1 质量定义

ANSI/IEEE Std 729—1983 定义软件质量为「与软件产品满足规定的和隐含的需求能力有关的特征或特性的全体」。软件质量反映 3 方面问题：

1. **软件需求**是度量质量的基础，不满足需求就不具备质量。
2. 不遵循标准定义的开发规则，质量得不到保证。
3. 只满足明确定义的需求、未满足**隐含需求**，质量也得不到保证。

> 质量 = 满足要求的程度 = 符合规定的要求 + 满足顾客的需求。质量管理是项目管理的最高统一，其目标是满足项目干系人（以用户为中心）的需求。

### 8.1.2 质量与等级

- **等级**是对具有相同功能的实体按不同技术特征进行分类/分级；**质量**是满足功能要求的特征总和。
- **低等级不代表低质量，高等级也不代表高质量**。质量低通常是问题，级别低可能不是。
- 需区分三个概念：**质量标准**（微观、侧重细节特征）、**质量策略**（宏观、侧重指导思想）、**质量责任**（管理层责任、最终责任、首要责任等，需明确细化，否则「人人有责、人人不负责」）。

### 8.1.3 软件质量成本

质量成本（Cost Of Quality，COQ）是产品第一次工作不正常而衍生的附加花费。按 Crosby 定义，「符合需求」的代价（第一次做对）最经济，「不符合需求」的代价是补救（额外时间、金钱、精力）。

- **预防成本（一致性成本）**：为确保质量进行预防工作的费用。
  - **评估费用**：为检测缺陷所衍生的成本（质量审计、测试等）。
  - **预防费用**：为预防失败所衍生的成本（用户满意确定、过程评审、改进等）。
- **缺陷成本（非一致性成本）**：为修复缺陷工作的费用。
  - **内部费用**：未发布软件的返工费用（缺陷标记、返工、重新测试等）。
  - **外部费用**：已发布但不符要求的费用（技术支持、修正、索赔等）。

> 预防重于事后检查：**预防成本应大于缺陷成本**。
> **质检过失比 = 预防成本 / 缺陷成本**，值**大于 2** 是努力达到的程度；若**小于 1**，后期测试阶段会发现很多错误。

质量形成于开发过程中，而非事后检查、测试、把关。**一个高质量的产品是开发出来的**，后期测试不能真正提高质量，只能靠前期质量预防与检测（代码走查、单元测试、对等评审）。

### 8.1.4 质量管理对象

软件质量管理的对象**既包括软件产品的质量，也包括软件过程的质量**。质量形成于开发过程而非事后检查，因此质量活动应更多安排在开发过程中，而不是开发后的测试检查。

## 8.2 软件质量模型

软件质量是软件满足需求规约中**明确说明**（合同、标准、规范中明确规定）以及**隐含需求**（不言而喻、不需规定）的程度。常见 4 个质量模型：

| 模型 | 提出年份 | 特点 |
| --- | --- | --- |
| Boehm 质量模型 | 1976 | 首次提出层次模型，60 个质量度量公式 |
| McCall 质量模型 | 1979 | 3 层结构（要素→准则→度量），质量要素 11 个 |
| ISO/IEC 9126 质量模型 | 1993 | 提出内部/外部质量度量概念 |
| ISO/IEC 25010 质量模型 | 2002 | 进一步演化的质量模型 |

> 1985 年 ISO 依据 McCall 模型提出 3 层软件质量度量模型；ISO/IEC 9126 为软件质量评价奠定基础。

### 8.2.1 Boehm 质量模型

从 3 个方面考虑软件质量：**可使用性、可维护性、可移植性**。将质量分解为若干层次，最底层引入数量化指标（如正确性、完备性、健壮性、一致性、可靠性、效率、可测试性、可理解性、可修改性、可扩充性、设备独立性、自包含性等）。

### 8.2.2 McCall 质量模型

列出的质量因素反映用户 3 种倾向（先能运行、再可维护、后可移植）：

| 倾向 | 质量因素 |
| --- | --- |
| 产品运行 | 正确性、可靠性、效率、可使用性、完整性 |
| 产品修正 | 可维护性、可测试性、灵活性 |
| 产品转移 | 可移植性、可复用性、互连性 |

由于对质量因素直接度量很困难甚至不可能，McCall 定义**评价准则**，通过分级（0 最低～10 最高）来估计软件质量特征值。

### 8.2.3 ISO/IEC 9126 质量模型

按 GB/T 8566—2001，软件质量框架是「**质量特征–质量子特征–度量因子**」三层结构：

- **上层·质量特征**（面向管理）：功能性、可靠性、效率、易使用性、可维护性、可移植性、使用质量。其中「质量要素」分两类——技术上对整体质量影响最大的特征、商业上客户最关心能成为卖点的特征。
- **中层·质量子特征**：上层特征的细化，是管理人员与技术人员关于质量问题的沟通渠道。
- **下层·度量因子**：定量化、可直接测量或统计，为得到质量子特征值提供依据。

**三模型对比**：
- McCall 最大贡献是建立质量特征与度量项间关系，但部分度量项是主观判断，且只考虑单一产品形态，不利于早期发现缺陷。
- Boehm 与 McCall 相似，差别在特征种类，且 Boehm 还包含 McCall 没有的硬件领域质量要素。
- ISO/IEC 9126 贡献在于把质量特征分为外部特征和内部特征，考虑了不同生命周期阶段的不同形态，但未清楚给出度量方法。

## 8.3 质量管理活动

时间、成本、质量三者需找到均满意的模式。质量管理的关键是**预防重于检查，事前计划质量而非事后检查**。质量管理主要是监控项目交付物和执行过程，确保符合标准、不合格项按正确方法排除。

**三大过程**：
- **质量计划**：确定与项目相关的质量标准以及如何满足这些标准。
- **质量保证**：定期评估项目整体性能以确保满足质量标准。
- **质量控制**：控制特定项目状态保证按质量标准完成，并确定质量改进方法。

**代表性质量学派**：

| 学派 | 核心思想 |
| --- | --- |
| 戴明 | 目标不变、持续改善、知识积累，预防胜于检验 |
| 朱兰 | 适用性——符合或超过相关人及客户的期望 |
| 克鲁斯比 | 质量=符合预先要求，源于预防，执行标准是**零缺陷**，用非一致成本衡量 |
| 田口玄一 | 统计技术质量管理，用**损失函数**决定未满足目标产品的成本 |

> **全面质量管理（TQM）**：通过全体员工参与，改进流程、产品、服务和公司文化，在百分之百时间内生产百分之百的合格产品。

### 8.3.1 质量保证（QA）

为提供信用、证明项目达到质量标准而开展的有计划、有组织的工作，贯穿整个项目生命周期，通过评估、检查、改进向管理者和顾客提供信任。

- 主要方法是**质量审计**：对过程或产品的结构化独立评估，可事先规划或临时决定。
- 质量审计分**软件过程审计**（需求/设计/编码/测试过程审计）与**软件产品审计**（需求规约/设计说明书/代码/测试报告审计）。
- 核心作用：保证软件开发透明，提供项目过程和产品的可视化。
- 表达为 **"Is it done right?"（完成得是否正确？）**——完成后看是否正确，本身不直接提高当前版本质量，但间接提高，属**管理职能**。开发高质量产品是开发组的责任，QA 人员职责是规划和维护质量过程。

### 8.3.2 质量控制（QC）

确定项目结果与质量标准是否相符、确定不符原因和消除方法、及时纠正缺陷的过程。主要目的是**发现和消除软件缺陷**。

- 缺陷任何阶段都可能引入，潜在缺陷越大，消除费用越高 → 每个可能引入缺陷的阶段完成后都开展质量控制活动。
- 方法：技术评审、走查、测试、返工。评审是面向人的过程，测试是运行软件以发现缺陷。
- 表达为 **"Is it right done?"（是否正确完成？）**——项目完成前检查质量，直接提高产品质量，一般由开发人员实施，属**检查职能**。

### 8.3.3 质量保证与质量控制的关系

| 维度 | 质量保证（QA） | 质量控制（QC） |
| --- | --- | --- |
| 焦点 | 过程与产品提交后的质量监管 | 产品推出前的质量把关 |
| 对象 | 一般的、普遍性的问题 / 过程 | 具体的产品或活动 |
| 职能 | 管理职能 | 检查职能 |
| 作用 | 总体保障、促进改善、间接提高 | 具体环节把关、直接提高 |

> 以航天飞机发射为例：倒计时中，QC 检测各部分是否运行正常（对本次发射有直接意义）；QA 只提交质量保证报告（对本次无直接意义，但对将来发射有意义）。

## 8.4 敏捷项目质量管理

敏捷项目中，质量活动由**所有团队成员在全生命周期持续执行**（瀑布式则由特定成员在特定时点执行）。特征：

- **全程质量审查**：贯穿始终的质量活动，通过结对编程、TDD、持续集成、持续测试实现。
- **尽早发现问题**：多版本频繁提交可尽早发现不一致和质量问题，整体变更成本较低。
- **不断评估改进**：迭代回顾会议中审核过程方法有效性并改进，寻找问题根本原因。

敏捷质量管理通过**质量内建**和**质量外延**实现。

### 8.4.1 质量内建

核心是在开发生命周期早期就关注质量（需求分析、设计评审、代码开发等环节）。统计表明，**需求阶段发现问题的修复成本仅为生产阶段的 1/100**。

质量内建与 DevOps 相辅相成，主要实践：

| 实践 | 效果 |
| --- | --- |
| 持续集成 | 每次合并触发自动化构建与测试，减少 25% 以上集成问题、提高 20% 交付速度 |
| 代码审查 | 减少 15%~20% 缺陷率，促进知识共享 |
| 版本控制和分支策略 | 提高 30% 代码稳定性、可追溯性 |
| 集成测试和系统测试 | 保障测试覆盖率至 80% |
| 环境一致性 | 环境不一致问题减少 60% 以上 |
| 自动化测试框架 | 提高 50% 测试效率、减少人工错误 |

### 8.4.2 质量内建的作用

- **提升自动化测试**：与 CI/CD 结合，覆盖率提升至 90% 以上，减少 50% 以上手动测试工作量。
- **加速反馈循环**：问题反馈周期从数天缩短至几小时甚至几分钟。
- **促进团队协作**：跨职能团队合作提高问题解决效率高达 60%，加快交付。
- **质量门禁的实施**：各阶段必须满足质量标准才进入下一阶段，缺陷率降低 30% 以上。

### 8.4.3 质量外延

即**测试左移 + 测试右移**，测试活动向前后延伸，体现为敏捷开发实践。

**1. 结对编程**：两人一起编码、互相评审。1999 年犹他州立大学试验（独自工作 13 人 vs 结对 28 人/14 对）：

| 测试用例 | 独自工作 | 结对编程 |
| --- | --- | --- |
| 程序1 | 73.4% | 86.4% |
| 程序2 | 78.1% | 88.6% |
| 程序3 | 70.4% | 87.1% |
| 程序4 | 78.1% | 94.4% |

结论：结对编程用较少时间产出更高质量代码；成员更勤奋、专注、有纪律且持续；团队开发能力提高快，还能**快速知识传递**（知识由团队共享，不怕人员流动）。

**2. 测试驱动开发（TDD）**：先写测试代码再写功能代码，循环添加功能直到完成。JUnit 是实现 TDD 的好框架。

**3. 持续集成与测试**：频繁集成到整体系统再重新测试，强调自动化测试。

**4. 不同层面自动化测试**：单元测试、集成测试、系统测试、冒烟测试、回归测试等；端到端用系统测试、构建模块用单元测试，冒烟测试判断工作产品是否良好。

**5. 验收测试驱动开发（ATDD）**：先与客户讨论验收标准，再创建测试、编写足够代码自动化测试以满足标准。

**6. 迭代评审**：迭代完成后向相关方展示运行情况、得到反馈。

**7. 迭代回顾会议**：评审本迭代过程、确定是否改进。

**8. 重构**：每迭代后逐步完善代码和设计，先完成正常工作再逐步提高质量。

## 8.5 软件项目质量计划

现代质量管理强调：**质量是计划出来的，而不是检查出来的**。软件完成后就无法再提高质量，好的质量保证始于好的设计并在好的编程过程中延续；保证软件几乎无错误的最好办法是在**前期**解决缺陷。

### 8.5.1 质量计划

确定项目应达到的质量标准及满足标准的计划安排和方法，**合适的质量标准是关键**。质量计划依据公司质量方针、产品描述及标准制定实施策略，为质量小组成员提供指南。

- **质量计划首先是确定项目质量目标**，根据 WBS 分解到每个工作包、落实到每个小组成员，并明确各工作包输入/输出及质量责任人。
- 可建立**项目质量模型**确定目标/标准。质量管理的对象是**产品和过程**。

**2023 年中国软件行业缺陷率基准**：

| 测试阶段缺陷率（缺陷数/功能点） | P10 | P25 | P50 | P75 | P90 |
| --- | --- | --- | --- | --- | --- |
| 值 | 0.03 | 0.05 | 0.16 | 0.72 | 1.15 |

| 交付阶段缺陷率（缺陷数/千功能点） | P10 | P25 | P50 | P75 | P90 |
| --- | --- | --- | --- | --- | --- |
| 值 | 2.01 | 3.58 | 13.16 | 38.23 | 67.56 |

**项目质量模型案例**（总分 100 分，质量目标 85 分以上，执行中跟踪分数走势）：

| 质量特征 | 权重 | 质量子特征 | 权重 |
| --- | --- | --- | --- |
| 功能性 | 44.44% | 完整性 / 准确性 / 安全性 | 29.7% / 53.9% / 16.4% |
| 可靠性 | 22.22% | 健壮性 / 容错性 / 易恢复性 | 66.6% / 16.7% / 16.7% |
| 效率 | 11.11% | 时间特性 / 资源特性 | 50% / 50% |
| 易使用性 | 11.11% | 易理解性 / 用户文档问题 / 易操作性 | 53.9% / 16.4% / 19.7% |
| 标准 | 11.11% | 行业标准 / 企业标准 | 50% / 50% |

### 8.5.2 质量计划的方法

1. **试验设计**：统计学方法，对特定要素设计不同组合方案，寻求优化方案，确定导致问题的主要变量。
2. **基准对照**：利用其他项目实施情况作为当前项目性能衡量标准，寻找最佳实践。
3. **质量成本分析**：分析为满足质量要求和解决不合格项付出的所有成本。
4. **测试与检查的规划**：决定如何测试/检查产品，如 α 测试、β 测试。
5. **各种数据分析图示**：
   - **因果分析图（鱼刺图）**：分解人员、设备、参考资料、方法、环境等原因，制定预防措施。
   - **流程图**：显示系统成分关系，预测质量问题发生点。
   - **思维导图**：基于单个质量概念可视化组织信息，快速收集质量要求、制约因素、依赖关系。

> 质量计划中还要确定有效的质量管理体系，明确质量监理人员及各层权限。**戴明环（PDCA 循环）**（计划–执行–检查–措施）是有效管理工具，须把质量环各环节落实到责任单位。

### 8.5.3 质量计划的编写

质量计划说明项目管理小组如何具体执行质量策略，可作为质量工作指南。应满足：质量目标与特性要求、质量活动与控制程序、各阶段职责/权限/交流方式/资源分配、控制手段与验证方法、质量记录。

**质量指标（质量属性）**：

| 指标 | 说明 |
| --- | --- |
| 可用度 | 任一随机时刻软件处于可使用状态的概率 |
| 初期故障率 | 初期故障期（交付后 3 个月内）单位时间故障数，以每 100 小时计 |
| 偶然故障率 | 偶然故障期（交付后 4 个月以后）单位时间故障数，以每 1000 小时计 |
| 平均失效前时间（MTTF） | 失效前正常工作的平均统计时间 |
| 平均失效间隔时间（MTBF） | 相继两次失效间正常工作的平均时间；民用软件约 1000 小时，高可靠软件 1000~10 000 小时 |
| 缺陷密度（FD） | 每千行源代码缺陷数；开发阶段平均 50~60 个，交付后 15~18 个 |
| 平均失效恢复时间（MTTR） | 失效后恢复正常工作所需的平均统计时间 |

**质量计划要素与形式**：
- 要素：明确质量保证（审计、评审软件过程/活动/产品）与质量控制（代码走查、单元/集成/系统测试）的活动安排；明确质量管理组织职责，QA 人员应有特殊上报渠道（慎用），**项目经理是质量的最终责任承担者**。
- 形式：无统一标准，一是将质量活动体现在进度计划活动中（如表 8-5 总体设计/详细设计增加评审活动），二是文档形式（质量保证计划模板）。

## 8.6 MED 项目的质量计划案例分析

「医疗信息商务平台」质量保证计划文档（质量经理参与制订），目录结构：导言、质量目标、质量管理职责、质量管理流程、质量活动（过程审核、产品审计）。

**质量目标**：客观核实实施行动与产品遵从需求/过程/标准，提前发现排除问题缺陷，具体包括监控开发过程保证产品质量、保证符合标准规程、保证不合理问题得到处理、确保计划/标准适合项目组需要。

**质量管理职责（5 角色）**：项目质量管理员、PMO 质量管理专员、各小组组长或项目经理、项目配置管理员、PMO 总体管理组。

**质量管理流程**（含质量计划、质量评估、质量改善、质量周报）：
- **质量计划**：依据进度计划确定要评审的活动和审计的产品，确定评审审计方式与资源，根据项目情况与历史经验确定 QA 工作重点。
- **质量评估**：确定各阶段评估指标，执行 QA 活动，记录不符合问题并判定问题等级。
- **质量改善**：QA 向负责人报告不符合问题、协商解决措施，重大问题报 PMO 总体管理组批准，跟踪直至解决，定期统计分析。
- **质量周报**：统计本周/上周遗留不符合问题，记录工作内容、问题及解决措施、经验建议，制订下周计划。

**质量活动**：项目质量管理员按计划或事件触发定期进行**过程审计**和**产品审计**，跟踪监控直至问题解决。

## 8.7 MSHD 项目的质量计划案例分析

**质量目标**：确保系统功能满足用户需求，具备运行稳定性、数据准确性；符合行业标准与用户需求，系统响应时间在可接受范围，**数据准确性高于 95%**。

**质量保证（QA）活动**：
- 文档审计：需求/设计/代码/测试等关键文档专人负责，修改后审计，并用 AI 辅助工具检测完整性和格式规范。
- 过程审计：定期审计需求分析、设计、编码全流程，确保遵循既定流程和标准。
- 代码审计：ESLint、Husky 等工具配置，代码在 GitHub 提交时自动审计。

**质量控制（QC）活动**：
- 代码走查：结对编程成员互相走查，用 AI 工具自动识别潜在问题和不规范实践。
- 测试活动：执行单元测试、集成测试，AI 辅助生成测试用例并监控覆盖率。

**体现质量控制的敏捷实践**：结对编程（提高质量、促进知识共享）、TDD（先写测试用例如前端测试 JSON）、CI/CD（GitHub Action 自动化构建部署、持续集成测试）。

## 本章小结

- **质量定义**：软件满足明确说明或隐含需求的程度；用户满意度是重要要素；质量与等级分离，低等级≠低质量。
- **质量成本**：预防成本（一致性）+ 缺陷成本（非一致性），质检过失比 = 预防成本/缺陷成本，大于 2 为努力目标，预防重于检查。
- **质量模型**：Boehm（1976）、McCall（1979，产品运行/修正/转移 3 倾向 11 要素）、ISO/IEC 9126（质量特征–质量子特征–度量因子三层）、ISO/IEC 25010。
- **三大过程**：质量计划（定标准）、质量保证 QA（"Is it done right?" 管理职能、审计）、质量控制 QC（"Is it right done?" 检查职能、发现消除缺陷）。
- **敏捷质量**：全程质量审查 + 尽早发现 + 不断改进；质量内建（与 DevOps 结合）与质量外延（测试左移右移：结对编程、TDD、ATDD、CI/CD、迭代评审/回顾、重构）。
- **质量计划**：质量是计划出来的；方法有试验设计、基准对照、质量成本分析、因果分析图等；指标含可用度、初期/偶然故障率、MTTF/MTBF/MTTR、缺陷密度 FD。
- **案例**：MED 采用质量保证计划文档（5 角色职责 + 计划/评估/改善/周报流程 + 过程/产品审计）；MSHD 采用 QA（文档/过程/代码审计）+ QC（代码走查/测试）+ 敏捷实践，数据准确性高于 95%。
