# 第13章 项目跟踪与度量

> 本章讲「如何用数据掌控项目」：项目执行控制是一个**集成**过程，核心是通过跟踪采集项目性能数据（进度、成本、质量、缺陷等）、度量分析偏差，及时纠正、必要时修订计划，从而保证项目总体目标的达成。

## 核心概念速览

| 概念 | 一句话 |
| --- | --- |
| 项目集成管理 | 由项目经理负责，协调各知识域过程、平衡目标冲突，从全局保证项目成功的管理 |
| 项目四要素 | 范围（S）、质量（Q）、进度（T）、成本（C），相互制约平衡 |
| 项目跟踪 | 按计划规定的频率采集进度、成本、质量、风险等性能数据，监控项目实际状态 |
| 软件项目度量 | 依据项目目标建立度量需求，采集分析数据以发现问题、量化改进 |
| GQM | 目标（Goal）→ 问题（Question）→ 度量（Metric），根据目标设计度量指标 |
| 燃尽图 | 反映剩余工作量/时间随时间递减的趋势图，用于进度监控 |
| 效率竖井 | 各部门局部优化导致整体效率低下的现象 |
| 流动效率 | 用户价值在系统中的流动速度（交付周期时长、等待时间占比） |

## 13.1 项目执行控制过程

系统是一个整体，元素彼此联系、相互影响，软件项目管理也须**以系统方式**进行集成控制。项目集成管理由**项目经理**负责，整合所有知识领域的成果，掌握项目总体情况。

### 13.1.1 项目目标的集成

- 项目集成管理的目标是对项目中不同组成元素进行**正确高效的协调**，而**不是**各元素的简单相加。
- 项目经理的本职工作是整合，须协调各方面的人员、计划和工作，在相互影响的目标和方案中做出**权衡**，满足甚至超出干系人的需求和期望。
- **各目标相互制约**：范围、成本、进度、质量等目标相互制约（图13-2），其中：
  - **进度目标与成本目标关系最密切**，几乎成对立关系——缩短进度常靠增加成本实现，降低成本常以牺牲工期为代价。
  - 工期、成本与质量关系密切——盲目缩短工期导致质量下降；质量出问题返工会延长工期；压缩成本削减必要质量环节导致质量下降。
- 每个项目须平衡**功能、人员、预算、进度、质量**，识别项目的**驱动、约束条件和自由程度**。
- 所有计划（进度、成本、质量、风险……）都**不是孤立的**，应以整体思想为指导，建立折中计划；集成计划具有**综合性、全局性、内外兼顾性**。

### 13.1.2 平衡项目四要素的关系

范围（S）、质量（Q）、进度（T）、成本（C）是软件项目管理的 4 个要素：

| 要素 | 含义 |
| --- | --- |
| 范围（S） | 定义「做什么」 |
| 成本（C） | 决定项目的投入（人、财、物） |
| 进度（T） | 定义项目的交付日期 |
| 质量（Q） | 定义系统好到什么程度 |

**成本函数关系**：可以设定成本是范围、质量、进度的函数：

$$C = F(S, Q, T)$$

- S 与 C 呈一定**正比**关系；
- Q 与 C 呈一定**正比**关系；
- T 与 C 呈一定**反比**关系。

**需求范围很大、资源少、工期短、质量要求高**的组合是不现实的，只能增加投资或延期。

**双方关注点**：
- 客户最关注**范围、质量、进度**（合同确定后一般不关心成本）；项目经理最关注**成本、范围、进度**。
- 双方共同关注的是**范围和进度**；进度几乎不能改变；范围是双方争论焦点。因此项目经理**无论如何都要处理好进度管理**，必须就进度与客户达成一致。

**成本、进度确定后如何提高满意度**：只能通过**减少范围或降低质量**来解决，主要依据客户情况——客户重范围则降质量、重质量则减范围、两者都重则同时降低，直到用户基本能忍受为止。

### 13.1.3 项目集成计划的内容

> 项目集成计划 = 运用整体和综合平衡的方法，集成各专项计划生成的、用于指导项目实施和管理的**整体性、综合性、全局性、协调统一**的正式批准文件。

- 包含重要的**基准计划**（范围基准、进度基准、成本基准、质量基准等），基准计划须经变更程序才能修改。
- 三大核心子计划（范围、进度、成本）是计划编制的基础，质量计划也是核心子计划；配置管理、沟通、人力、干系人、风险、合同等子计划是编制原材料。集成计划**不是简单堆砌**，而是不断反馈、校正各子计划。

**项目计划书 13 项内容**：

1. 确定项目概貌（以合同/招投标文件或可行性报告为依据）
2. 确定项目团队（组织结构、人员分工）
3. 明确项目团队内外的协作沟通（用户沟通、周报月报、例会）
4. 规划开发环境和规范（工具、环境、技术规范）
5. 项目范围说明（成果核对清单、WBS）
6. 编制项目进度计划（交付成果、任务时间、人力资源、角色职责）
7. 项目成本计划（资源计划、费用估算、费用预算）
8. 项目质量计划（质量保证与控制活动）
9. 项目沟通计划（信息交流内容、方式、频率）
10. 风险计划（识别、评估、应对策略）
11. 项目合同计划（外包采购的进度监控与质量控制）
12. 配置管理计划（配置项、基线、变更控制）
13. 制订其他辅助工作计划（培训、支持、验收计划）

**集成计划目录示例**：导言 → 项目概述 → 任务范围 → 目标 → 实施策略 → 组织结构 → 计划结构 → 生存期 → 管理对象 → 风险分析 → 估算 → 时间计划 → 关键资源计划 → 设施工具计划 → 质量管理计划 → 配置管理计划 → 管理评审 → 度量计划 → 沟通计划。

### 13.1.4 项目集成计划的执行控制

项目控制过程目的是**保证项目目标达成**，进度、成本、质量控制是重要监控内容；需不断收集信息、度量分析、发布运行状况、分析趋势，并**管理好变更控制系统**。

**执行控制流程**（图13-3）：设立基准计划 → 监督执行 → 从项目数据库采集性能与变更信息 → 与计划比较（进度、成本、质量）→ 判断偏差 → 标识偏差、分析影响、提出纠正措施、评审方案 → 必要时按变更控制流程修改计划并通知相关人员。

**基本步骤（5 步）**：

1. **建立计划标准**——项目正确完成应达到的目标，过程控制的依据。
2. **观察项目的性能**——建立监控报告体系，记录实施情况。
3. **测量和分析结果**——实际结果与计划比较，协调矛盾、调配资源、实现动态平衡。
4. **采取必要措施**——有偏差则纠正，必要时修改计划，可借助项目管理软件。
5. **做好计划修订工作，控制反馈**——内外部条件大变化时修订计划，并通知相关人员。

**控制原则**：系统管理、提高透明度、管理制度化、令行禁止、统一调配、合理适度授权；应确定范围、成本、进度、质量等控制标准（如设置控制线）。

## 13.2 项目跟踪过程

项目执行控制的前提是**数据采集**；项目跟踪是在生存期内按计划规定的**跟踪频率**和步骤，对项目管理、技术开发、质量保证活动采集数据（进度、资源、成本、性能、质量等），用于分析计划执行情况。

**跟踪过程定义**（图13-4）：

| 项 | 内容 |
| --- | --- |
| 参与角色 | R1 项目管理者；R2 项目助理 |
| 进入条件 | E1 项目计划被正式批准 |
| 输入 | I1 项目计划书 |
| 活动 | A1~A10（见下） |
| 输出 | O1 相关数据记录表格 |

**活动 A1~A10（均由项目助理负责）**：确定跟踪频率与记录方式 → 记录实际任务完成情况（进度/完成时间）→ 记录完成任务所花人力与工时 → 计算实际人力成本和实际任务规模 → 记录除人力外的其他成本 → 记录关键资源使用 → 记录风险发生及处理对策 → 按期按任务性质统计时间分配 → 填写培训实施记录并收集教材 → 将数据提交配置管理者入库。

**输出表格**：进度记录数据、关键资源使用记录表、风险处理记录表、资源成本统计表、任务性质/时间分配表、项目培训实施记录表。

## 13.3 软件项目度量

> 德鲁克：「如果你不能度量它，就无法改进它。」产品开发会产生大量数据，但**数据不是度量**——所有度量都应由项目目标和度量需求驱动。

### 13.3.1 项目度量要素

主要度量要素（5 类）：

1. **项目进度度量**——定期跟踪，及时发现进度偏差，赶工或调整进度计划。
2. **规模和工作量度量**——在需求完成、设计完成、编码完成、内部测试完成、项目结束等节点度量；规模/工作量度量方法应与估算方法一致，并对不同活动、阶段分别度量。
3. **成本度量**——开发中定期或事件驱动度量直接成本；结束后分项度量；可按交付规模与综合单价结算。
4. **质量度量**——难以精确定量，一般由若干专家打分 + 检查表对照评估指标；**缺陷密度**直接影响客户满意度，可有效说明项目完成质量。
5. **人员生产率度量**——生产率是团队生产能力的重要指标，需定期度量分析。

**全行业生产率基准数据**（SSM-BK-202309，单位：人时/功能点）：

| 分位 | P10 | P25 | P50 | P75 | P90 |
| --- | --- | --- | --- | --- | --- |
| 生产率 | 2.06 | 4.15 | 7.14 | 15.38 | 18.92 |

> 缺乏量化管理，项目管理只能处于「混沌」状态。据称只有 **26%** 的 IT 项目成功实现范围、进度、成本目标；采用量化管理后过程变得「可视化」，问题可以「让数字说话」。企业应建立**历史项目数据库、风险数据库**，经验是历史信息的积累。

### 13.3.2 基于 GQM 的度量

**GQM（目标/问题/度量）**用于建立度量活动，也指导软件过程分析与改进；其核心内容是**根据目标设计问题，通过问题设计度量指标**。

**示例**（表13-2）：

| 层级 | 内容 |
| --- | --- |
| 目标（G） | 在 6 个月内将变更请求过程的平均执行时间减少 10% |
| 问题 1 | 变更请求过程执行时间的基线是什么 |
| 度量 1-1 / 1-2 | 改进启动时平均执行时间 / 标准偏差 |
| 问题 2 | 当前变更请求过程的执行时间是多少 |
| 度量 2-1 / 2-2 | 当前平均执行时间 / 标准偏差 |

### 13.3.3 度量技术

- 量化度量技术通过数据表收集分析，包含数学统计分析；量化数据作为过程副产品收集（如缺陷数量/人时 → 缺陷发现率）。
- **质量控制基本工具**：检查表、帕累托图、直方图、散点图、趋势图、控制图、因果图。
- 量化数据可作模拟模型输入，预测过程改进效果；过程度量技术收集定量/定性数据，用于识别与评价过程改进。

## 13.4 项目研发效能度量

### 13.4.1 效率竖井

产品交付需前后职能部门（产品、开发、测试等）和平行部门（前端、后端、算法等）协作。传统方法关注部门独立改进，**过度局部优化反而造成效率竖井**，带来：

- **基于局部信息的工作优先级安排**——部门间相互等待，需求无法顺畅流动（前/中/后台优先级不一致、进度无法对齐）。
- **批量式工作移交**——为最大化单环节效率，批量接受/移交工作（批量集成、批量测试），造成积压等待。
- **跨部门问题处理不及时**——公共环境维护、接口对齐、问题排查等导致需求无法顺畅进展。

> **效率竖井**：站在各自视角每个部门都觉得自己繁忙且「高效」，但站在全局和业务视角系统对外反应迟缓——各个环节繁忙而「高效」，总体效率和响应速度却很低。它是研发效能提升的**普遍症结**。

### 13.4.2 效能改进度量指标

效能改进的关键是**从以局部资源效率为核心，转变为以价值流动效率为核心**，关注用户价值端到端的流动，改进整个系统。

- **资源效率** = 各环节资源利用率和产出（忙闲程度、使用率、代码产出、测试执行速度）。
- **流动效率** = 用户价值在系统中的流动速度（需求从提出到交付的时长越短越好、等待时间占比越小越好）。

**研发效能指标体系（5 组指标）**：

| 指标组 | 细分指标 | 说明 |
| --- | --- | --- |
| 持续发布能力 | 发布频率 | 单位时间内的有效发布次数 |
| | 发布前置时间（变更前置时间） | 从代码提交到功能上线的时间 |
| 需求响应周期 | 交付周期时间 | 从确认需求到需求上线的平均时长（含业务/开发/运营） |
| | 开发周期时间 | 从开发团队理解需求到可上线的平均时长 |
| 交付吞吐率 | 单位时间交付需求数量 | 强调单团队需求吞吐率前后对比，反映趋势 |
| 交付过程质量 | 缺陷创建和修复时间分布 | 缺陷持续、及时地被发现并尽快修复 |
| | 缺陷库存 | 控制开发过程缺陷库存量，接近可发布状态 |
| 对外交付质量 | 单位时间故障（线上问题）数 | 与故障平均解决时长共同决定系统可用性 |
| | 故障平均解决时长 | 同上 |

- **交付过程质量的核心是内建质量**——全过程、全时段的质量，而非依赖特定阶段（测试阶段）或特定时段（项目后期），是持续交付的基础。
- **三方面对应**：持续发布能力 + 需求响应周期 → 流动效率；吞吐率 → 资源效率；交付过程质量 + 对外交付质量 → 质量水平。

## 13.5 MED 项目集成计划与度量案例分析

### 13.5.1 项目集成计划

「医疗信息商务平台」项目集成计划要点：

- **项目概述**：全方位的医疗电子商务平台，向医疗专业人员提供医务管理知识及医疗产品信息，提供 B2B 医疗网络服务及医疗器材采购、供货商间电子商务服务。
- **任务范围**：按功能分（产品目录浏览查询、用户注册登录、网上交易、医务管理、协会学会、分类广告、新闻/About us/帮助、E-mail/Chat Room、多语言服务）；按工作性质分（网页、后台应用服务、数据库、平台内容开发维护）。
- **实施目标**：**5 个月**内完成平台开发；使技术人员熟悉电子商务技术结构；初步建成平台内容管理工具集。
- **风险及应对**：时间、需求、资源三类风险；应对策略——快速成型和增量开发、按优先级开发、独立开发/测试/运行环境、开发人员与应用域专家密切配合、通过企业质量管理体系管理过程；并分**管理策略、技术策略、QA 策略**落实。
- **组织结构**：合同管理者、项目管理者、需求管理组、系统设计组、系统开发组（前台/后台/DB 组）、CM 组、质量保证组、开发环境支持组、项目助理。
- **生存期**：**类 Scrum 敏捷模型**，分 **4 个 Sprint**，每 Sprint 约 **4 周**，各 Sprint 完成后提交可运行版本。
- **规模估算（成本链）**：

| 项目 | 计算 | 结果 |
| --- | --- | --- |
| 内部开发成本 | 396 人天 × 1000 元/天 | 39.6 万元 |
| 开发成本 | 39.6 万元 + 2.4 万元（外包） | 42 万元 |
| 管理成本 | 开发成本 × 10% | 4.2 万元 |
| 直接成本 | 开发成本 + 管理成本 | 46.2 万元 |
| 间接成本 | 直接成本 × 20% | 9.24 万元 |
| **总估算成本** | 直接成本 + 间接成本 | **55.44 万元** |

- **时间计划**：2018 年 7 月 3 日开始，2018 年 12 月 25 日截止；4 个冲刺里程碑（7.9~8.8、8.9~9.7、9.10~10.5、10.8~11.9），远粗近细、滚动计划。
- **度量数据定义**（为估算与管理提供量化指标）：

| 指标 | 计算方法 |
| --- | --- |
| 平均网页工作量 | （时间 × 人力）/ 完成网页数量 |
| 平均 KF 工作量 | （时间 × 人力）/ 完成 KF 数量 |
| 平均数据工作量 | （时间 × 人力）/ 完成产品数据条数 |
| 平均生产率 | 设计：（时间×人力）/设计模块数；开发：（时间×人力）/代码行数（不含自动生成）；测试：（时间×人力）/测试案例数；内容开发：平均数据工作量 |
| 平均故障率 | 测试过程错误数量 / KLOC |

### 13.5.2 项目数据跟踪度量案例分析

## 本章小结

- 项目计划是**集成**的，执行控制过程也是**集成**的：以整体思想为指导、从全局出发、统一协调各专项计划，平衡目标冲突，保证总体目标实现。
- **四要素**范围（S）、质量（Q）、进度（T）、成本（C）相互制约：C = F(S, Q, T)，S、Q 与 C 成正比，T 与 C 成反比；进度是双方共同关注且几乎不可改变的要素。
- 集成计划的执行控制遵循 5 步：**建立标准 → 观察性能 → 测量分析 → 采取措施 → 修订反馈**，并须管理好变更控制系统。
- 数据采集是执行控制的基础，项目跟踪按计划频率采集性能数据；**度量**让量化管理成为可能（进度、规模工作量、成本、质量、生产率五大要素），GQM 是核心度量设计方法。
- 研发效能须从**局部资源效率转向价值流动效率**，用 5 组指标（持续发布能力、需求响应周期、交付吞吐率、交付过程质量、对外交付质量）衡量「持续快速交付价值的能力」，克服效率竖井。
- 敏捷度量常用**燃尽图**监控剩余工作量趋势；MED（类 Scrum、4 个 Sprint、总成本 55.44 万元）与 MSHD（多迭代增量、WBS 责任矩阵）两案例展示了工时、人力成本、缺陷等数据的采集与度量实践。
