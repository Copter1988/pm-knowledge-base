# 第14章 项目核心计划执行控制

> 本章讲「如何把核心计划管住」：围绕项目管理的「金三角」（时间、质量、成本），对范围、进度、成本、质量四大核心计划进行全过程跟踪控制——核心方法是**图解控制法**、**挣值分析法**、**网络图分析法**与敏捷控制手段，以及贯穿始终的**变更控制**。

## 核心概念速览

| 概念 | 一句话 |
| --- | --- |
| 项目金三角 | 时间、质量、成本，须同时满足才能完成项目目标 |
| 范围控制 | 监督范围状态、管理范围基准变更，防止范围蔓延与镀金 |
| 范围蔓延 | 未经控制的产品或项目范围扩大 |
| 挣值分析（已获取价值） | 用成本会计概念综合评估进度、成本绩效的方法 |
| BCWS | 计划完成工作的预算成本（到该日期本应完成多少） |
| BCWP | 已完成工作的预算成本（挣值，到该日期已完成多少） |
| ACWP | 已完成工作的实际成本（到该日期实际花了多少） |
| BAC / TAC | 工作完成的预算成本 / 计划完成时间 |
| 图解控制法 | 综合甘特图、费用曲线、资源图做偏差分析的方法 |
| 贝叶斯网络 | 基于概率分析与图论的不确定性知识表达和推理模型 |
| 质量保证（QA） | 计划、系统的活动，确保项目满足相关标准 |
| 质量控制（QC） | 监控项目结果，确保结果符合质量标准 |

## 14.1 范围计划执行控制

> 通过执行范围计划交付项目成果，同时控制范围变更。

### 14.1.1 项目范围的执行控制

- 范围执行控制是**监督项目和产品的范围状态、管理范围基准变更**的过程，主要作用是在整个项目期间维护范围基准，保证最终提交客户满意的产品。
- 重要工作是**确定偏离范围基准的原因和程度**，并决定是否采取纠正或预防措施。
- 采用的数据分析技术：
  - **偏差分析**——将范围基准与实际结果比较，判断偏差是否在临界值区间内、是否需采取措施。
  - **趋势分析**——审核范围偏差随时间的变化，判断范围管理是改善还是恶化。
- **范围核实和验证**贯穿项目始终，交付物须获得客户或干系人认可；客户的正式接收一般是项目收尾阶段最重要的任务。

### 14.1.2 范围变更控制

- 控制范围，确保所有变更请求、纠正/预防措施都通过**实施集成变更控制过程**处理；变更发生时用变更控制过程管理。
- **范围蔓延**：未经控制的产品或项目范围扩大；需重点防治范围蔓延与**范围镀金**（超出需求做多余功能）。
- 变更不可避免，每个项目都必须强制实施某种形式的变更控制。
- 范围管理主要针对**需求变更管理**。典型流程：提出变更请求 → 评估变更影响 → 经 SCCB（软件变更控制委员会）表决决定接受/部分接受/推迟。
- 需求变更后需重新修改 WBS；需求是重要基线，需求变更管理是重要基线变更管理。
- 需求变更的根源：用户在需求确定阶段往往不能确切定义需求；系统越清晰，用户新要求越多，变更不可避免。
- 管理要点：
  - 不要轻易答应「你给我们做个什么」类要求，否则需求接踵而至，项目可能失控。
  - 树立顾问权威，以专家姿态与客户接触，避免与一般业务人员随意交谈。
  - 进入设计阶段后，向用户说明再提变更的冲击和后果；可设专职需求变更管理人员，或用商业化工具（如 Rational Requisite Pro）做属性描述与状态跟踪。

### 14.1.3 敏捷项目范围管理

- 需求不断变化、风险大、不确定性高的项目，初期无法明确范围，需在项目期间逐步明确。
- 敏捷方法缩短早期定义和协商范围的时间，通过**构建和审查原型、发布多个版本**持续探索和明确需求。
- 将需求列入**未完项**，在整个项目期间被定义和再定义，循序渐进地确定范围。

## 14.2 进度与成本执行控制

> 基本目标：在给定限制条件下，根据跟踪采集的进度、成本、资源数据，与原基准比较分析，保证项目在可控的进度、成本、资源内完成——用最短时间、最小成本、最小风险完成工作。

- 进度控制两个要点：① 进度计划要**现实**；② 要有**纪律**，遵守并达到计划要求。
- 成本控制：落实成本计划，动态比较计划/实际成本、直接/间接成本，找偏差并处理；成本失控很难在预算内完成。
- 常用分析方法：**图解控制法、挣值分析法、网络图分析法**。

### 14.2.1 图解控制法

> 利用时间图、进度图、成本图、资源图等做偏差分析，审查目标绩效与实际绩效的差异。

1. **甘特图**——看出计划起止时间及计划/实际进度对比。
2. **延迟线**——对未按计划进展的活动提供更醒目的可视化指示，越弯曲偏离越大。
3. **时间线**——横轴计划时间、纵轴实际时间，记录目标变更；垂直向下为正常，斜线表示延期，实点表示已完成。
4. **费用曲线图**——累计成本图，计划与实际曲线的高度差即成本偏差，理想情况下两曲线应很相似。
5. **资源图**——显示资源消耗，面积代表某段时间的资源消耗；实际面积大于计划说明投入人工过多。
6. **偏差分析和控制**（以进度为例）：
   - 精确记录任务消耗的实际时间（可用 JIRA 等工具）。
   - 量化任务计划偏差：
     - 持续时间偏差（%）=（实际持续时间−计划持续时间）/计划持续时间×100
     - 进度偏差（%）=（实际结束时间−计划结束时间）/计划持续时间×100
   - 对计划偏差做**根因分析**。

- **图解控制要综合看图**：单图不能说明全貌。例：甘特图每项任务用时都超计划，但实际费用比计划少，看似「省了钱」，实则从资源图看是**未投入足够资源**（人力/设备），这才是进度推迟的真正原因。反之，进度与计划一致但费用高，可能是资源投入远超计划所致。
- **优点**：一目了然确定项目状况，易于向管理层和项目人员报告。
- **缺点**：只提供视觉印象，缺少量化信息（如花费速度、每项工作预算份额、完成百分比）——这是挣值分析法的用武之地。

### 14.2.2 挣值分析法

> 综合范围、进度、成本绩效，对进度、成本状态做绩效评估，既可用于偏差分析，也可用于趋势分析（预测进度延误）。

**原理**：传统做法只做实际数据与计划数据的减法，会因实际完成任务量变化而产生不一致。挣值引入「已获取价值」（BCWP，已完成工作的价值），避免这种偏差。

**模型输入（5 个）**：

| 输入 | 含义 |
| --- | --- |
| BCWS | 计划完成工作的预算成本（到该日期本应完成多少） |
| BCWP | 已完成工作的预算成本，即挣值（到该日期完成多少） |
| ACWP | 已完成工作的实际成本（实际花了多少） |
| BAC | 工作完成的预算成本（项目预计总成本） |
| TAC | 计划完成时间 |

**模型输出（9 个）与判读**：

| 指标 | 公式 | 判读 |
| --- | --- | --- |
| SV（进度差异） | BCWP−BCWS | 0 正常 / 负落后 / 正超前 |
| CV（费用差异） | BCWP−ACWP | 0 正常 / 负超预算 / 正低于预算 |
| SPI（进度效能指标） | BCWP/BCWS×100% | 100% 正常 / <100% 落后 / >100% 超前 |
| CPI（成本效能指标） | BCWP/ACWP×100% | 100% 正常 / <100% 超预算 / >100% 低于预算 |
| EAC（预测完成成本） | BAC/CPI | 按当前花钱速度预测的最终成本 |
| SAC（预测完成时间） | TAC/SPI | 按当前进度效能预测的完工时间 |
| VAC（完成成本差异） | BAC−EAC | 预计最终成本与预算之差 |
| VAT（完成时间差异） | TAC−SAC | 预计完工时间与计划之差 |
| TCPI（未完工成本效能指标） | （BAC−BCWP）/（Goal−ACWP） | >1 需做得比计划好；<1 做得差些也能达标 |

> 研究提示：项目进展到 **20%** 左右 CPI 应趋于稳定，若此时 CPI 不理想应及时采取措施。

**BCWP 的计算规则**：
- **50/50 规则**（最常用）：工作开始但未完成时认定已实现一半价值，全部完成才实现全部价值。
- **0/100 规则**（保守）：未完成不产生价值，完成才实现全部价值。
- **经验加权法**：根据经验确定已完成百分比。

**示例（50/50 规则）**：A、B、C、D 各 100 美元，A、B、C 完成、D 开始未完成，则 BCWP=350 美元；ACWP=700 美元，BCWS=400 美元，BAC=1000 美元 → SV=−50（落后 50）、CV=−350（超支 350）、SPI=87.5%、CPI=50%、EAC=2000 美元、TCPI=（1000−350）/（1000−700）≈2.17（将来 1 美元需创造 2.17 美元价值）。

**例 14-1**：项目由 A、B、C、D 组成，总预算 53 000 元（A=26 000、B=12 000、C=10 000、D=5000）。截至 8 月 31 日：A 全完成、B 过半、C 刚开始、D 未开始。采用 50/50 规则得 BCWS=39 800、ACWP=35 000、BCWP=37 000。则：
- CV = 37 000−35 000 = **2000 元**；SV = 37 000−39 800 = **−2800 元**
- SPI ≈ **93%**（<1 进度落后）；CPI ≈ **106%**（>1 费用节省）
- EAC = BAC/CPI ≈ **50 000 元**；VAC = 53 000−50 000 = **3000 元**

> 注意：BCWP 应依据任务**总预算**（用 50/50 规则）计算，而不是依据表 14-1 中「截至 8 月 31 日」的 BCWS 值。

**例 14-2**（经验加权规则，人员成本 500 元/人天）：BAC=31 人天，第三周 BCWS=7、BCWP=6.5、ACWP=9 人天：
- SV = −0.5 人天；SPI ≈ 92.9%；CV = −2.5 人天（超预算 1250 元）；CPI ≈ 72.2%（超预算 27.8%）
- EAC ≈ 43 人天；VAC = −12 人天（超预算 6000 元）；SAC = 10 周/SPI ≈ 10.8 周（推迟约 0.8 周）
- 结论：应分析「为何多花工作量」——是否非全职影响效率、是否任务不熟悉、是否计划不科学，找出原因解决或修正计划。

### 14.2.3 网络图分析法

> 利用网络图描述任务进度与结构关系，优化控制进度。本章重点介绍**贝叶斯网络**对项目进展的控制。

- 软件项目高度不可预知，贝叶斯网络解决不确定知识推理，可随时改进结构和参数、吸收新信息。
- **贝叶斯网络**：基于概率分析和图论的不确定性知识表达/推理模型，是有向无环图（DAG，1985 年 Judea Pearl 提出）。节点表示随机变量，箭头表示条件依赖，圈表示随机变量。
- **贝叶斯定理**：P(A|B) = P(B|A)·P(A) / P(B)。
  - 条件概率 P(A|B)：在 B 已发生条件下 A 的概率。
  - 联合概率 P(A∩B) 或 P(A,B)：两事件共同发生的概率。
  - 边缘概率（先验概率）：通过边缘化（求和/积分）消去不需要的事件得到。
  - 后验概率 P(A|B)：B 发生后对 A 概率的重新评估。
- 若节点 X 的联合概率可表示为各节点在其父节点条件下的条件概率之积 p(X)=∏ p(xᵢ|pa(i))，则称 X 为相对 DAG G 的贝叶斯网络；任意随机变量的联合概率可由各自局部条件概率分布相乘得出。

**基于贝叶斯网络的进度偏差预测六步**：
1. **建立项目网络图**——监控实际进展，分析偏差原因。
2. **建立贝叶斯网络**——无现成规则，靠专家经验，对每个活动构造网络，明确各节点状态、属性值与条件概率（如「编码」活动含 12 个因素：coding_process_quality、coding_team_quality、coding_complexity、project_size、programmer_experience、team_size、process_maturity、requirement_volatility、stuff_turnover_rate、design_complexity、coding_method、estimation_accuracy）。
3. **数据处理**——因连续贝叶斯算法需高斯分布，选离散贝叶斯学习算法；将变量值归一化/离散化到区间 [0,1]，每个因素划分 3 个状态（H/M/L，如编码进度偏差划分为「<10%」「10%~20%」「>20%」）。
4. **贝叶斯模型学习**——选择结构学习算法与条件概率表，先验概率由专家经验确定。
5. **贝叶斯网络更新**——每次新数据输入网络更新节点状态，建立数据库定期更新、周期性考核进度。
6. **分析原因**——用敏感性分析（如计算熵值）找出最关键因素。例：熵减最高的是 coding_process_quality（0.04435，偏差 3.53），对编码进度偏差影响最大，应从编码过程质量入手减少延迟。

### 14.2.4 敏捷项目进度与成本控制

**敏捷进度控制要点**：比较上一时间周期已交付验收的工作量与估算值、实施回顾性审查、对未完项重新排序、确定迭代可交付速度、判断并管理进度变更；外包时定期向承包商了解里程碑状态。

**衡量指标**：敏捷以**交付价值**（完成的工作）而非预测型指标（完成百分比）衡量进展；团队能力稳定后才能较好预测未来几周。
- **迭代速率（Velocity）**：一个迭代周期内交付的故事个数，反映团队生产能力，需几次迭代才能达到稳定速度。
- 定量指标之外还收集定性指标（业务满意度、团队士气等）。
- 「得寸进尺」式期望：团队生产能力越大，上层和客户期望越高，管理者应适当控制期望值，避免期望提升快于生产力提升。

**1. 基于迭代的执行控制**
- **燃尽图**：显示剩余工作量随时间的下降（虚线为计划线）；**燃起图**：显示已完成工作。两者基于相同数据、不同视角。
- **项目数据采集与分析**：Scrum 要求透明性，产品增量是最重要的透明方式；每日站会更新 Sprint 待办列表剩余工作量，燃尽图 Y 轴剩余工作、X 轴 Sprint 时间。若燃尽线临近结尾仍不向下接近完成点，需减小范围或改进工作方式。
- **趋势燃尽图**：如 Sprint 前领取估算 15 天任务（15×8=120 小时），每天更新剩余时间，与计划指导线对比，判断任务是否正常。

**2. 基于流程的敏捷执行控制**（各阶段时间长度可不同）
- **交付周期**：从项目添加到看板直至完成的全部时间。
- **周期时间**：处理一个工作项目所需的时间（从开始到完成）。
- **响应时间**：一个工作项目等待工作开始的时间（从准备就绪到第一列）。

**3. 交付可用价值的衡量**
- 燃尽图/燃起图、交付周期、周期时间用于评价项目；要衡量「已完成的工作」，不能未完成功能就衡量故事点——违背「可用的软件是衡量进度的主要指标」原则。
- 故事点对团队而言是唯一的，相对估算无法跨团队比较或相加速度。

**4. 敏捷背景下的挣值管理**
- 挣值基于已完成功能，可用产品待办列表燃起图显示已完成价值（左 Y 轴故事点、右 Y 轴支出）。
- 传统 SPI/CPI 易转换为敏捷术语：如计划一次迭代完成 30 个故事点、实际 25 个，SPI=25/30=0.83；CPI=EV/AC=$2.2M/$2.8M=0.79（投入 1 美元只得 79 美分）。

### 14.2.5 与计划偏差的管理

**偏差管理三类手段**：
- **绩效审查**：按进度基准测量、对比、分析进度绩效（实际开始/完成日期、完成百分比、剩余持续时间）。
- **趋势分析**：检查绩效随时间变化，判断改善还是恶化，与未来绩效目标对比。
- **偏差分析**：关注实际与计划起止日期、持续时间和浮动时间的偏离，确定原因与程度、评估影响、决定纠正/预防措施（非关键路径延误影响小，关键/次关键活动稍许延误需立即行动）。

**布鲁克斯法则**：向已滞后项目增加人力会使项目更加滞后。管理层在项目滞后时往往首先想到加人。破解之道：把不需要项目背景知识的工作（如与项目背景无关的函数开发、非项目相关的例行「项目干扰」）交给新人，让原有人力专注最值得做的事。

**1. 时间偏差管理注意事项**
- 进度冲突是项目管理最主要的冲突；安排进度「先紧后松」，与上层/客户沟通「先松后紧」留余地。
- 过分重视进度最易误导项目、伤害质量。进度滞后主因：范围/成本变化、风险分析不足、对项目要素理解掌控不够；还包括项目成员职业素养问题。
- 出现第一次进度偏差时项目经理就应**介入诊断、挖掘根源**，而非等大偏差再应急处理。
- 估算很重要，不切实际的进度只能延期或降质；任务完成百分比不可靠，可靠方法是任务细分并定义严格出入口准则。

**2. 成本偏差管理注意事项**
- 必须核算项目人力成本：预算时明确人力总数，执行中记录实际人力，结束时核算盈亏；对利润低、风险大的项目，多投入一个人月就可能赔本，需动态监控人力投入。

**3. 进度计划变更**
- 进度基准的任何变更须经实施集成变更控制过程审批，关注：判断当前状态、影响变更因素、重估进度储备、判断是否已变更、管理变更。

## 14.3 质量计划执行控制

> 质量的执行控制是对软件质量进行度量后做出的决策，促使产品符合标准；围绕**质量保证**和**质量控制**两方面进行，二者相互作用、可能交叉，且是持续不断的过程。

### 14.3.1 质量保证的执行

- **质量保证（QA）**：在项目过程中实施的有计划、有系统的活动，确保项目满足相关标准。可对内（项目组/组织）或对外（客户等）提供。
- QA 三要点：① 定期评价项目各方面表现；② 评价推测项目最终能否达到质量指标；③ 帮助相关人员建立质量信心。
- **主要活动**：
  - **产品审计**——按产品标准从使用者角度编写审计要素，审计产品、记录不符合项、出审计报告（可审计需求/设计/源代码/测试报告等）。
  - **执行过程审计（质量审查）**——对项目质量管理活动的结构性复查，确保活动遵循规程，总结经验教训。
- 质量保证是软件透明开发的主要环节，是监视机构和上报机构；独立 QA 组享有「越级上报」权，发现问题可直接向上级报告，对项目组起威慑作用；但 QA 人员应耐心协调、尽量组内解决，减少开发人员附加工作量。

### 14.3.2 质量控制的执行

- **质量控制（QC）**：检查项目成果是否符合质量标准，并找出消除不合格原因的方法，贯穿项目执行全过程。
- QC 三要点：① 控制对象是项目工作结果；② 依据相关质量标准跟踪检查；③ 对不满意问题分析原因、采取措施消除。
- **重点流程**：代码测试覆盖率监测、错误追踪与修复、定期性能监测、用户反馈和需求收集。
- **方法与策略**：

1. **技术评审（TR）**：尽早发现工作成果缺陷。主体为设计产品（需求规约、设计规格、代码、测试计划、手册等）。建议流程：召开评审会（3~5 人、每次 ≤2 小时）→ 开发组讲解 → 提问讨论 → 做出决策（接受/拒绝/暂接受需修改）→ 完成评审报告。
   - 应优先评审关键环节：项目计划、软件架构设计、数据库逻辑设计、系统概要设计。
   - 很多项目表面因性能失败，实因设计阶段技术评审不够而失败。
   - **对等评审**：由背景能力相当的人员对工作产品评审，是提高生产率与质量的重要手段。
   - **检查表（checklist）**：结构化验证工具，先确认该做的工作、再落实是否完成。
2. **代码走查**：编码阶段开发人员自查，可发现测试无法监测的逻辑错误；**代码评审**是更高一层（一群人阅读讨论、逐句讲解逻辑），静态分析过程。
3. **测试**：工作量最大的质量工作，重点是测试用例设计。层次包括单元测试、集成测试、系统测试、功能测试（重中之重）、性能测试、压力测试、接收测试。
   - 测试目的在证明软件**有错误**，而非证明正确；成功的测试是发现至今未发现的错误。
   - 质量控制应尽早开展（越早越能保证质量、降低成本），在需求/设计/编码阶段通过评审保证质量。
4. **返工**：将有缺陷项改造为符合要求和设计规格的项，是导致延误的常见原因，应尽力减少。
5. **数据分析手段**：
   - **控制图法**：展示质量随时间变化，上下限为可允许最大/最小值；连续 7 个或更多点落在平均线同一方向（即使都在受控范围内）即说明存在质量问题，称为**七点规则**。
   - **趋势分析**：依过去成果预测未来质量；**Pareto 分析图**源自 Pareto 规则——80% 的问题由 20% 的原因引起（优先解决前两个主要问题）。
   - **因果图 / 直方图**：识别质量缺陷可能造成的结果 / 按来源展示缺陷数量。
   - **抽样统计**：以小批量抽样检验确定批量产品质量，抽样频率和规模在质量计划中确定（成本低于 100% 检查，但可能导致更高失败成本）。
   - **缺陷跟踪核查表**：跟踪缺陷全过程（原因、引入阶段、影响、状态、解决方案）。

### 14.3.3 敏捷项目质量执行

- 敏捷要求整个项目期间**频繁开展质量审核**，而非临近结束才执行：定期检查质量过程效果、寻找问题根本原因、通过回顾会议评估改进方法。
- 关注小增量工作、频繁提交，以在项目早期发现不一致和质量问题、降低质量成本。
- 典型质量活动：结对编程、TDD、持续集成、不同层面测试、迭代评审、验收测试驱动开发、迭代回顾会议。

## 14.5 MED 项目核心计划执行控制案例分析

> 「医疗信息商务平台」项目的范围、时间、成本、质量计划执行控制。

### 14.5.1 范围计划的执行控制

- 采用敏捷模型，通过迭代和增量有效应对变更；每个迭代完成即产生可发布版本，不断与用户反馈、更新产品列表，范围变更得到有效控制。
- 变更表实例（表 14-13）：变更「自动保存竞拍记录」，影响分析为进度、费用、资源计划，成本增加 5 人天、进度延长 3~4 天，变更程度「低」，审批「批准变更」。

### 14.5.2 时间、成本的执行控制

- 计划 4 个迭代，原则「**远粗近细**」：总体计划做较粗控制，每个 Sprint 做严格精细化控制。

**总体计划（1~15 周）**：依据 0/100 规则做盈余分析，每周任务基本按计划完成，第 9 周略有提前、第 14 周略有滞后；任务结束时 **CPI=0.94**，超出预算。

**每个迭代**：每天站立会议统计任务进展，实时更新 Sprint 待办列表，用跟踪甘特图与燃尽图跟踪（如「组织成员注册」任务在 7 月 11 日、7 月 13 日的燃尽图，及第一个 Sprint 在 7 月 18 日的燃尽图）。

### 14.5.3 质量计划的执行控制

- 案例包括需求管理过程评审报告、软件系统设计评审报告、阶段评审过程评审报告及问题图示。
- **需求管理过程评审报告**：针对进入条件（用户初始需求、参与人员）与需求确认过程逐条评审（如「本项目没有进行配置管理，只进行版本管理」）。
- **软件系统设计评审报告**：评审合同标准符合性、可维护性、架构合理性、系统安全性、性能、数据库、模块等项，结论「基本符合要求，可进行开发」。
- **阶段评审过程评审报告**：评审项目经理在里程碑点对任务完成情况、质量、产品提交、风险分析的审核职责。
- **评审缺陷统计（表 14-15）**：缺陷比率曲线显示需求导致的缺陷数量较多、比率较大，之后呈下降趋势（系统需求规约 34.4%、概要设计 30.3%、数据库设计 26.1%、详细设计 23.1%、系统测试计划 18.4%、集成测试计划 17.1%、单元模块程序 12%，控制线 20%）。

## 14.6 MSHD 项目核心计划执行控制案例分析

**第 1 次迭代范围（6 项功能）**：
- t1：用户信息和灾情信息管理数据库的建立
- t2：用户注册与登录
- t3：文本灾情信息的解码
- t4：灾情信息可视化展示
- t5：文本文件传输模块
- t6：请求响应服务

**执行情况**：t2、t3、t4 落后于计划但按规定时间完成；t5、t6 落后且未按计划完成。

**第 1 次迭代挣值分析（表 14-16）**：
- BCWP = 136 320 元，ACWP = 150 600 元，BCWS = 174 400 元
- SV = 136 320 − 174 400 = **−38 080 元**（<0，进度落后）
- CV = 136 320 − 150 600 = **−14 280 元**（<0，超预算）
- SPI = 0.78（<1）；CPI = 0.91（<1）
- BAC = 174 400 元，TAC = 1 个月：
  - EAC = BAC/CPI = 174 400/0.91 = **191 648 元**
  - SAC = TAC/SPI = 1/0.78 = **1.28 月**
  - VAC = BAC − EAC = **−17 248 元**；VAT = SAC − TAC = **0.28 月**
- TCPI 两方案：
  - **方案一**（按原定预算 BAC 完成，目标 174 400）：TCPI = (174 400−136 320)/(174 400−150 600) = 38 080/23 800 = **1.6**——每单位成本需完成原本 1.6 倍工作量，成本低但任务难完成。
  - **方案二**（按新 EAC 完成，目标 191 648）：TCPI = 38 080/(191 648−150 600) = 38 080/41 048 = **0.93**——增加一定成本，任务相对易完成。
  - 团队选择**方案二**，将保证迭代 1 完成放在最优先位置。

**第 1~2 次迭代**：燃尽图显示第 1 次迭代进度稍有落后，第 2 次迭代完成时基本与计划一致。

## 本章小结

- 核心计划的执行控制覆盖**范围、进度、成本、质量**四大方面，围绕项目「金三角」（时间、质量、成本）展开。
- 范围控制重在**变更控制**：经集成变更控制过程处理，防治范围蔓延与镀金，需求变更管理是基线变更管理的关键。
- 进度/成本控制的三大方法：**图解控制法**（甘特图、延迟线、时间线、费用曲线、资源图综合看图）、**挣值分析法**（BCWS/BCWP/ACWP/BAC/TAC → SV/CV/SPI/CPI/EAC/SAC/VAC/VAT/TCPI）、**网络图分析法**（贝叶斯网络六步：网络图→贝叶斯网络→数据处理→模型学习→网络更新→原因分析）。
- 挣值核心公式：SV=BCWP−BCWS、CV=BCWP−ACWP、SPI=BCWP/BCWS×100%、CPI=BCWP/ACWP×100%、EAC=BAC/CPI、SAC=TAC/SPI、TCPI=(BAC−BCWP)/(Goal−ACWP)；BCWP 常用 50/50、0/100 规则计算。
- 敏捷控制：交付价值而非完成百分比，燃尽图/燃起图、迭代速率、交付周期/周期时间/响应时间、敏捷挣值。
- 质量控制分**质量保证（QA）**与**质量控制（QC）**：技术评审、代码走查/评审、测试、返工，配合控制图（七点规则）、Pareto 分析（80/20）、抽样统计、缺陷跟踪等数据分析手段。
- 心法：偏差出现时尽早介入查根因，布鲁克斯法则警示不要简单靠加人救火；核心计划控制与质量、风险、人员等辅助控制相辅相成。
