# 第3章 软件项目生存期模型

> 本章讲「如何选择实施策略」：生存期模型 = 项目实施策略。核心是从**预测型**到**敏捷型**的连续谱系，以及各模型的优缺点、适用场景和选择依据。

## 核心概念速览

| 概念 | 一句话 |
| --- | --- |
| 生存期模型 | 描述开发的主要阶段、各阶段过程活动、各阶段输入输出的框架 |
| 预测型 | 提前大量计划、一次性执行（瀑布、V 模型） |
| 迭代型 | 反复反馈改进直到正确（原型） |
| 增量型 | 分段交付可立即使用的成果 |
| 敏捷型 | 迭代 + 增量结合，频繁交付（Scrum、XP 等） |
| 混合型 | 预测型与适应型（迭代/增量/敏捷）的组合 |

---

## 3.1 生存期选择

**生存期模型的三个基本特征**：
1. 描述开发的主要阶段
2. 定义每个阶段要完成的主要过程和活动
3. 规范每个阶段的输入和输出

> **人和过程**是保证项目成功的两个关键因素：好的人 + 好的过程，才能最大限度保证成功。

**发展变迁**：作坊式 → 瀑布模型 → 敏捷模型 → DevOps 模型 → AI 驱动模型。

**四大模型特征对比**（选择模型的关键参考）：

| 特征 | 预测型 | 迭代型 | 增量型 | 敏捷型 |
| --- | --- | --- | --- | --- |
| 项目需求 | 固定 | 变化 | 变化 | 变化 |
| 开发活动 | 整个项目只执行一次 | 反复执行直到正确 | 每个增量的活动执行一次 | 反复执行直到正确 |
| 产品交付 | 提交一次 | 提交一次 | 频繁小增量提交 | 频繁小增量提交 |
| 目标 | 成本可管理 | 得到正确解决方案 | 加快速度 | 通过频繁提交反馈体现客户价值 |

- 从**项目变化**角度：预测型低、迭代型高；从**提交频率**角度：预测型低、增量型高。
- 充分了解/确定需求 → 预测型；仍在发展的需求 → 适应型。
- **连续区间观**：没有模型完美适用于所有项目，每个项目在区间上找一个点实现最佳平衡。

---

## 3.2 预测型生存期模型

> 利用已知和已证明的事物减少不确定性，活动以**顺序方式**执行。适用于高确定性明确需求、稳定团队、低风险。

### 3.2.1 瀑布模型（waterfall model）

```
需求分析 → 设计 → 实施 → 测试 → 维护
```

**优点**：简单易用直观、进程严格、便于控制、早期接受基线和配置控制、按阶段设检查点。
**缺点**：初期要求完整正确需求分析（很难）、线性无反馈（用户末期才见成果、风险高）、不适合新项目、不允许/限制变更、早期错误后期才发现。
**适用**：需求很明确、功能明确完整无重大变化的系统；短期项目。

> Royce（1970）建议：在关键**原型阶段之后**应用瀑布模型，原型阶段充分理解关键技术及客户需求。

### 3.2.2 V 模型（Paul Rook, 1980）

瀑布模型的变种，**强调测试的重要性**，将开发活动与测试活动紧密对应：

| 开发活动 | 对应测试 |
| --- | --- |
| 需求分析 | 系统测试 |
| 概要设计 | 集成测试 |
| 详细设计 | 单元测试 |
| 编码调试 | （编码与调试） |

- 测试与开发**并行**：需求分析阶段就应准备系统测试、概要设计阶段准备集成测试、详细设计阶段准备单元测试。
- **优点**：简单、测试与开发对应并行、全过程质量意识。
- **缺点**：初期要求完整需求、方案必须很明确、不能存在变更。
- **适用**：需求明确 + 方案明确 + 对性能安全要求严格（航天飞机控制系统、公司财务系统）。

---

## 3.3 迭代型生存期模型

- 通过**连续原型/概念验证**改进产品，对部分完成/未完成工作反馈改进；每个新原型带来新反馈和团队见解。
- 用于识别和减少项目**不确定性**；适合复杂性高、变更频繁、范围受相关方不同观点支配的项目。
- 特点：为**学习**而优化（非交付速度），可能需要更长时间；每个迭代结束后**可以没有交付**。

> **迭代 vs 增量**：迭代应对**产品内部因素**的不确定性（澄清需求、范围、方法）；增量应对**外部因素**的不确定性（逐步开发特性，多次交付）。

---

## 3.4 增量型生存期模型

- 将需求**分段**为一系列增量产品，每个增量都经历需求分析→设计→实施→测试→交付；每个增量是一个交付成果。
- 第一个增量是**核心产品**（基本需求），交付用户评价后再计划下一个增量，直至完善产品。
- 交付的是满足客户需求**子集**的可运行产品。

**优点**：适应变化、降低开发风险（先做主要/高风险功能）、更快得到可操作系统、减少需求变更。
**缺点**：需开放式体系结构（构件并入不破坏已建部分）、需求不稳定时部分增量可能重开发、过程控制失去整体性。
**适用**：已有产品升级/新版本、完成期限严格、领域熟悉且已有原型、市场用户把握不准需逐步了解。

---

## 3.5 敏捷型生存期模型

- 符合敏捷宣言原则的模型，结合**迭代 + 增量**；客户满意度随早期持续交付提升。
- 两种实现方式：**基于迭代**（相等时间盒内交付完整功能）与**基于流程**（按能力从待办列表提取功能、限制 WIP）。

### 3.5.1 Scrum（核心 = 3-3-5-5）

**3 个角色**：
1. **产品负责人（PO）**——代表客户意愿与全体干系人，写用户故事、排优先级、维护产品订单（product backlog），保证团队做「正确的事」。
2. **Scrum 主管（SM）**——保证 Scrum 过程正确实施，讲授规则、确保遵守，仆人式领导。
3. **开发团队**——跨职能自组织（一般 5~9 人），将 Sprint 订单转化为功能增量，共同负责。

**3 个工件**：
1. **增量（Increment）**——一个 Sprint 完成的产品待办项 + 之前所有增量的价值总和；必须「完成」（可用）。
2. **产品待办事项列表（Product Backlog）**——有序的产品想法列表，**所有需求的唯一来源**，动态变化，由 PO 维护。
3. **Sprint 待办事项列表（Sprint Backlog）**——当前 Sprint 要完成的任务清单；任务以小时为单位分解（>16h 需再分解），仅团队有权更改。

**5 个事件**：
1. **Sprint 计划会议**（≤8h：前 4h PO 讲最高优先级需求，后 4h 安排 Sprint）→ 产出 Sprint 待办列表
2. **Sprint 迭代开发**（每个 Sprint 交付可用增量，频繁集成、早发现错误）
3. **每日站立会议**（≤15min、站立、固定时间地点；每人答 3 问：今天完成什么/明天做什么/有何障碍）
4. **Sprint 评审会议**（展示软件、收集反馈、决定下一次内容）
5. **Sprint 回顾会议**（≤4h，反思并持续改进）

> Sprint（冲刺）是 Scrum 核心，周期 1~4 周（限制在一个月左右），长度保持一致；产出可用的潜在可发布产品增量。产品待办事项**梳理**贯穿全程（排序、移除、升级、分解、归并、估算）。

**5 个价值观**：勇气（courage）、开放（openness）、专注（focus）、承诺（commitment）、尊重（respect）。

### 3.5.2 XP（极限编程，Kent Beck）

**13 个核心实践**（分三个层面）：

| 层面 | 实践 |
| --- | --- |
| 整体实践（4） | 统一团队、策划游戏、小型发布、客户验收 |
| 开发团队实践（5） | 代码集体所有、编码标准、恒定速率（40h 工作）、系统隐喻、持续集成 |
| 开发者实践（4） | 简单设计、结对编程、测试驱动开发（TDD）、重构 |

- **实施三原则**：快速反馈、假设简单、包容变化。
- 关键实践要点：结对编程（两人一台机器、提高质量与知识交流）；TDD（先写测试、bug 立即加测试）；重构（随时随地消除重复、提高重用性）；小型发布（频繁发布、甚至每日）。

### 3.5.3 OpenUP

基于统一过程（UP）的**轻量级**、迭代增量、开放可扩展过程框架。特征：轻量级（简化过程）、迭代增量、灵活可定制、自适应、协作沟通、**用例驱动**、**风险导向**。适合中小型项目。

### 3.5.4 看板方法（kanban）

- 基于**可视化**的敏捷方法，用看板跟踪工作项状态；不规定迭代长度，强调**持续交付**，通过限制 WIP 保证高质量高效率。
- 源自精益生产（大野耐一 1953 年用于丰田）；状态墙含用户故事、bug、非直接产生业务价值的任务（重构、搭建环境），用不同颜色卡片统一管理。

### 3.5.5 Scrumban 方法

Scrum 到看板的**过渡/混合**方法：以 Scrum 为框架、看板为过程改进方法；用小冲刺 + 看板面板可视化，用 **WIP 限制**管理，设置**规划触发因素**决定何时规划下一步。

### 3.5.6 精益模型（lean）

借鉴制造业精益生产（丰田），强调**减少浪费、快速响应变化、持续学习**。两大核心概念：
- **拉式系统（pull system）**——前一环节任务完成后自动从上游提取下一个任务，以客户需求驱动。
- **价值流图（value stream mapping）**——识别过程中的浪费，最小化未完成工作和半成品。

### 3.5.7 持续交付

- 敏捷方法（XP、Scrum）的自然延伸；需求以小批量在各角色间流动，短周期小粒度频繁交付。
- **三者区别**：
  - **持续集成（CI）**：个人代码向整体交付，尽早发现问题
  - **持续部署（CD）**：集成代码尽快向运行环境交付，尽早测试
  - **持续交付**：尽快向客户交付，尽早发现生产问题
- 持续交付的前提是持续部署；需**自动化构建流水线（build pipeline）**支持。

### 3.5.8 DevOps

- **Dev + Ops** 的组合：促进开发、技术运营、质量保障（QA）三者的沟通、协作与整合。
- 背景：开发（想快速提交）与运营（想高性能高可靠低成本）目标差异 → **「混乱之墙」（wall of confusion）**。
- DevOps = 开发、技术运营、质量保障三者的**交集**，解决信息鸿沟，融合开发端与运营端。

### 3.5.9 规模化敏捷

| 框架 | 说明 |
| --- | --- |
| **Scrum of Scrums（SoS）** | 多个 Scrum 团队（3~9 人）各派代表定期开会（每日或每周 2~3 次），协调工作、清除障碍 |
| **SAFe** | 企业级规模化敏捷框架，结合敏捷、系统思维、精益、产品开发流程 |
| **LeSS** | Large-Scale Scrum，保留 Scrum 核心（角色/事件/工件），多团队交付共同产品，强调透明、检查、适应 |

## 3.6 混合生存期模型（四种）

| 方式 | 说明 | 适用场景 |
| --- | --- | --- |
| 先敏捷后预测 | 开发阶段用敏捷，之后进入明确可重复的发布阶段 | 新产品开发后推向大量用户并培训 |
| 敏捷和预测综合 | 同一生命周期同时用两者（短迭代 + 前期评估/工作分配/进度跟踪仍预测） | 团队逐步向敏捷过渡 |
| 以预测为主、敏捷为辅 | 对不确定/复杂/可能范围蔓延的部分用敏捷，其余用预测 | 整体稳定、局部不确定 |
| 以敏捷为主、预测为辅 | 特定不可协商/不可用敏捷的要素用预测 | 集成外部供应商组件等 |

## 3.7 AI 驱动项目的生存期模型

### 3.7.1 AI 驱动的传统瀑布模型（八大优化）

需求管理自动化（NLP 提取需求）→ 设计智能化 → 编码自动化 → 测试智能化 → 部署维护自动化 → 持续学习优化 → 风险管理增强 → 文档知识管理（知识图谱）。

### 3.7.2 AI 驱动的敏捷模型

- AI 协助敏捷 SDLC 每个阶段，缩短反馈环路：AI 分析工具、AI 驱动架构与设计、AI 编程助手/生成器、AI 测试工具、DevOps AI 工具。
- 综合效率可提高 **30%~50%**；Copilot 使开发效率提升超过 55%（对比蒸汽机仅提升 15%）。
- **AI 驱动 Scrum**：产品 Backlog（优先排列、预测价值）、Sprint 计划（难度估计、完成时间预测）、每日站会（自动跟踪进度、问题识别）、质量评估（数据分析）、反馈（情绪收集分析）。

**AI 项目关键考虑因素**：数据驱动开发、迭代快速实验、模型选择与集成、自动化与 CI、可解释性与透明度、安全隐私、监控维护、跨学科团队协作。

## 3.8 MED 项目生存期模型案例分析

- **采用 Scrum 敏捷模型**，分 4 个 Sprint（每冲刺约 4 周），每个 Sprint 完成提交可运行版本。
- 优先级 1~4 在第 1 个 Sprint（用户注册、用户管理、产品/经销商编辑、产品浏览查询），后续按优先级迭代。
- **各阶段定义**（需求分析、系统设计、项目规划、迭代 n 设计、迭代 n 开发、集成测试、确认测试、产品提交），每阶段含：阶段目标、进入条件、输入、输出、完成标志。

## 3.9 MSHD 项目生存期模型案例分析

- **采用多迭代增量开发模型**，理由：需求不够清晰（需逐步了解、逐步引入新数据源）、快速响应变化、持续交付价值（早期交付功能完备模块、验证可行性）。
- 模型：用户需求 → 用户故事地图 → 最小用户故事 → 迭代任务 → 开发/测试/迭代 → 阶段评价 → 调整 → 交付可运行系统。

## 模型选择速查表

| 情形 | 推荐模型 |
| --- | --- |
| 需求明确、方案明确、性能安全要求严格 | V 模型 |
| 需求明确、功能完整、短期项目 | 瀑布模型 |
| 需求不明确、需逐步澄清（内部不确定性） | 迭代型（快速原型） |
| 已有产品升级、期限严格、需快速交付价值 | 增量型 |
| 需求变化快、需持续交付与用户反馈 | 敏捷型（Scrum/XP） |
| 部分要素确定性高、部分不确定 | 混合模型 |

## 本章小结

- 生存期模型总体分**预测型**（瀑布、V）与**适应型**（迭代、增量、敏捷），混合型是二者组合。
- 选择依据：**需求稳定性、开发活动重复性、交付频率、目标**四个维度。
- 敏捷代表：Scrum（3-3-5-5）、XP（13 实践、三原则）、看板/Scrumban、精益、持续交付、DevOps、规模化敏捷（SoS/SAFe/LeSS）。
- AI 驱动模型：传统瀑布八大优化 + 敏捷 SDLC 反馈环路缩短 + AI 驱动 Scrum，效率提升 30%~50%。
- 心法：项目开发之初只能按项目特点和经验选择，并在开发过程中**不断调整**。
